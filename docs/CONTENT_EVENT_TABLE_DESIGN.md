# 콘텐츠 행동 이벤트 테이블 컬럼 설계안

- 작성일: 2026-09-30
- 상태: 팀 검토용 제안. DB 마이그레이션·API 구현·실제 적재는 별도 작업입니다.
- 기준: 현재 PostgreSQL 모델, 이벤트 종류별로 테이블을 나누자는 팀 합의.
- 구성: 이벤트 테이블 7개 + 상태 변경 요청의 재시도 방지를 위한 보조 테이블 1개.

## 1. 현재 구조와 설계 원칙

| 기존 테이블 | 현재 역할 | 이번 설계와의 관계 |
| --- | --- | --- |
| `user_account` | 사용자 계정 | `user_id BIGINT` 참조 |
| `content` | 콘텐츠 | `content_id BIGINT` 참조 |
| `topic` | 영화·음악·애니메이션 도메인 | `topic_id BIGINT` 참조 |
| `tap` | 사용자가 이용하는 도메인 공간 | 사용자 소유권과 행동 당시 문맥 확인 |
| `content_reaction` | 현재 O/X 및 좋아요 상태 | 유지. 상태 변경과 동시에 이벤트 추가 |
| `saved_item` | 현재 북마크 상태 | 유지. 저장·해제 시 이벤트 추가 |
| `content_tag`, `subtopic` | 콘텐츠별 세부 주제 | 추천 특성 데이터에 활용 |

이벤트는 발생할 때마다 새 행을 추가합니다. 일반적인 사용자 행동으로 과거 이벤트를 수정하거나 삭제하지 않습니다. 회원 데이터 삭제·보관 기간 만료 등 관리 작업은 별도 정책으로 처리합니다.

기존 반응과 북마크는 `(user_id, tap_id, content_id)` 단위입니다. 행동 이력은 `user_id + content_id`로 모을 수 있지만, **현재 선호·현재 저장 여부는 활성 `tap`에 속한 기존 상태 테이블에서 조회**합니다. 과거 탭의 이력을 새 탭의 현재 상태로 자동 복원하지 않습니다. 현재 도메인 추가 API는 삭제된 탭에 대해 복구를 요구하므로, 탭 재생성을 현재 구현된 정상 흐름이라고 가정하지 않습니다.

이벤트의 필수 FK는 `content_reaction_id`나 `saved_item_id`에 연결하지 않습니다. 현재 반응 행은 선택을 취소하면 삭제될 수 있습니다.

## 2. 7개 이벤트 테이블의 공통 컬럼

아래 컬럼은 공통 부모 테이블을 만드는 의미가 아니라, **각 이벤트 테이블에 같은 이름·자료형으로 포함하는 컬럼**입니다. `필수`는 `NOT NULL`, `선택`은 `NULL` 허용입니다.

| 컬럼 | PostgreSQL 자료형 | 필수 여부 | 기본값·제약·용도 |
| --- | --- | --- | --- |
| `event_id` | `UUID` | 필수 | PK. 논리적인 이벤트마다 생성하고 재전송에는 같은 UUID 사용. 요청 없이 DB에서 매번 새 UUID를 만들지 않음 |
| `event_seq` | `BIGINT` | 필수 | `GENERATED ALWAYS AS IDENTITY`, UNIQUE. 테이블 안에서 서버 삽입 순서를 식별 |
| `user_id` | `BIGINT` | 필수 | FK → `user_account.user_id`. 서버가 인증 정보에서 결정 |
| `content_id` | `BIGINT` | 필수 | FK → `content.content_id`. 실제 행동 대상 |
| `topic_id` | `BIGINT` | 필수 | FK → `topic.topic_id`. 서버가 행동 당시 콘텐츠 도메인에서 결정 |
| `tap_id` | `BIGINT` | 조건부 | 선호·좋아요·북마크는 필수. 다른 이벤트는 이용 경로에 따라 선택 |
| `occurred_at` | `TIMESTAMPTZ` | 필수 | 행동 시각. 상태 변경은 서버 처리 시각, 브라우저 관찰은 검증한 클라이언트 시각 |
| `received_at` | `TIMESTAMPTZ` | 필수 | 서버가 해당 이벤트를 처음 받은 시각. 재전송 시 최초 값 유지 |
| `session_id` | `UUID` | 선택 | 브라우저 탐색 세션용 ID. 로그인 토큰·인증 세션 키와 별개 |
| `source_screen` | `VARCHAR(30)` | 필수 | `home`, `topic`, `content_detail`, `saved`, `search`, `notification`, `api`, `unknown` |
| `data_source` | `VARCHAR(20)` | 필수 | `production`, `local_demo`, `automated_test`, `imported`. 서버 환경·계정 분류로 결정 |
| `schema_version` | `SMALLINT` | 필수 | 기본값 `1`, `CHECK (schema_version > 0)`. 이벤트 정의 버전 |

### 공통 규칙

- 로그인한 사용자와 현재 로컬 시연 계정을 대상으로 합니다. 익명 사용자를 지원하려면 `anonymous_id`와 로그인 후 연결 정책을 별도 설계하며, 지금 `user_id`에 임의의 공용 계정을 넣지 않습니다.
- UI 경로는 `session_id`를 보내고 Swagger 등 API 직접 호출은 `NULL`을 허용합니다. `source_screen`은 허용 목록만 받습니다.
- `event_seq`는 테이블별 번호이며 전역 이벤트 순서나 모든 트랜잭션의 커밋 순서를 뜻하지 않습니다. 같은 반응 대상의 상태 변경은 6절의 잠금 규칙 안에서 순서대로 INSERT합니다.
- 클라이언트 시각은 신뢰할 수 있는 서버 시각과 구분합니다. 비정상적인 미래 시각·허용 범위 밖의 지연 전송은 거부하거나 별도 수집 오류로 남깁니다. 허용 범위는 수집 정책으로 합의하고, 거부된 이벤트를 정상 시각으로 조작해 학습에 넣지 않습니다.
- `data_source`를 클라이언트가 `production`으로 지정할 수 없게 합니다. 초기 로컬 실행은 `local_demo`로 분류합니다. `imported`는 일반 행동 수집 API에서 허용하지 않습니다.
- 이메일, 닉네임, 로그인 토큰, 공유 대상 연락처, 임의의 전체 URL은 저장하지 않습니다. 설명되지 않은 데이터를 담는 범용 `metadata` 컬럼은 초기안에서 제외합니다.
- 현재 문맥에 존재하지 않는 값을 임의로 만들지 않습니다. 추천 시스템이 아직 없으면 추천 요청 ID와 모델 버전은 `NULL`입니다.
- 이벤트 테이블에는 `UNIQUE(user_id, content_id)`를 두지 않습니다. 같은 글에 대한 여러 번의 실제 행동은 각각 저장합니다.

## 3. 이벤트별 추가 컬럼

아래 표의 컬럼을 각 테이블의 공통 컬럼에 더합니다.

### 3.1 `content_impression_event` — 실제 화면 노출

| 컬럼 | 자료형 | 필수 여부 | 의미·제약 |
| --- | --- | --- | --- |
| `surface_view_id` | `UUID` | 필수 | 홈·토픽·저장함 등 목록 화면을 한 번 방문한 단위 |
| `feed_request_id` | `UUID` | 선택 | 이 콘텐츠를 반환한 목록 API 응답 식별자 |
| `position` | `INTEGER` | 필수 | 해당 화면 목록의 1부터 시작하는 절대 순번. `CHECK (position >= 1)` |
| `visible_ratio` | `NUMERIC(5,4)` | 필수 | 기록 조건을 충족한 시점의 카드 노출 비율. 0~1 |
| `visible_duration_ms` | `INTEGER` | 필수 | 기준 노출 비율을 연속으로 충족한 시간. 0 이상 |
| `recommendation_request_id` | `UUID` | 선택 | 내부 추천 결과 식별자. 외부 공급자 ID는 나중에 별도 매핑 |
| `recommendation_model_version` | `VARCHAR(100)` | 선택 | 당시 추천 모델 또는 추천 정책 버전 |

제안하는 초기 측정 기준은 **카드 면적 50% 이상이 활성 화면에 연속 1초 이상 노출**된 시점입니다. 서비스용 제안값이며 표준이나 검증된 최적값을 의미하지 않습니다. 적용 시 `schema_version=1`의 정의로 고정하고 기준 변경 시 버전을 올립니다.

- `UNIQUE(user_id, surface_view_id, content_id)`로 한 목록 방문 중 같은 글의 스크롤 재등장·재렌더링을 중복 집계하지 않습니다. 새 방문이나 명시적 새로고침에는 새 `surface_view_id`를 발급합니다.
- 최초 유효 노출의 순번과 측정값을 보존합니다. 목록 API의 응답·프리패치 자체는 노출이 아닙니다.
- 첫 1초 전에 클릭한 경우 노출 이벤트가 없을 수 있으며, 열람을 누락시키거나 가짜 노출을 생성하지 않습니다.

### 3.2 `content_open_event` — 상세 화면 열람

| 컬럼 | 자료형 | 필수 여부 | 의미·제약 |
| --- | --- | --- | --- |
| `view_id` | `UUID` | 필수 | 상세 화면을 한 번 방문한 단위. UNIQUE |
| `impression_id` | `UUID` | 선택 | 유입된 노출 이벤트의 `event_id`. 직접 접속·노출 기준 미충족이면 NULL |
| `entry_method` | `VARCHAR(20)` | 필수 | `card`, `direct`, `bookmark`, `notification`, `search`, `unknown` |

콘텐츠 본문을 실제 상세 화면에 표시했을 때 한 번 기록합니다. API GET, Next.js 프리패치, 컴포넌트 재렌더링은 새로운 열람이 아닙니다. 다시 방문하거나 새로고침하면 새 `view_id`를 사용합니다. 임의의 화면 터치나 실패한 카드 클릭은 열람으로 세지 않습니다.

### 3.3 `content_read_event` — 읽은 시간·스크롤

| 컬럼 | 자료형 | 필수 여부 | 의미·제약 |
| --- | --- | --- | --- |
| `view_id` | `UUID` | 필수 | 해당 상세 방문의 `content_open_event.view_id` |
| `checkpoint_no` | `INTEGER` | 필수 | 해당 방문 안에서 증가하는 측정 번호. 1 이상 |
| `active_duration_ms` | `BIGINT` | 필수 | 해당 방문 시작부터의 **누적** 활성 체류 시간. 0 이상 |
| `max_scroll_ratio` | `NUMERIC(5,4)` | 필수 | 해당 방문에서 도달한 본문 최대 진행 비율. 0~1 |
| `checkpoint_reason` | `VARCHAR(20)` | 필수 | `interval`, `hidden`, `leave` |

- `UNIQUE(user_id, view_id, checkpoint_no)`로 같은 체크포인트 재전송을 제거합니다.
- 같은 `view_id`의 누적 시간과 최대 스크롤 값은 측정 번호에 따라 감소하지 않아야 합니다. 역순 전송은 수신 시각 순으로 해석하지 않습니다.
- 활성 시간은 문서가 보이고 포커스가 있으며 최근 활동이 있는 동안만 증가시킵니다. 예: 활동 없이 60초가 지나면 일시 정지하고 다음 활동부터 재개. 이 기준도 초기 제안값입니다.
- 스크롤 비율은 본문 시작부터 뷰포트 하단까지의 도달 위치를 본문 길이로 나눈 값으로 정의하고 0~1로 제한합니다. 첫 화면에 모두 보이는 짧은 글은 1일 수 있지만, 그 사실만으로 완독을 확정하지 않습니다.
- 주기 전송과 화면 숨김·이탈 시 전송을 함께 사용합니다. 브라우저 강제 종료로 마지막 기록이 유실될 수 있으므로 체류 시간은 관측값입니다.
- **방문별 시간은 `MAX(active_duration_ms)`를 사용합니다. 체크포인트 시간을 SUM하지 않습니다.** 사용자별 총시간은 방문별 MAX를 먼저 구한 뒤 합산합니다.

### 3.4 `content_preference_event` — 더 볼래요·그만 볼래요

| 컬럼 | 자료형 | 필수 여부 | 의미·제약 |
| --- | --- | --- | --- |
| `previous_value` | `VARCHAR(1)` | 선택 | 변경 전 `O`, `X`, NULL |
| `new_value` | `VARCHAR(1)` | 선택 | 변경 후 `O`, `X`, NULL. NULL은 선택 취소 |
| `view_id` | `UUID` | 선택 | 상세에서 발생했다면 해당 방문 ID |

- `tap_id NOT NULL`.
- 각 값에 `CHECK (value IN ('O', 'X'))`. NULL은 의도적으로 허용합니다.
- `CHECK (previous_value IS DISTINCT FROM new_value)`로 `O→O`, `NULL→NULL`을 제외합니다. NULL을 포함하므로 단순 `<>`로 대체하지 않습니다.
- 기존 반응 행이 없으면 이전값은 NULL입니다. 두 값 모두 서버가 잠근 현재 상태에서 결정합니다.
- 초기 대상 범위는 이 행의 `content_id`입니다. 장르·가수·감독 전체에 대한 명시적 거부라고 자동 확장하지 않습니다. 범위를 확대하려면 별도 대상 컬럼·사용자 안내·정책 버전을 설계합니다.

### 3.5 `content_like_event` — 좋아요·취소

| 컬럼 | 자료형 | 필수 여부 | 의미·제약 |
| --- | --- | --- | --- |
| `previous_value` | `BOOLEAN` | 필수 | 변경 전 좋아요 여부. 기존 행이 없으면 false |
| `new_value` | `BOOLEAN` | 필수 | 변경 후 좋아요 여부 |
| `view_id` | `UUID` | 선택 | 상세 방문 ID |

`tap_id NOT NULL`, `CHECK (previous_value <> new_value)`. `false→true`는 추가, `true→false`는 취소입니다. 선호 O/X와는 별개로 기록합니다.

### 3.6 `content_bookmark_event` — 저장·해제

| 컬럼 | 자료형 | 필수 여부 | 의미·제약 |
| --- | --- | --- | --- |
| `action` | `VARCHAR(10)` | 필수 | `add` 또는 `remove` |
| `view_id` | `UUID` | 선택 | 상세 방문 ID. 목록·저장함에서 발생하면 NULL 가능 |

- `tap_id NOT NULL`, `CHECK (action IN ('add', 'remove'))`.
- 기존 행 없음 또는 `status='deleted'` → `kept`이면 `add`입니다.
- `kept` 또는 `resurface_off` → `deleted`이면 `remove`입니다.
- **`resurface_off`도 저장된 상태입니다.** `kept↔resurface_off`는 저장·해제 이벤트로 기록하지 않습니다. 재노출 설정을 분석하려면 별도 설정 변경 이벤트를 추가합니다.
- 이미 저장된 글에 대한 저장 요청, 이미 해제된 글에 대한 해제 요청은 새 행동 변경 행을 만들지 않습니다.

### 3.7 `content_share_event` — 공유 시도와 결과

| 컬럼 | 자료형 | 필수 여부 | 의미·제약 |
| --- | --- | --- | --- |
| `share_attempt_id` | `UUID` | 필수 | 공유 버튼을 한 번 실행한 단위 |
| `phase` | `VARCHAR(10)` | 필수 | `start`, `result` |
| `action` | `VARCHAR(30)` | 필수 | `clicked`, `link_copied`, `native_share_resolved`, `cancelled`, `failed` |
| `method` | `VARCHAR(15)` | 필수 | `native`, `clipboard`, `unavailable` |
| `view_id` | `UUID` | 선택 | 상세 방문 ID |
| `error_code` | `VARCHAR(50)` | 선택 | 실패 시 허용 목록의 코드. 예: `NOT_ALLOWED`, `NO_TARGET_OR_CANCEL`, `UNAVAILABLE`, `UNKNOWN` |

- `UNIQUE(user_id, share_attempt_id, phase)`로 시도당 시작 1행·결과 최대 1행을 저장합니다. 시작과 결과는 서로 다른 `event_id`입니다.
- `phase='start'`이면 `action='clicked'`이며 `error_code IS NULL`입니다. 결과 단계에는 `clicked`가 올 수 없습니다.
- `link_copied`는 `method='clipboard'`, `native_share_resolved`는 `method='native'`일 때만 허용합니다. 성공 결과에 오류 코드를 넣지 않습니다.
- 브라우저가 알려준 범위만 기록합니다. 플랫폼에 따라 `AbortError`는 취소 외에도 공유 대상 부재일 수 있으므로 `cancelled`를 확실한 사용자 의사로 학습하지 않습니다. 필요하면 `NO_TARGET_OR_CANCEL`로 구분합니다.
- `native_share_resolved`는 공유 API 처리 결과이며 상대방 전달 완료를 보장하지 않습니다. 카카오톡 등 최종 공유 앱을 알 수 없다면 추정하지 않습니다.
- 공유 횟수 계산에서 시작과 결과를 두 번 더하지 않습니다. 시도 수는 `share_attempt_id` 단위, 복사 수는 `link_copied` 결과 단위로 계산합니다. 결과가 안 오면 미관측 상태로 둡니다.

## 4. 외래키·문맥 연결·인덱스

### 4.1 물리 FK 제안

| 연결 | 삭제 정책 제안 | 이유 |
| --- | --- | --- |
| `user_id → user_account.user_id` | `ON DELETE CASCADE` | 계정 실삭제 시 사용자 이벤트도 삭제. 탈퇴 상태 변경만으로는 실행되지 않음 |
| `content_id → content.content_id` | `ON DELETE RESTRICT` | 콘텐츠는 기존 `deleted_at`을 사용하는 논리 삭제를 기본으로 하여 이력 보존 |
| `topic_id → topic.topic_id` | `ON DELETE RESTRICT` | 참조 중인 도메인 실삭제 방지 |
| `(tap_id, user_id) → tap(tap_id, user_id)` | `ON DELETE NO ACTION`, `DEFERRABLE INITIALLY DEFERRED` | 기존 복합 UNIQUE 재사용, 다른 사용자의 탭 참조 방지. 계정 삭제 CASCADE는 트랜잭션 종료 시 일관성 확인 |

- 탭은 논리 삭제를 기본으로 합니다. 이벤트를 유지한 채 탭만 실삭제하는 작업은 허용하지 않습니다.
- `topic_id = content.topic_id` 및 탭의 도메인 일치는 서버가 기록 시 검증합니다. 위의 개별 FK만으로 세 테이블 간 도메인 일치까지 보장되지는 않습니다. DB에서도 강제하려면 별도 복합 UNIQUE/FK 또는 트리거가 필요합니다.
- 회원 탈퇴 시 이벤트 처리와 학습 데이터·캐시 삭제를 별도 구현해야 합니다. CASCADE가 외부 파일이나 학습 결과까지 삭제하지는 않습니다. 실제 보관 기간은 팀 합의 항목입니다.

### 4.2 브라우저 이벤트 간 연결

`impression_id`, 다른 테이블의 `view_id`, 추천 요청 ID는 **초기안에서 논리적 연결 키**로 두며, 이벤트 간 즉시 물리 FK를 걸지 않습니다. 결과·읽기 이벤트가 네트워크 지연으로 부모 이벤트보다 먼저 도착할 수 있기 때문입니다.

- 부모가 있으면 `user_id`, `content_id`, `session_id` 문맥을 검증합니다. 공유 시도의 각 단계도 같은 사용자·콘텐츠·방식이어야 합니다.
- 부모가 아직 도착하지 않았다면 연결 확인을 보류하고, 늦게 도착하면 수집·집계 단계에서 연결합니다. 부모 방문이 끝내 없는 읽기 이벤트는 검증된 읽기 시간에 포함하지 않습니다.
- 사용자·콘텐츠·방문 문맥이 불일치한다고 확인된 이벤트는 연결 분석뿐 아니라 읽기 시간·공유 횟수 등 관련 추천 집계 전체에서 제외하고 오류 지표를 남깁니다. 원본을 임의로 고치지 않고 별도의 검증 결과나 검증된 집계 뷰로 제외를 일관되게 적용합니다. 일반 조회에서도 다른 사용자 데이터와 연결하지 않습니다.
- 각 테이블의 `user_id`, `content_id` FK 및 인증·열람 권한 검증은 그대로 적용합니다. 논리 연결 키를 보냈다는 사실만으로 다른 사용자의 이력을 조회할 수 없습니다.

### 4.3 인덱스

각 테이블의 기본 후보:

1. PK `event_id` 및 UNIQUE `event_seq`.
2. `(user_id, occurred_at DESC)` — 사용자별 최근 행동.
3. `(content_id, occurred_at DESC)` — 콘텐츠별 행동.
4. 위 각 절의 방문·체크포인트·공유 단계 UNIQUE.

기간별 전체 추출은 `(received_at, event_seq)` 인덱스를 조회량에 따라 추가합니다. FK를 선언한다고 참조하는 쪽 인덱스가 자동 생성되는 것은 아니므로 삭제·탭 조회 성능도 실제 쿼리로 확인합니다. 초기에는 파티셔닝이나 모든 컬럼의 인덱스를 추가하지 않습니다.

## 5. 보조 테이블 `content_action_request` — 상태 변경 요청 중복 방지

이 테이블은 추천 학습용 이벤트가 아니라, **선호·좋아요·북마크 API가 같은 요청을 다시 실행하지 않도록 처리 결과를 보관**합니다. 이벤트 PK만으로는 이벤트가 생기지 않는 동일 상태 요청의 재실행까지 막을 수 없습니다.

| 컬럼 | 자료형 | 필수 여부 | 의미·제약 |
| --- | --- | --- | --- |
| `user_id` | `BIGINT` | 필수 | FK → `user_account.user_id`, `ON DELETE CASCADE` |
| `request_id` | `UUID` | 필수 | 사용자 동작마다 생성하는 재시도 키. 복합 PK `(user_id, request_id)` |
| `action_type` | `VARCHAR(20)` | 필수 | `preference`, `like`, `bookmark` |
| `content_id` | `BIGINT` | 필수 | 대상 콘텐츠 FK, `ON DELETE RESTRICT` |
| `tap_id` | `BIGINT` | 필수 | 위와 같은 소유자 복합 FK |
| `payload_hash` | `VARCHAR(64)` | 필수 | 대상·요청값·문맥 등 불변 요청 필드의 정규화된 SHA-256. 같은 키의 다른 요청 검출 |
| `result` | `VARCHAR(10)` | 필수 | `changed`, `noop` |
| `event_id` | `UUID` | 선택 | 변경이 있을 때 생성된 이벤트 ID. `action_type`으로 대상 테이블 식별 |
| `response_status` | `SMALLINT` | 필수 | 처리된 HTTP 응답 코드 |
| `response_body` | `JSONB` | 선택 | 재전송에 반환할 원래 응답. 토큰·개인정보 제외, 204는 NULL |
| `created_at` | `TIMESTAMPTZ` | 필수 | 최초 처리 시각 |

제약: `changed`이면 `event_id IS NOT NULL`, `noop`이면 `event_id IS NULL`. `event_id`는 여러 테이블 중 하나를 가리키므로 단일 물리 FK를 걸 수 없으며, 같은 트랜잭션에서 정합성을 보장합니다. 변경 이벤트 ID에는 UNIQUE를 두고 요청의 타입에 맞는 테이블에만 생성합니다.

초기안에서는 요청 기록을 자동 만료하지 않습니다. 만료시킬 경우 오래된 재시도를 거부할 수 있는 서버 검증 요청 유효기간 규약을 먼저 추가합니다. 결과 보관만 지우고 오래된 요청을 새 요청처럼 실행하면 취소된 선호·저장이 되살아날 수 있습니다.

## 6. 저장 순서와 동시성

선호·좋아요·북마크 API는 다음 처리를 한 트랜잭션으로 묶습니다.

1. 인증으로 `user_id`를 확정하고 요청 형식·대상 소유권을 확인합니다.
2. `(user_id, request_id)` 처리 기록을 조회합니다. 이미 있으면 요청 해시를 비교하고, 같으면 기존 결과를 반환합니다. 다르면 409로 거부합니다. 이 단계에서 상태 변경을 다시 실행하지 않습니다.
3. 초기 구현은 해당 사용자의 `tap` 행을 `SELECT ... FOR UPDATE`로 잠급니다. 같은 탭의 다른 콘텐츠 변경도 직렬화되는 비용이 있지만, 아직 존재하지 않는 반응 행에 대한 동시 생성까지 다룰 수 있습니다.
4. 잠금 획득 후 요청 기록을 다시 확인하고, 활성 탭·콘텐츠 유효성을 검증한 뒤 최신 상태를 읽습니다. 동시에 같은 키가 다른 대상에 도착한 경우에는 요청 PK 충돌 시 해당 트랜잭션 전체를 롤백하고 기존 해시와 대조합니다.
5. 실제 변경이면 현재 상태 갱신 + 이벤트 INSERT + 요청 처리 결과 INSERT를 수행합니다. 동일 상태면 이벤트 없이 `noop` 처리 결과만 INSERT합니다.
6. 모두 성공하면 커밋합니다. 하나라도 실패하면 함께 롤백합니다. 취소 시 반응 행을 삭제하더라도 이벤트는 유지합니다.

브라우저 관찰 이벤트는 이벤트 ID 및 자연 중복키를 검사해 저장합니다. 같은 키에 다른 콘텐츠·값이 오면 조용히 덮어쓰지 않고 충돌로 처리합니다. 클라이언트에서는 관찰 이벤트를 재전송하는 동안 최초 시각·값도 유지합니다.

이 규칙은 **재시도된 동일 요청**을 보호합니다. 서로 다른 새 요청이 역순 도착하는 문제는 별개이므로, 초기 UI는 같은 상태 변경 대상을 한 번에 하나만 요청하도록 하고 완료 후 다음 요청을 보냅니다. 다중 탭에서 엄격한 사용자 의도 순서까지 보장하려면 별도 상태 버전과 낙관적 잠금 규약이 필요합니다. 초기 동시 새 요청은 서버가 잠금을 획득한 순서로 반영합니다.

## 7. 기록 예시와 집계 규칙

아래는 같은 사용자·콘텐츠·활성 탭에서 실행한 가상 예시입니다. e1·r1 등은 설명용이며 실제 값은 UUID입니다.

| 순서 | 행동 | 이벤트 행 | 현재 상태 |
| --- | --- | --- | --- |
| 1 | 더 볼래요, 요청 r1 | 선호 e1: NULL → O | O |
| 2 | r1 네트워크 재시도 | 추가 없음. 원래 응답 재사용 | O |
| 3 | 다시 O 요청 r2 | 이벤트 없음. r2는 noop 기록 | O |
| 4 | 그만 볼래요, 요청 r3 | 선호 e2: O → X | X |
| 5 | 과거 요청 r2 재전송 | 추가 없음. r2를 재실행하지 않음 | X |
| 6 | 선호 취소, 요청 r4 | 선호 e3: X → NULL | 선택 없음 |
| 7 | 저장, 해제, 다시 저장 | 북마크 add / remove / add 3행 | 저장됨 |

추천 데이터 처리 기준:

- 이벤트 종류별 테이블은 공통 형태의 `UNION ALL` 뷰로 조회할 수 있습니다. 이때 `event_type`을 테이블별 상수로 추가하며 통합 행의 식별자는 `(event_type, event_id)`입니다.
- 원본에는 행동과 관측값을 저장합니다. 추천 점수·가중치는 학습 파이프라인에서 버전별로 계산합니다.
- 선호 취소, 북마크 해제, 공유 취소를 명시적인 부정 선호 X와 동일하게 처리하지 않습니다. 아무 행동이 없다고 싫어한다고 단정하지 않습니다.
- 열람·공유·저장 이벤트를 함께 더해 단일 횟수로 만들지 않습니다. 여러 이벤트가 같은 방문·시도를 나타낼 수 있습니다.
- 현재 저장·선호는 활성 탭의 상태 테이블을 사용합니다. 과거 특정 시점의 상태를 학습하려면 그 시점 이전 이벤트와 탭 생애주기 자료가 필요합니다. 현재 상태를 과거 정답에 섞지 않습니다.
- 동일 상태 대상의 최신 변경 순서는 직렬화된 서버 처리와 `event_seq`를 사용하며, 클라이언트 시각만으로 결정하지 않습니다. 전체 테이블을 합칠 때 서로 다른 테이블의 `event_seq`를 비교하지 않습니다.
- 초기 로컬·자동 테스트 데이터는 서비스 학습에서 제외합니다. 정식 수집 시작 전에 존재한 상태를 실제 행동 이벤트처럼 소급 생성하지 않습니다. 필요하면 수집 시작 시점의 기준 상태 스냅샷을 별도로 남깁니다.

### 콘텐츠 특성·학습 데이터 버전

현재 `content_tag`는 최신 연결이며 과거 태그 이력을 제공하지 않습니다. 이번 이벤트 컬럼만으로 과거의 장르·분위기·인물 분류까지 재현할 수 있는 것은 아닙니다.

첫 학습 데이터 추출부터 콘텐츠 특성 스냅샷, 분류 규칙 버전, 집계 코드 버전, 이벤트 추출 기준 시각을 함께 보관합니다. 태그 변경 전후의 정확한 시점별 추천을 평가하려면 **태그 유효기간을 가진 이력 또는 콘텐츠 특성 버전 테이블**을 추가합니다. 이벤트 정의인 `schema_version`을 태그 버전으로 대신 사용하지 않습니다. 세부 주제가 여러 개인 글을 위해 이벤트에 단일 `subtopic_id`를 필수로 넣지 않습니다.

## 8. 구현 시 확인할 사례

1. 동일 요청 재전송과 원래 noop이었던 오래된 요청 재전송 모두 최신 상태를 바꾸지 않는다.
2. 같은 대상의 동시 상태 변경에서 이전값·이후값·최종 상태가 일치한다. 첫 반응 생성과 반응 행 삭제 후 재생성도 포함한다.
3. 상태 변경 실패 시 이벤트와 요청 처리 결과가 함께 롤백된다.
4. 노출 재렌더링, 상세 프리패치, 읽기 체크포인트 재전송으로 건수가 부풀지 않는다.
5. 누적 읽기 시간 10초·20초·30초를 보내면 총 읽기 시간은 30초다.
6. 북마크 재노출 설정만 끄면 remove 이벤트가 생기지 않는다.
7. 공유 시작·결과가 순서가 바뀌어 도착해도 한 시도로 집계된다. API resolve를 실제 전달 완료로 표시하지 않는다.
8. 다른 사용자의 탭·방문·노출 ID를 보내도 다른 사용자 이력과 연결되지 않는다.
9. 탭 논리 삭제, 사용자 실삭제, 콘텐츠 논리 삭제 시 합의한 이력 정책이 지켜진다.
10. 로컬 시연 데이터가 정식 추천 학습 데이터에 섞이지 않는다.

## 9. 팀에서 확정할 사항

- 50%·1초 노출, 60초 비활동 기준 및 시간 오류 허용 범위.
- 그만 볼래요를 콘텐츠 단위로 유지할지, 주제·작품·인물 범위까지 확장할지.
- 콘텐츠/탭은 논리 삭제를 기본으로 할지와 회원 탈퇴·이벤트 보관 기간.
- 과거 시점의 추천 평가를 위한 콘텐츠 특성 이력 도입 시점.
- 클릭 시도 자체와 북마크 재노출 설정 변경도 별도 이벤트로 수집할지.

나머지 컬럼과 무결성 규칙은 이 초안을 기준으로 마이그레이션 및 수집 API 구현 항목으로 옮길 수 있습니다.

## 10. 확인한 코드와 참고 자료

- 현재 모델: `backend/app/models/user.py`, `content.py`, `catalog.py`, `v1.py`.
- 현재 상태 변경: `backend/app/services/reaction_service.py`.
- 도메인 추가·복구 조건: `backend/app/services/catalog_service.py`.
- 브라우저 공유: `frontend/lib/share-content.ts`.
- 임시 분류: [온보딩 임시 세부 주제](PROVISIONAL_ONBOARDING_INTERESTS.md).
- [PostgreSQL 제약조건 문서](https://www.postgresql.org/docs/current/ddl-constraints.html): PK, UNIQUE, FK, NULL의 CHECK 동작과 참조 인덱스 기준을 확인했습니다.
- [MDN Navigator.share](https://developer.mozilla.org/en-US/docs/Web/API/Navigator/share): 플랫폼별 Promise 처리 시점 및 오류 의미에 따라 공유 전달 완료를 별도로 추정하지 않습니다.
- [Amazon Personalize 상호작용 데이터](https://docs.aws.amazon.com/personalize/latest/dg/interactions-datasets.html): 사용자·아이템·시간·이벤트 유형·노출 문맥을 활용하는 사례입니다. 이 문서의 테이블명·분리 방식·측정 기준은 우리 서비스용 제안이며 특정 서비스의 필수 스키마가 아닙니다.
