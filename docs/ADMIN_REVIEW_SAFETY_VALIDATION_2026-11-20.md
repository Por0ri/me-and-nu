- 기준 PR: #92, `782dd1a7b033b72d45973611cde2b9484c824502`.
- Checking 기준: `8ff9ffcdf196cf9e8d8bde0e226aecad2454493c`.
- 로컬 수정 브랜치: `codex/admin-review-safety-20261120`.
- 기존 검증에서 재현한 결함: 다른 계정으로 로그인한 뒤 이전 요청을 재확인하면 새 계정의 조치로 커밋되는 문제, 불확실 상태 또는 패널 해제 후 이탈 경고가 사라지는 문제.
- 실제 쓰기 활성화는 별도 단계다. `ACTIVATION=null`을 유지하며, 이번 검증은 가상 계정·루프백 API·폐기 가능한 로컬 PostgreSQL만 사용한다.

## 요청 계약

상세 GET의 `review.scope`는 `{actorUserId, adminAccountId}` 또는 `null`이다. 현재 검수 권한이 있으면 콘텐츠가 이미 처리되어 `allowedActions`가 비어 있어도 scope를 반환한다. 응답이 유실된 성공 요청도 동일 권한으로 재확인할 수 있어야 하기 때문이다.

POST 본문은 기존 6필드를 유지한다. 최초 확인한 scope를 별도로 고정하고 모든 전송에 다음 헤더를 사용한다.

| 헤더 | 값 |
| --- | --- |
| `X-Admin-Review-Actor` | 최초 확인한 사용자 ID |
| `X-Admin-Review-Grant` | 최초 확인한 관리자 권한 부여 레코드 ID |

scope는 인증 수단이 아니다. 서버는 실제 세션과 CSRF를 검증하고, 트랜잭션에서 현재 사용자·권한 레코드를 잠근 뒤 기대 scope와 비교한다. 누락·잘못된 헤더는 거부하고, 불일치는 `409 REVIEW_SCOPE_CHANGED`로 중단한다. 콘텐츠 수정과 감사 기록 조회·생성보다 먼저 검사하며, 최신 권한으로 자동 대체하지 않는다. 같은 사용자의 권한 회수 후 재부여도 새로운 grant이므로 기존 요청을 실행하지 못한다.

프런트엔드의 사전 확인은 사용자 안내를 위한 추가 보호다. 사전 확인 직후 쿠키나 권한이 바뀌는 경우에는 서버 검증이 최종적으로 차단한다. CSRF 토큰 교체 자체를 계정 변경으로 취급하지 않는다.

## 화면과 미확정 요청

요청 진행 중·결과 불확실 상태는 패널 수명과 별개로 추적한다. 상세 재조회나 앱 내 이동으로 패널이 해제되어도 요청 번호와 원래 scope를 유지하고, 문서를 떠날 때 경고한다. 이전 처리 결과가 불확실한 상태에서 권한이 없어지거나 계정이 바뀌면 재전송을 차단하되 미확정 결과를 성공·실패로 단정하지 않는다.

브라우저 저장소에 검수 내용을 영구 저장하지 않는다. `beforeunload`는 브라우저가 허용하는 이탈 경고이며, 브라우저 강제 종료·사용자의 경고 무시 후에도 복구를 보장하는 저장 기능은 아니다.

| TypeScript 및 Webpack 프로덕션 빌드 | 통과, 정적 페이지 30/30 생성 | `validation/fixed-build-unrestricted.log` |

브라우저 검증은 실제 React 패널·전역 안내·API 클라이언트와 루프백 가짜 API를 연결했다. 원래 9개 정상 시나리오, 이전 결함 3개 재현의 수정 확인, 같은 사용자 권한 재부여, 권한 GET 실패 후 요청 보존, scope 누락·형식 오류를 포함한다. 새로고침 시 실제 `beforeunload` 대화상자를 취소하고 동일 요청이 유지되는지 확인했다. 실제 Checking 서버 브라우저 E2E와는 구분한다.

BE 합계는 서로 다른 테스트 390개다. 마지막 1개는 20개 통과 후 추가한 회귀이며, 제품 코드가 바뀌지 않아 해당 항목만 별도로 실행했다. 테스트의 PostgreSQL 컨테이너는 실행 후 제거했다. 테스트에는 헤더 누락·중복·비정상 값, 다른 계정, 같은 사용자 새 권한, 정상 동일 권한 replay, 인증·CSRF·잠금·롤백 회귀를 포함한다.

독립 HTTP 재현에서는 A의 미확정 요청을 B가 재확인해도 추가 POST·검수 감사 기록이 생기지 않았고 원 요청·scope·이탈 경고가 유지됐다. A로 복귀해 CSRF를 갱신하면 같은 요청이 1회 처리되고 경고가 해제됐다. 재확인에서 409가 발생할 때에도 원래 미확정 상태를 보존하면서 최신 상세를 다시 조회하도록 보완했다. 증거는 작업 루트의 `out/admin-pr92-review-evidence-20261120/fixed_scope_review.cjs` 및 `fixed-scope-review-output.log`에 있다.

첫 빌드는 샌드박스의 `.next/types` 폴더 생성 권한 오류로 중단됐다. 동일 제품 코드를 권한이 허용된 실행으로 재검증해 빌드 종료 코드 0을 확인했다. 최초 실패 로그는 `validation/fixed-build-sandbox.log`에 보존했다. 패키지·잠금 파일·마이그레이션·활성화 설정은 변경하지 않았다.

최종 독립 코드 리뷰에서 추가 수정이 필요한 결함은 발견되지 않았다. 수정은 이 로컬 브랜치에 미커밋 상태로 남아 있으며, 실제 서버 배포·관리자 권한 부여·서비스 콘텐츠 승인/반려는 수행하지 않았다.

## 실제 Checking 사용까지 남은 단계

1. Main의 관리자 탈퇴 보호 패치를 검토·반영한다. Main과 Checking은 DB를 공유한다.
2. 이번 FE·BE 계약 변경을 함께 검토하고 Checking에 반영한다. 기존 BE에 scope 없는 GET을 받으면 FE는 검수 실행을 허용하지 않아야 한다.
3. 실제 사용할 기존 계정, 역할별 권한, 전용 콘텐츠·초안과 정리 계획을 정한다.
4. 실제 로그인·쿠키·CSRF·역할별 GET부터 확인한 뒤 전용 데이터로 승인·반려·감사 기록·동일 요청 재확인을 검증한다.
5. 위 결과를 확인한 후 별도 코드 변경으로 쓰기를 활성화한다.

11월 19일 문서의 미배포·미마이그레이션 항목은 당시 기록이다. 11월 20일 앞선 읽기 전용 점검에서는 Checking BE `ab7aa22`, migration `47c1a8d6b302`, 관리자 grant 0건을 확인했다. 이번 로컬 수정은 아직 해당 서버에 배포되지 않았다.
