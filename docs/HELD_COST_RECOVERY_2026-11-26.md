# 봉인된 보류 결과의 미확정 비용을 보존하는 복구

기준: `main`의 `1eaa3aecef73381a6f3c489405d9416d935a000e`.
이번 범위는 제품 복구 기능과 격리 회귀 테스트다. 운영 작업 DB·체크포인트·산출물·
공개 콘텐츠·추천 데이터는 수정하지 않으며, 실제 복구 적용·유료 생성·자동 수집 재개·
커밋·푸시·배포는 수행하지 않는다.

## 목적과 보존 규칙

기간을 확정할 수 없어 정상 보류된 결과가 이미 봉인되어 있으나 사용량 증거가 누락된 경우,
원래 결과를 고치거나 같은 기사를 재생성하지 않고 그 작업을 정리할 수 있게 한다.
기존 결과 파일 없는 실패 복구와 구분해 검증하고, 처리 후에도 명시적인 정지 상태를 유지한다.

- DB 작업·시도는 `succeeded / held`, producer 결과는 `expiry_unresolved_held`로 유지한다.
- 입력·정규화 URL·작품 ID·시도 ID·시작/종료 시각·결과 SHA·봉인 manifest·표지 이력은 변경하지 않는다.
- 비용은 `accounting_method=unknown`, `estimated_cost_usd=null`, 전체 비용 미확정으로 남긴다.
  확인된 부분 사용량만 알려진 소계에 더하며 0원 확정이나 과거 다른 작업의 예약금으로 대체하지 않는다.
- 원래 시도의 `counts_slot=true`를 보존한다. 하루 40회 한도를 초기화하지 않으며,
  held 결과를 검수 통과 20건이나 내보내기 대상으로 올리지 않는다.
- 과거 실패 복구 영수증·재개 기록·알려진 비용·예약금·검수/적재 선택 이력을 보존한다.
- 복구는 체크포인트의 해당 행을 처리 완료로 기록할 뿐이다. 상태는
  `stopped / failure_reconciled_paused`이며, 다음 기사 실행에는 별도의 명시적 재개가 필요하다.

## 검증 계약과 하위 호환

기존 `menu_worker.failure_recovery`의 plan/apply 인터페이스와 영수증 schema 1을 유지한다.
작업 종류는 operation으로 엄격히 구분한다.

| operation | 원래 DB/결과 | 처리 |
| --- | --- | --- |
| `reconcile_failed_generation_unknown_cost` | 기존 `needs_attention` 실패 | 기존 검증과 영수증을 계속 지원 |
| `reconcile_held_generation_unknown_cost` | `succeeded / held / expiry_unresolved_held` | 정상 종료·봉인·입력·시도와 비용 미확정을 별도로 검증 |

기존 `failure_recovery_receipt`, 감사 목록, 일시 정지 사유의 이름은 호환을 위해 유지한다.
이름이 같아도 실제 작업 상태를 실패로 바꾸지는 않는다. 영수증 operation·원본 백업·DB 행·
결과 봉인을 재검증하므로 두 종류를 서로 바꾸거나 임의 작업에 재사용할 수 없다.

총비용을 정상 확인할 수 있는 결과(명시적 0회 포함), 검수 통과/다른 producer 상태, 정상 종료가 확인되지 않은 결과,
누락/변조된 봉인, 다른 입력/시도, 실행 중 작업, 비용 형식 오류·모순은 복구 대상으로 인정하지 않는다.
횟수 제한 일일 정책에서만 허용하며, 미확정 비용을 가진 상태로 비용 한도 모드를 우회할 수 없다.

## 계획·적용·재개는 분리

아래는 운영 실행용 자리표시자 예시다. 이번 작업에서는 운영에 실행하지 않는다.

1. 생성 Worker/Controller/적재기·타이머가 정지했고 브로커가 비었는지 확인한다.
2. 작업 DB·원본 결과·상태 파일을 백업하고 원본 체크포인트 바이트 SHA를 확보한다.
3. 읽기 전용 계획을 만든다.

```text
python -m menu_worker.failure_recovery plan
  --checkpoint <원래 일일 체크포인트 절대 경로>
  --expected-sha256 <원본 바이트 SHA256>
  --artifact-root <원래 산출물 루트>
  --job-id <원래 보류 작업 ID>
  --reason <원본 보류 상태와 미확정 비용을 보존하는 운영 사유>
```

출력 plan의 operation·원본 작업/시도·봉인 해시·부분 비용·원래 기록·일일 정책을 확인하고
`plan` 객체와 `plan_sha256`을 별도 보관한다. 계획만으로 파일/DB/큐를 변경하지 않는다.

4. 별도 적용 승인을 받은 뒤 정확한 계획 해시로 복구한다.

```text
python -m menu_worker.failure_recovery apply
  --plan-file <검토한 plan 객체 JSON>
  --expected-plan-sha256 <검토한 plan_sha256>
```

기존 Controller 잠금·생성 이력 잠금·DB 쓰기 차단 잠금 아래 원본이 그대로인지 확인한다.
원본 체크포인트·전체 작업 DB 스냅샷·영수증을 0700/0600으로 먼저 보존하고 체크포인트만
원자 교체한다. 같은 계획 반복 적용과 중간 중단 후 재시도는 이력을 추가로 늘리지 않는다.
원본이 달라졌다면 중단한다. DB 행과 Agent 파일을 고쳐 통과시키지 않는다.

5. 호스트 스케줄러의 기존 `--reconcile`로 영수증을 연결해도 `reconciled_paused`를 유지한다.
   이후 **별도 재개 승인**과 정확한 영수증 SHA가 있을 때만 `--resume-reconciled` /
   Controller `--apply --resume-failure-recovery`로 다음 기사부터 진행한다.

기존 생성 시작 이력과 source+canonical URL 중복 방지는 계속 적용된다. 원래 보류 기사를
다시 발견하거나 다른 요청 키/유형으로 제출해도 새 생성이 허용되지 않는다. 날짜가 지나면
그날 새 생성은 하지 않고 기존 횟수·영수증·미확정 비용을 다음 날 이력에 보존한다.

## 검증 결과

최종 고유 테스트 **459건 통과**, 실패·오류·건너뜀은 모두 0건이다.

| 범위 | 통과 |
| --- | ---: |
| Worker 복구·일일 횟수·배분·비용·재개 회귀 | 150 |
| 실제 격리 PostgreSQL 복구·표지 이력·일자 이월 | 34 |
| Linux 호스트 스케줄러·릴리스 연결 이관·파일 권한 | 42 |
| 추천 피드·콘텐츠 적재·승인 전 비노출 회귀 | 233 |

신규 회귀는 보류 복구 단위 17건, 기존 실패+보류 혼합 Controller 6건,
실제 PostgreSQL 11건, 호스트 연동 3건으로 37건이다. 기존 실패 영수증의 하위 호환 회귀도 통과했다.
실행 중 소스 해시가 그대로였음을 확인했고 `git diff --check`도 통과했다.

실제 PostgreSQL 검증은 별도 tmpfs DB·내부 전용 네트워크·공개 포트 0개로 실행했다.
운영 데이터를 가져오지 않고 가짜 자료로 작업 8건/시도 8건, 당일 시도 4회/통과 1건과
기존 실패 복구 영수증·알려진 비용·예약금을 재현했다. 검증 중 재개는 **가짜 생성기와 테스트 DB에서만**
명시적으로 수행했으며, 운영 재개·실제 LLM 호출이 아니다.

- 같은 계획 반복 적용과 체크포인트 교체 전/후 중단에서 원본과 영수증이 보존됐다.
- 원래 보류 작업/시도/봉인 파일/기존 실패 영수증이 그대로이고, 검수·내보내기는 거절됐다.
- 같은 URL의 다른 요청 키/유형·URL 표기 변형도 기존 생성 시작 이력 때문에 재생성할 수 없었다.
- 가짜 생성기로 다른 기사 36건만 더 처리해 당일 총 40회·통과 1건에서 멈췄다.
  완료 후 다시 실행해도 횟수·파일·비용 이력은 늘어나지 않았다.
- Controller 검증에서는 기존 실패·보류를 포함해 23회 시도에서 검수 통과 20건을 채우고 멈췄다.
- 날짜가 지난 재개는 새 작업 없이 마감하고, 다음 날에는 두 미확정 비용과 기존 원본 이력을 이월했다.
- 자동 재개·이전 영수증으로 새 보류 해제·비용 한도 모드 우회·변조된 봉인/DB/백업은 거절됐다.

신규 PostgreSQL 테스트의 기존 성공 1건 전달은 과거 fixture의 수동 자료를 처리하는 한정 stub이다.
보류 작업의 내보내기 거절은 실제 export 함수로 확인했으며, 새로운 36건은 실제
JobStore submit/claim/generation-start/complete와 PostgreSQL 행을 사용했다.

테스트 컨테이너·임시 DB·내부 네트워크를 제거했고 기존 로컬 컨테이너는 그대로다.
기타 회귀는 네트워크 없는 읽기 전용 소스 컨테이너와 임시 파일/메모리 DB에서 실행했다.
모든 실행에서 실제 LLM 호출 0회, 운영 서버 접근 0회, 서비스 DB 접근/쓰기 0회다.
공개 콘텐츠·추천 코드와 정책, Agent 생성 코드는 변경하지 않았다.

제품 실행 로직 변경은 `worker/menu_worker/failure_recovery.py`에 한정된다.
`bounded_resume.py`는 기존 실패 전용 주석을 보류까지 포함하도록 정정했다.
`daily_resume.py`와 호스트 `scheduled_run.py`의 실행 로직은 기존 계약 그대로 호환됐다.
DB 스키마 변경이나 운영 마이그레이션은 없다.

검증 로그는 저장소 밖 `out/held-cost-recovery-validation-20261126/`에 보관한다.

- `worker-20261126T070403Z.summary.json` 및 `.log`
- `postgres-20261126T070103Z.summary.json` 및 `.log`
- `schedule-20261126T070438Z.summary.json` 및 `.log`
- `feed-20261126T064942Z.summary.json` 및 `.log`

개발 중에는 신규 PG 테스트에서 기존 성공 콘텐츠의 전달 번들이 빠져 한 번 실패했다.
해당 fixture만 보완해 최종 34건을 모두 통과했다. 첫 PG 실행의 전체 컨테이너 비교는
병렬 임시 테스트 컨테이너의 정상 종료와 겹쳐 완료되지 않아, 최종 PG 검증을 단독 실행하고
전체 컨테이너 동일성과 cleanup을 다시 확인했다. 또한 호스트 권한 테스트 컨테이너에서
소유자 변경 후 chmod에 필요한 `FOWNER` capability가 빠져 한 건 실패했으며,
임시 테스트 컨테이너 권한만 보완한 뒤 전체 42건을 통과했다. 이 과정에서 제품의 보호 조건이나
운영 설정을 완화하지 않았고, 초기 실패 로그도 보존했다.

운영에서 이전에 준비한 원본 증거는 [복구 준비 문서](HELD_COST_RECOVERY_PREPARATION_2026-11-26.md)에
기록돼 있다. 이 문서의 구현과 테스트는 그 원본에 적용했다는 뜻이 아니다.
