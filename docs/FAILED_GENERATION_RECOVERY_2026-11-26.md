# 실패 작업과 미확정 비용을 보존하는 복구 절차

## 이번 작업의 범위

`main`의 `9c97f406965808b01bb64bd3d45e6818c24746a1`에서 분리한 작업 트리에서 구현했다.
기존 Agent 종료 기록 보완은 [별도 문서](AGENT_FAILURE_EVIDENCE_2026-11-26.md)를 따른다.
이번에는 복구 절차와 회귀 테스트만 구현했다. 운영 체크포인트·작업 DB·서비스 DB·워커·타이머는
변경하지 않았으며 배포와 실제 유료 생성 재개도 실행하지 않았다.

## 보존하는 것

- 원래 실패 작업은 `needs_attention`이다. 작업·시도 ID, 시작·종료 시각, 오류, DB 행과
  시도 이력, 원래 산출물을 수정하거나 삭제하지 않는다.
- 같은 출처·정규화 URL의 생성 시작 이력과 중복 방지 규칙을 유지한다. 다른 유형이나
  새 요청 키를 사용해도 원래 실패 기사를 다시 생성하지 않는다.
- 실패한 작업의 `counts_slot=true`를 유지하여 그날 40회 시도 중 1회로 계산한다.
  검수 통과 20건 목표에는 포함하지 않는다.
- 비용은 `accounting_method=unknown`, `estimated_cost_usd=null`이다. 확인된 부분 사용량만
  별도 합산하고 전체 비용은 미확정으로 표시한다. 비용 0이나 다른 작업의 기존 $1 예약금으로
  대신 처리하지 않는다. 기존 성공·보류·예약금·검수·적재 기록은 그대로 남는다.
- 다음 날에도 전체 이력과 미확정 비용 참조가 이어진다. 비용 한도로 실행하는 과거 모드에는
  미확정 비용을 이월하여 실행할 수 없다. 이번 복구는 하루 횟수 제한 모드에만 적용된다.

## 복구와 재개는 별도 단계

### 1. 읽기 전용 복구안

수정한 Worker 이미지와 동일한 코드로, 기존 전용 작업 DB와 원래 산출물 경로를 사용한다.
다음 명령은 작업·큐·체크포인트를 쓰지 않는다. 예시는 자리표시자를 사용하며 실행하지 않았다.

```text
python -m menu_worker.failure_recovery plan
  --checkpoint <컨테이너에서 보이는 일일 체크포인트 절대 경로>
  --expected-sha256 <체크포인트 원본 바이트 SHA256>
  --artifact-root <기존 산출물 루트>
  --job-id <원래 실패 작업 ID>
  --reason <미확정 비용과 실패 이력을 보존하는 복구 사유>
```

출력의 `plan` 객체만 별도 JSON 파일에 저장하고 `plan_sha256`을 검토한다.
계획은 원본 체크포인트·실패 작업과 모든 시도·전용 작업 DB 스냅샷·기사의 전체 산출물 목록과
해시를 묶는다. 실행 대기/실행 중인 작업이 있거나 종료 기록이 불명확하면 거부한다.
검수할 수 있는 정상 결과나 이미 봉인된 결과가 있으면 건너뛰는 복구를 허용하지 않는다.

### 2. 명시적인 복구 적용 — 계속 정지

```text
python -m menu_worker.failure_recovery apply
  --plan-file <검토한 plan 객체 JSON 파일>
  --expected-plan-sha256 <검토한 plan_sha256>
```

컨트롤러와 같은 UID 10001로 실행해야 이후 컨트롤러가 보존 파일을 읽을 수 있다.
복구 디렉터리는 0700, 원본 체크포인트·작업 DB 스냅샷·영수증 파일은 0600으로 보존한다.
원본 작업 DB에 쓰지 않는다. 실행 잠금, 생성 이력 잠금, DB 테이블 읽기 잠금 아래에서
변경 여부를 재검사하고, 증거 파일을 먼저 보존한 뒤 체크포인트만 원자적으로 바꾼다.

체크포인트 행의 처리 상태는 `complete`가 되지만, 실제 작업 상태는 계속 `needs_attention`이다.
전체 체크포인트는 `stopped / failure_reconciled_paused`가 되며 재개 권한을 부여하지 않는다.
같은 계획을 반복 적용해도 복구 기록은 한 번만 남는다. 적용 전후 증거가 달라지면 중단한다.

영수증 경로는 `<checkpoint>.failure-recovery/<plan_sha256>.receipt.json`이다.
출력의 `receipt_sha256`은 파일 바이트가 아닌 영수증 JSON의 정규화된 해시이다.

### 3. 스케줄러에 복구 기록 연결 — 계속 정지

기존 `scheduled_run.py` 공통 인자(검토된 정책·정책 해시, 상태 루트, 환경 파일, 릴리스 경로)에
다음 인자만 붙인다.

```text
--reconcile
--recovery-receipt <호스트에서 보이는 동일 영수증 절대 경로>
--reviewed-recovery-sha256 <receipt_sha256>
```

호스트는 컨트롤러 코드로 실패 이력·산출물·체크포인트·빈 브로커를 다시 검증한다.
저널은 `reconciled_paused`이며 기존 차단 사유도 보존한다. 일반 타이머의 `--apply`는
이 상태를 재개하지 않는다. 이 단계에는 Worker 시작, 큐 발행, LLM 호출, 서비스 적재가 없다.

### 4. 향후 별도 승인 후 명시적으로 재개

이번에는 실행하지 않는다. 수정 이미지·호스트 도구 반영 및 별도 재개 확인 후,
동일한 공통 인자와 영수증에 `--resume-reconciled`를 사용한다.
내부 컨트롤러도 `--apply --resume-failure-recovery <receipt_sha256>`를 요구한다.
기존 호스트 저널은 릴리스 SHA·환경 파일·Compose 해시를 고정하므로, 새 이미지 배포 시에도
기존 저널을 지우거나 제한을 초기화하면 안 된다. 운영 반영 단계에서 이력 보존을 확인하는
별도의 설정 이관이 필요하며, 이번에는 기존 정책·환경 파일을 변경하지 않았다.

- 남은 생성 시간에는 원래 기사 대신 다음 기사로 진행한다. 기존 시도·통과 수에서 이어가며
  40회/20건 제한을 초기화하지 않는다.
- 날짜가 지났거나 새 작업의 1,500초 처리 여유가 없으면 Worker를 시작하지 않고 그날을 마감한다.
  이미 검수 통과한 결과만 원래 날짜·정책·번들 해시에 묶어 검수 대기로 적재한다.
- 지난 날짜의 적재는 명시적인 `--once --apply --reconcile-policy-date <원래 날짜>`와 검토한
  정책 해시를 요구한다. 원래 정책 날짜·최대 20건·대상 DB·중복 방지·검수 대기 상태를 유지한다.
  원래 날짜를 오늘로 바꾸거나 기존 콘텐츠를 공개/승인하지 않는다.
- 적재가 확인되어 그날 저널이 완료된 뒤에만 다음 날 계획으로 넘어갈 수 있다.
- 재개 중 중단되면 일반 타이머가 임의로 이어가지 못한다. 동일 영수증으로 명시적인 재개를
  다시 요청한다. 새 실패가 생기면 그 작업에 대한 새 복구안·영수증이 필요하다.

## 검증 범위

네트워크 없는 컨테이너와 외부 연결·호스트 포트·실제 API 키가 없는 임시 PostgreSQL에서 검증한다.
실제 제공자 호출은 없고, 생성 결과는 가짜 Agent/합성 결과로 대체한다.

- 복구안의 읽기 전용 동작, 변경된 계획·체크포인트·DB·산출물 거부, 잠금 충돌, 반복 적용,
  적용 도중 중단 후 복구, 원본 실패 이력·부분 비용·미확정 총액 보존.
- 정리만으로 재개되지 않음, 잘못된 영수증과 새 실패 차단, 같은 기사 재생성 차단,
  다음 기사 순차 진행, 실패 포함 하루 40회 및 통과 20건 제한 유지.
- 날짜 경계에서 새 생성 차단, 다음 날 원래 작업/비용 이력 보존, 비용 제한 모드 우회 차단.
- 지난 날짜의 적재를 명시적인 단건 복구로만 허용, 중복 적재 방지, 승인 전 비노출,
  기존 추천 피드·검수·콘텐츠 적재 회귀.

서비스 DB 변경이나 자동 생성 재개는 이 검증에 포함하지 않는다.

최종 결과는 고유 테스트 **427건 통과, 선택적 외부 Celery 인계 1건 생략**이다.

- Worker 복구·컨트롤러·횟수·비용 회귀 101건: 전체 100건 통과 후, 원본 바이트 검증 1건을
  추가한 최종 핵심/컨트롤러 22건 재실행까지 통과했다.
- 실제 격리 PostgreSQL 작업 이력·중복·표지 이력·날짜 이월 26건 통과(신규 복구 9건 포함).
- 호스트 스케줄러 27건 통과.
- 백엔드 적재·검수·공개 제어·추천 피드 273건 통과, 선택적 외부 인계 1건 생략.

초기 새 합성 테스트에서 작품/출처 메타데이터와 정상 수집 대기 동작을 충분히 재현하지 못한
부분을 fixture에서 보완하고 다시 통과시켰다. 서비스 코드의 보호 조건을 완화하지 않았다.
임시 PostgreSQL 컨테이너와 전용 네트워크는 검증 후 제거했다.

## 운영 반영 전 릴리스 연결 이관

새 이미지를 비활성으로 배포한 후, 위 복구 적용 전에 새 릴리스의
`deploy/daily-generation/release_migration.py`로 기존 저널 연결을 이관한다.
타이머는 비활성·중지, 스케줄 서비스는 중지, 생성 Worker·컨트롤러·적재기는 실행 중이
아닌 상태여야 한다. 이 도구는 상태를 조회해 확인할 뿐 서비스 중지나 재개를 수행하지 않는다.

새 정책은 기존 정책에서 `release_sha`만 바꾼다. 새 비공개 기본 환경 파일은 기존 파일의
`DAILY_RELEASE_TAG='...'` 한 줄만 변경한다. 출처·작품·40회/20건 제한·대상 DB·원본 이력·
키와 DB 자격 증명은 그대로 유지한다. 이번 코드 배포에서는 두 Compose 파일도 이전 릴리스와
바이트가 같아야 한다. 다른 설정 변경을 함께 이관하려 하면 거부한다.

```text
python3 <새 릴리스>/release_migration.py
  --old-policy <기존 정책> --old-policy-sha256 <기존 정책 해시>
  --old-runtime-env <기존 비공개 기본 환경 파일> --old-release-dir <기존 릴리스>
  --new-policy <새 정책> --new-policy-sha256 <새 정책 해시>
  --new-runtime-env <새 비공개 기본 환경 파일> --new-release-dir <새 릴리스>
  --state-root <기존 상태 루트>
  --backup-dir <상태 루트 밖의 새 비공개 백업 디렉터리>
```

기본 명령은 로컬 파일만 읽으며 `plan`과 정규화된 `plan_sha256`을 출력한다. `plan` 객체를
별도 비공개 파일로 저장하고, 같은 인자에 다음을 추가해 서버 root 권한으로 적용한다.

```text
--apply --plan-file <검토한 plan 객체 파일> --reviewed-plan-sha256 <plan_sha256>
```

원래 저널·미완료 날짜의 두 환경 파일·기본 환경 파일과 계획을 0700/0600 백업에 먼저
보존한다. 변경 가능한 파일은 해당 날짜의 `planning.env`, `runtime.env`, 저널 세 개뿐이다.
저널은 릴리스 연결 정보와 이관 감사 기록만 갱신하며 `blocked` 또는 `reconciled_paused` 상태와
모든 날짜 이력을 유지한다. 체크포인트·일일 계획·적재 정책·번들·기존 영수증은 바이트 해시를
대조한다. 저널을 마지막에 교체하므로 중간 중단 시 같은 계획과 백업으로 다시 적용할 수 있다.
생성·적재·서비스 DB 쓰기나 제한 초기화는 없다.

`/etc/me-nu-daily-schedule.env`의 릴리스·정책·정책 해시·기본 환경 경로는 이 도구가
수정하지 않는다. 운영 반영 담당자가 원본 바이트와 백업을 확인하고, 예상 원본 해시가
일치할 때만 새 경로·해시로 별도 원자 교체한다. 상태 루트는 유지한다. 타이머를 비활성으로
둔 채 새 연결의 상태 조회를 확인한 다음 위 복구 적용과 `--reconcile`까지만 진행한다.
이번 승인에는 `--resume-reconciled`, 타이머 활성화, Worker 시작이 포함되지 않는다.

추가 이관 회귀 **12건**을 네트워크 없는 Linux 컨테이너에서 통과했다. 조회 전용 계획,
세 파일만 변경, 전체 이력 보존, 반복 적용, 중간 교체 후 복구, 원본/백업 변조·잠금·실행 중
서비스 차단, 출처·자격 증명·Compose 변경 거부를 포함한다. OS 조회 명령도 테스트에서는
가짜 실행기로 대체했으며 실제 서버 이관이나 서비스 명령은 실행하지 않았다.
