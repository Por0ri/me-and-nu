# RAG 생성 전 실패 예약 복구 · 2026-11-27

## 문제와 처리 범위

A07은 정상 발췌문을 ID 순서로 읽으면서 원문 변조로 오인한 Agent 문제였고, PR #145에 발췌 순서·기존 인용 보존 수정이 반영됐다. A08은 이 실패가 생성 시작 전에 발생해 비용이 0으로 확정됐는데도 일일 예약이 `reserved`에 남아 전체 스케줄이 멈추는 별도 문제다.

이번 변경은 A08의 정확히 확인된 실패만 마감한다. 작업 DB의 실패 job·attempt, 요청·예약 ID, 비용 기록, 이미 사용한 일일 시도와 중복 방지 이력은 바꾸지 않는다. 실패한 같은 기사를 다시 생성하거나 검수·공개 기준을 완화하지 않는다.

## 자동 마감 조건

다음 조건을 모두 만족해야 한다.

- 동일 요청·입력 해시·예약·작품·출처·유형, 해당 기록 당시 일일 정책과 할당 순번이 일치한다.
- 시도는 한 번이며 job·attempt 모두 `failed`, 오류는 `rag_preflight_failed`다.
- 두 기록의 생성 시작 시각이 NULL이고 종료 시각과 해제된 claim이 확인된다.
- 두 기록 모두 `cost_complete=true`, `usage_records=[]`다.
- 결과·산출물·생성 시작·적재 흔적이 없고 checkpoint에 비용 불명확 또는 상충하는 사용량 증거가 없다.

이 경우 예약만 `complete`로 바꾸고 실패 상태와 비용 `0.00000000`, 원래 DB 기록의 해시를 저장한다. 다음 후보로 진행할 수 있지만 같은 실패 작업은 재발행하지 않는다. 성공 건수는 증가하지 않고, 실패도 하루 40회 시도에 포함된다. 생성 시작 여부나 비용이 불명확하면 기존처럼 보류한다.

## 이미 멈춘 예약의 운영 복구

`python -m menu_worker.rag_preflight_recovery`는 기본적인 생성 실행기가 아닌 별도 복구 도구다.

1. 자동 생성 타이머와 소비자를 정지하고 작업 DB에 대기·실행 작업이 없고 큐가 비었는지 확인한다.
2. `plan --checkpoint ... --expected-sha256 ... --artifact-root ... --job-id ... --reason ...`으로 읽기 전용 계획을 만든다.
3. 계획·대상·해시를 확인한 뒤 `apply --plan-file ... --expected-plan-sha256 ...`을 명시한다.
4. 파일·DB·생성 이력 잠금 아래 전체 작업 DB 스냅샷과 checkpoint의 변경 여부를 다시 확인한다. 원본 checkpoint·DB 스냅샷·복구 영수증을 변경 불가 파일로 보관하고 대상 예약만 마감한다.
5. checkpoint는 `stopped / failure_reconciled_paused`에 남는다. 호스트 스케줄러의 기존 `--reconcile` 절차로 영수증을 확인하고 journal도 `reconciled_paused`로 기록한다.

복구는 생성 재개 승인이 아니다. 별도 `--resume-reconciled` 승인 전에는 타이머와 Worker를 켜지 않는다. 다음 날 이월에서도 실패 증거와 영수증을 다시 확인하며, 이전 미확정 비용은 0으로 바꾸지 않는다.

## 검증과 배포 원칙

- 실제 LLM 호출 없이 단위 및 격리 PostgreSQL 회귀로 확인한다.
- 원래 실패 행·시도·비용 보존, 동일 계획 재실행, stale 계획·변조된 영수증 거부, 시작/비용 불명확 차단, 다음 후보 처리와 다음 날 이월을 검증한다.
- 하루 최대 40회 시도·검수 통과 20건, 운영자 승인 후 공개를 유지한다.
- 새 Worker/controller/RAG 이미지만 배포한다. 기존 importer·벡터 DB·추천 이미지와 공개 API·콘텐츠는 유지한다.
- 실제 사고 문서는 정지된 Worker의 읽기 전용 볼륨과 새 RAG 이미지로 `_preflight`만 검사한다. 네트워크·provider import·키 읽기·파일 쓰기를 차단하며 산출물을 생성하지 않는다.
- 운영 백업·이미지 해시·복구 계획/영수증·배포 결과는 별도 배포 기록에 보관한다.

검증 환경을 구성하는 과정에서 최소 Worker 이미지에는 Pillow와 전체 출처 카탈로그가 없어 전체 회귀를 실행할 수 없었다. 필요한 의존성과 저장소 구조가 있는 이미지로 검증 환경을 바로잡았다. 또한 신규 다음 날 테스트의 필수 RAG 범위·런타임 해시·inbox 입력 누락을 보완했으며, 운영 검증 조건은 완화하지 않았다.

최종 확인 결과:

- 전체 Worker 회귀 489개 실행: 352개 통과, 별도 환경이 필요한 137개 제외, 실패 0개.
- 신규 A08 실제 PostgreSQL 12개와 기존 RAG·실패·보류·스키마 호환 회귀 43개: 고유 55개 모두 통과.
- 엄격한 실패 검증 단위 테스트 7개와 47개 subtest 통과. 생성 전 실패만 반복돼도 시도 40회에서 멈추고 성공 건수는 0으로 유지된다.
- 배포 도구의 이미지 범위·환경 변경 범위·동기화·정지된 소비자 교체 회귀 24개 통과.
- 실제 LLM 호출·운영 DB 쓰기 없이 확인했으며, 임시 PostgreSQL은 검증 후 정리했다.
