# Figma 화면 기준 API V1.1 구현 대상 — 알림·활동 화면 포함

기준: 2026-09-29. Figma의 [‘화면 흐름 정리’](https://www.figma.com/design/mF65Z3XbeQvtGl1ngRaSox/%25ED%258C%258C%25EC%259D%25B4%25EB%2584%2590?node-id=1430-47731)와 FE(최신)의 [알림](https://www.figma.com/design/mF65Z3XbeQvtGl1ngRaSox/%25ED%258C%258C%25EC%259D%25B4%25EB%2584%2590?node-id=1659-22109)·[활동](https://www.figma.com/design/mF65Z3XbeQvtGl1ngRaSox/%25ED%258C%258C%25EC%259D%25B4%25EB%2584%2590?node-id=1659-22146) 화면, [Notion API V1.1 명세서](https://app.notion.com/p/94604c45a961835bbd1601fc3ab15ac0), 현재 공개 라우트·FE 호출 함수와 [V1.1 로컬 정합화 결과](API_V1_1_LOCAL_ALIGNMENT.md)를 비교했다. 확인된 화면 기준 백로그이며 모든 변형 프레임과 프로토타입 전환을 전수 검증한 결과는 아니다.

API V1.1에는 API-003을 제외한 번호 API **108개**가 있다. 현재 백엔드에는 번호에 대응하는 공개 V1 라우트 **24개**가 있다(그 밖에 개발용 6개·상태 확인 2개). 직전 정합화 작업은 첨부 로컬 프롬프트에 따라 **기존 공개 라우트 24개만** 대상으로 삼았으므로 Figma 화면 전체의 완료를 뜻하지 않는다. 이 24개에는 FE 호출 함수가 준비됐지만 실제 제품 화면은 홈·Topic/Subtopic 피드와 글 상세 중심이고, 다른 조작은 개발용 API 점검 화면에 남아 있다. 아래는 **확인한 화면을 완성할 때 연결할 API와 데이터 결정 사항**이다. `구현`은 경로와 로컬 동작이 있다는 뜻이며 모든 V1.1 기능이 제공된다는 뜻은 아니다. 경로는 모두 `/api/v1`로 시작하고 끝 `/`를 붙이지 않는다.

## 2. 알림·활동 화면 구현 대상

| 작업 | 구현 범위 | 완료 기준·남은 계약 |
| --- | --- | --- |
| **알림 목록 — 화면 필수** | API-107 목록, 수신자별 알림 저장소와 커서 조회, FE 호출 함수·알림 페이지를 만든다. | Figma의 오늘·어제·최근 7일·최근 30일 묶음은 `createdAt`으로 화면에서 계산할 수 있다. 새 글 카드의 `contentId`로 API-029 상세에 연결할 수 있지만 카드 탭 동작은 Figma에서 확인되지 않았다. |
| **미읽음·읽음 — 명세 동작** | API-108 전체 미읽음 수와 API-109 단건 읽음을 구현하고, 배지·읽음 UI가 확정되면 화면에 연결한다. | 최신 프레임에는 미읽음 배지·읽음별 카드 차이가 보이지 않는다. 109는 CSRF가 필요한 변경 요청이고 재호출해도 최초 `readAt`을 유지한다. DM 미읽음은 108에 포함되지 않는다. |
| **새 글·공지 알림 생산** | 팔로우한 채널의 새 공개 글과 운영 공지에 대해 수신자별 알림을 생성한다. 동일 발행 이벤트의 재처리로 중복 생성되지 않도록 한다. | 채널·팔로워 관계와 공개 발행 이벤트가 필요하다. 현재 `Content.creator_channel_id`는 nullable이고 Agent 발행은 이를 채우거나 알림을 만들지 않는다. Agent 글을 구독자에게 알리려면 발행 주체/채널을 연결해야 한다. 공지 작성·배포 경로도 정해야 한다. |
| **카드 표시 계약** | 새 글 작성 주체와 썸네일·이동 대상을 표시할 필드 또는 안정적인 조회 경로를 정한다. | API-107은 `creator_new_post`·`system_notice`만 주고 채널 ID·이름·이미지, 카드 썸네일은 없다. 화면의 우측 썸네일을 API-029 추가 조회로 채울지 107을 보강할지 결정한다. 탭별 필터와 개수가 필요해지면 계약을 확장한다. |
| **DM 답변 알림·활동 탭** | 알림 탭의 DM 답변과 활동 탭의 팔로우 시작·메시지 도착 이벤트를 위한 생성·저장·목록 계약을 새로 정의하거나 107을 확장한다. | API-014는 본인 열람·반응·관심 기록이고, 107에는 DM·팔로우 이벤트 타입이 없다. 팔로우의 행위 주체, 상대방 표시값, 대화 ID, 시각, 읽음·배지 범위를 확정한다. [Figma 범위 메모](https://www.figma.com/design/mF65Z3XbeQvtGl1ngRaSox/%25ED%258C%258C%25EC%259D%25B4%25EB%2584%2590?node-id=1380-18554)는 DM 답변 **알림**을 요구하고 DM **대화 화면**만 후속으로 둔다. 실제 DM 답변 이벤트 공급은 DM 송수신 기능에 의존한다. |
| **알림 설정** | API-068 조회·069 변경과 FE 토글을 연결한다. | DB의 기본 설정 행은 있지만 공개 라우트는 없다. 명세는 알림 종류별 허용만 정의하므로 Figma의 ‘21시 이후 알림허용’은 시간대·적용 대상·저장 필드를 정한 뒤 확장한다. |

현재 코드에는 [NotificationSetting 기본 모델](../backend/app/models/v1.py)만 있다. 알림함·읽음 상태·팔로우 관계의 저장 모델, API-068·069·107~109 라우트, FE 호출 함수와 알림 페이지는 아직 없다. `Content.creator_channel_id`는 nullable이고 [현재 Agent 발행](../backend/app/services/movie_agent_publication.py)은 글에 채널 ID를 연결하지 않는다. 로컬 검증은 **채널 팔로우 → 공개 글 발행 → 수신자에게 알림 1건 생성 → API-107 목록 확인**을 기본으로 한다. 동일 발행 이벤트를 다시 처리해도 알림이 중복되지 않아야 한다. 배지·읽음·카드 이동 UI가 확정되면 **API-108 확인 → API-109 읽음 → API-029 상세 이동** 흐름을 추가한다. 브라우저 푸시를 제공할 계획이라면 푸시 구독·전송 계약을 별도로 정의한다.

## 3. 구현 전에 결정할 계약 차이

1. **온보딩 선택 수와 데이터:** Figma는 세부 토픽 **5개 이상**, [V1.1 API-004](https://app.notion.com/p/2cc04c45a96182428cb881a3ba0bc94f)는 소비자 **1개 이상**을 허용한다. 현 [영화 seed](../backend/app/seeds/movie_catalog.py)는 두 개만 만든다. UI 규칙과 서버 검증 중 어느 쪽을 기준으로 할지 정하고, 최소 5개를 유지한다면 Topic 데이터부터 늘려야 한다.
2. **홈 AI의 의미:** [Home_AI](https://www.figma.com/design/mF65Z3XbeQvtGl1ngRaSox/%25ED%258C%258C%25EC%259D%25B4%25EB%2584%2590?node-id=1430-49127)는 “보고 싶은 글 유형”을 요청한다. [V1.1 대화 API-048·052·053](https://app.notion.com/p/bf304c45a9618212b00581db06837b86)는 AI **질문·답변**을 제공하지만 요청을 취향으로 저장하거나 [피드 API-028](https://app.notion.com/p/30304c45a96182bda8aa014fc6401b6e)을 재정렬·생성하는 계약은 없다. 일반 AI 답변 화면으로 둘지, 콘텐츠 요청 API와 결과 상태를 새로 정의할지 결정한다. 이 화면을 Content_AI와 같은 동작으로 가정하면 안 된다.
3. **구독 대상과 채널 공급:** [API-045~047](https://app.notion.com/p/4f504c45a961829ea9cb01accbede1b4)은 채널 중심인데 Figma는 사람 목록이다. 047은 `totalCount`와 사람 프로필을 주지 않는다. 사람/채널 중 화면 대상을 확정하고 활성 채널·`channelId` 공급, API-056 정보, 목록 필드·총 개수·DM 수신자를 함께 정한다. 채널 모델은 있지만 현재 로컬 seed가 구독 가능한 채널을 제공하지 않는다.
4. **페이지 이동과 저장함 카드:** [API-028](https://app.notion.com/p/30304c45a96182bda8aa014fc6401b6e)은 `cursor/nextCursor`만 제공한다. Figma의 **1–5 번호 페이지**에서 전체 페이지 수 또는 임의 번호 이동을 구현하려면 계약을 바꾸거나 UI를 순차 더보기로 바꿔야 한다. [API-041](https://app.notion.com/p/04604c45a96183ac829001f4338afa6a)에는 Save 카드의 썸네일·By me:nu·상대 시간 정보가 없다. API-102도 `imageUrl`·`createdAt`은 있지만 byline이 없으며 `createdAt`을 저장 시각으로 표시할지 정해야 한다. 원본이 없어도 Save 카드가 남을 수 있는지와 표시 규칙도 정한다.
5. **V1.1 평면 Subtopic은 해결됨:** [Subtopic 라우트](../backend/app/api/v1/subtopics/router.py)와 응답 스키마·FE 호출 타입에서 공개 `parentSubtopicId`를 제거했다. 남은 문제는 Figma **5개 이상** 대 API-004 **1개 이상**의 선택 수와 영화 seed 두 개, 애니·음악 데이터다.
6. **마이페이지와 알림:** [API-068·069](https://app.notion.com/p/6f004c45a96183dca53d816be7cc4bdd)에는 Figma의 “21시 이후 알림허용” 필드가 없다. 실제 알림 탭이 확인됐지만 API-107~109는 새 글·시스템 알림의 조회·전체 미읽음 수·단건 읽음에만 대응한다. 새 글 알림 생산과 채널 관계, 채널 표시 정보가 필요하다. Figma 메모가 요구하는 DM 답변 알림, 활동 탭의 팔로우 시작·메시지 도착은 API-014나 107~109로 표현할 수 없어 이벤트 계약을 새로 정해야 한다. [API-070](https://app.notion.com/p/ec904c45a96183bea39a019d0e7d210b)은 콘텐츠·DM 신고이고 일반 문의는 받지 않는다. [API-011](https://app.notion.com/p/b5d04c45a96182a7aa450124b4ce4610)은 동의 문구를 제공하지만 FAQ·전체 법적 문서 조회 경로는 따로 없다. 자료의 출처를 정한다.
7. **크리에이터 시작 분기:** Figma의 역할 선택은 API-004 `accountType=creator`로 저장할 수 있지만, V1.1에는 크리에이터가 새 공개 글이나 채널을 만드는 API가 없다. 이번에 확인한 프레임도 시작 선택 이후의 제작 절차를 확정해 주지는 않는다. 실제 매거진 생성 화면을 만들기 전에 제작 주체와 API 범위를 정한다.
8. **활동의 수집과 조회:** API-033은 피드 노출·글 열람을 **기록**해 추천 학습과 `seen` 상태의 근거를 만드는 경로다. API-014는 본인의 열람·반응·관심·기억 기록 조회다. FE(최신) 활동 탭의 팔로우 시작·메시지 도착을 이 둘로 제공할 수 없으므로 별도 이벤트 종류·목록·탭 계약이 필요하다.
