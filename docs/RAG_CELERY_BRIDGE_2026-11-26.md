# RAG 사전 기반 생성과 Celery 연결 검증

기준 main은 `73601b8d1a532760997eb78992c2b21ffeebb39a`이며, 별도 작업 브랜치
`codex/rag-generation-bridge-20261126`에서 구현했다. 기존 작업 디렉터리의 수정사항은 건드리지 않았다.
이번 범위는 코드·이미지 빌드·격리 검증이다. 실제 모델 호출, 운영 DB 반영, 운영 Worker/자동 생성 설정 변경은 하지 않았다.

## 구조와 보존 범위

pgvector는 근거 검색 저장소다. 생성기나 추천 계산기를 대체하지 않는다.

| 역할 | 연결 위치 | 이번 변경 |
| --- | --- | --- |
| 원문·이미지·기존 생성 및 검수 이력 | 인계된 RAG SQLite와 이미지 | 원본 보관, 명시한 별도 실행 사본만 새 작업 기록 |
| 벡터 검색 | 전용 PostgreSQL `menu_rag_vector` 계열 DB의 `rag_vector` 스키마 | 생성 시 읽기 전용, 기존 1,024차원 벡터 재사용 |
| 실행·중복·비용 이력 | 전용 `menu_content_jobs` 작업 DB | v8의 RAG 작업/시도 테이블 추가, 기존 v7 작업 보존 |
| 검수 대기 콘텐츠 | 기존 콘텐츠 적재기 | RAG 봉인 결과 전용 입력 어댑터 추가, 승인 전 비노출 |
| 공개 콘텐츠·추천 | 기존 서비스 DB/피드 | 추천 계산·공개 판정 코드 변경 없음 |

PR #111의 pgvector 변경(`71644c7`, `38a1a37`)을 현재 main에 로컬로 적용해 재사용했다.
확인 시 PR #111은 draft/open 상태이며, 이 작업이 PR의 원격 머지를 의미하지 않는다.
초기 이전·WAL·증분 갱신의 상세 조건은 `agent-handoff/RAG_PGVECTOR_VALIDATION_2026-11-24.md`에 있다.

기존 벡터의 모델은 `text-embedding-3-small`, 차원은 1,024이며, 검색 점수는 `1 - cosine distance`를 유지한다.
근거 조각→문서→출처 URL→작품 ID 연결과 기존 필터를 보존한다.
원문/출처/작품과 seed 본문 해시를 생성 전후에 재검증하므로, 검색 중 입력이 바뀐 결과는 정상 결과로 내보내지 않는다.
새 본문에 저장된 벡터가 없는 증분 색인은 임의 유료 임베딩을 하지 않고 중단한다.

## 한 건의 처리 흐름

1. `DictionaryCandidates`가 등록된 출처, 기존 작품, 유형에 맞는 미사용 근거를 읽기 전용으로 찾는다.
2. `MixedDailyController`가 기존 기사 후보와 RAG 후보를 함께 배분한다. 같은 일일 checkpoint의 시도 40회·검수 통과 20건을 사용한다.
3. 슬롯과 입력 해시를 먼저 저장하고 `content.rag_generate`에 작업 ID만 발행한다.
4. RAG Worker가 기존 기사 생성과 같은 DB 잠금을 잡은 뒤 단건 생성·독립 검수만 실행한다. 검수가 요구한 재생성 작업은 자동 실행하지 않는다.
5. 검수 PASS이고 blocker가 없는 결과만 별도 `rag-inbox`로 내보낸다. 기존 기간형 inbox와 섞지 않는다.
6. `rag_pending_import`가 봉인·정책·원문·이미지를 검증하여 기존 적재기로 연결한다. 기본 실행은 DB 연결 없는 dry-run이다.
7. 명시적으로 적재할 때는 `pending_review / needs_review / Draft checking`으로 들어간다. 공개는 기존 운영자 승인 절차를 따른다.

RAG 주제 중복 키는 namespace와 안정적인 work ID다. 날짜·요청 순서·작업 재전달로 새 생성 권한이 생기지 않는다.
이미 생성이 시작됐을 수 있는 작업은 재생성하지 않으며, 원본 입력·시도·검수·비용 기록을 보존한다.
적재도 namespace/work에 묶여 동일 결과는 한 건만 유지하고, 같은 정체성의 다른 결과는 충돌로 차단한다.

날짜는 한국 시간 기준이다. 전날 발행돼 다음 날 도착한 메시지와 자정까지 실행 여유가 부족한 새 작업은 모델 호출 전에 차단한다.
1,500초는 신규 시작을 허용하는 여유 시간이며, 진행 중인 provider 응답이 반드시 자정 전에 끝난다는 보장은 아니다.
자정을 넘긴 기존 작업이 다음 날 새 작업으로 재생성되지는 않는다.

## 사용량과 장애

생성·독립 검수뿐 아니라 검색 질문의 임베딩 호출도 사용량에 포함한다. 기존 근거 벡터 재사용과 새 질문 임베딩은 구분한다.
실제 실행에는 명시한 모델 단가(백만 토큰당 USD의 input/output/cached_input)가 필요하다.
모델 및 `text-embedding-3-small`의 단가 누락·잘못된 값은 사전 검증에서 차단한다.
응답 모델 버전의 단가를 찾을 수 없거나 사용량이 누락되면 0달러로 추정하지 않고 미확정 비용으로 남긴다.

생성 실패·반려·보류·결과 파일 검증 실패도 이미 확인된 사용량을 보존한다. 부분 비용은 알려진 소계로 표시하며 총액은 미확정으로 유지한다.
미확정 RAG 실패를 자동으로 복구 완료 처리하거나 새 날짜로 넘기지 않는다. 별도 근거 확인 없이 같은 주제를 다시 생성하지 않는다.
기존 기사 실패 복구 승인과 비용 이력은 그대로 유지한다.

## 비활성 기본값과 운영 반영 전 준비

- `compose.rag.yaml`은 선택형 `rag-generation` profile이다. Beat 등록, 공개 포트, 자동 재시작은 추가하지 않는다.
- `RAG_GENERATION_ENABLED=false`가 기본값이다. 환경 변수와 명시 runtime 파일 모두 활성화를 허용해야 실행한다.
- 이미지에는 원문 덤프, 이미지 자료, API 키, DB 접속 정보를 넣지 않는다. 실행 사본/이미지/키/벡터 DSN은 별도 경로로 연결한다.
- 벡터 읽기 계정은 전용 DB만 허용해야 한다. 임의 서비스 DB 이름은 어댑터에서 거부한다.
- 작업 DB v8은 운영에 아직 적용하지 않았다. 운영 적용 시 기존 작업 DB 백업, 마이그레이션, Worker 이미지 일치 확인이 필요하다. v7 Worker를 v8 DB에 그대로 붙이는 되돌리기는 피한다.
- RAG 원본을 새 실행 사본으로 준비할 때 문서·이미지·검수 ID를 유지한다. 인계본의 로컬 이미지 경로는 실행 사본 안에서 실제 mount 경로에 맞춰야 한다.
- `daily_resume`의 `--rag-scope`, `--expected-rag-scope-sha256`, `--rag-delivery-root`, `--expected-rag-runtime-sha256`로 명시한 범위를 계획에 묶는다. 기존 period-only 경로는 그대로 둔다.
- 일일 controller와 RAG Worker에서 실행 사본/runtime/artifact 경로가 같은 절대 경로로 보여야 한다. 기존 controller 컨테이너에도 읽기 전용 사전 조회 경로를 연결해야 한다.
- `--preflight`는 원장·봉인·큐 상태를 검증한다. `--apply`는 실제 발행이므로 이번 검증에서 실행하지 않았다.
- RAG 적재 정책에는 대상 DB, 일일 정책 해시, 원문 artifact root, 작품/유형/출처와 `feed_valid_until`을 명시해야 한다. 유효 기간을 임의로 정하지 않는다.

## 확인된 데이터 범위

읽기 전용 인계 사전에서 8개 작품 범위, 후보 45건을 찾았다. 재조회 시 요청 정체성이 같았다.
이는 생성 성공이나 검수 통과 45건을 의미하지 않는다. 이미지 가용성, 근거 충분성, 실제 모델 검수 통과율은 별도 실행에서 확인해야 한다.

## 무과금 검증

모든 DB 테스트는 별도 Docker DB, 외부 포트 0개, 내부 전용 네트워크 또는 network none, 키 없는 환경에서 수행했다.
기존 공개 콘텐츠·회원·추천 DB는 연결하지 않았다. 테스트 자원은 검증 후 정리했다.

서로 겹치는 검증 묶음이 있으므로 표의 수를 단순 합산하지 않는다.
최종 로컬 이미지는 `me-nu-rag-generation:bridge-20261126`, image config SHA는
`25e6c8b21f6a3fbfa9013aa0311a79f4c66a3e9a443237c6c7ef8dc9cefc8164`다. 운영에 배포하지 않았다.

검증 로그는 작업 디렉터리 상위 `out/rag-bridge-vector-validation-20261126`,
`out/rag-bridge-queue-validation-20261126`, `out/rag-service-validation-20261126`,
`out/rag-consumer-validation-20261126`에 있다. 이번 최종 실행의 핵심 결과는 이 문서에 함께 기록했다.

검증 중 새 사용량 테스트 2개의 문자열 표기 비교(`0.03`과 `0.03000000`)를 Decimal 비교로 바로잡았다.
전체 RAG 테스트 첫 시도는 제품 이미지에 pytest가 없어 테스트 모듈 1개를 불러오지 못했다. 테스트 도구가 포함된 별도 검증 이미지로 재실행했다.
Compose 설정 검사는 실제 환경 파일을 읽지 않고 임시 검증용 값을 사용한다.

실제 모델의 검수 통과율과 운영 서버 동시 부하는 이번 무과금 검증으로 확정하지 않는다.
운영 적용과 RAG 유료 실행은 이 검증 결과를 검토한 뒤 별도 단계에서 진행한다.

## 운영 반영 사전 점검에서 보완한 사항

2026-11-26 사용자가 비활성 운영 반영을 승인했다. 운영의 기존 기사 controller/Worker는
`e4cf3e9`, 작업 DB는 v7이었다. 전용 pgvector DB는 아직 없었으며, API/추천 DB와 분리해 준비한다.

실제 배포 소스의 `failure_recovery._snapshot`이 기존 5개 테이블만 허용하는 것을 확인했다.
기존 controller를 실행한 채 RAG 두 테이블부터 추가하면 보존 중인 held 복구 이력 검사에서 중단될 수 있다.
새 코드는 v7/5개 표 또는 v8/7개 표 조합만 허용하며, v8 복구 시 RAG 원장도 snapshot·잠금·idle 검사에 포함한다.
기존 v7 영수증/원본 DB 백업/미확정 비용은 수정하지 않는다. 실제 격리 DB에서 v7 복구 후 v8 전환과
새 controller 검사를 검증했다. 운영에서는 작업을 마친 시점에 백업하고 호환 이미지와 DB를 함께 전환해야 한다.

`deploy/rag-generation`은 운영의 기존 tasks 네트워크와 artifacts bind 경로를 재사용한다.
로컬용 named volume과 섞지 않으며, controller와 consumer는 동일 절대 경로의 별도 RAG inbox를 본다.
RAG Worker는 기본 비활성, API 키/인터넷 연결 없이 준비한다. 전용 vector DB는 내부 네트워크만 사용한다.
