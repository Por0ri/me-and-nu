# me;nu 백엔드 MVP 구현·배포 태스크

- 작성일: 2026-10-10
- 기준 문서: `IMPLEMENTATION_STATUS_2026-10-10.md`
- 기준 코드: 보고서에 기재된 로컬 `main`, `c942cac`
- 목표: 기존 백엔드를 실제 DB와 연결해 검증하고, AWS Lightsail에 내부 검증용 환경을 배포한 뒤 운영·자동 배포 기반을 마련한다.
- 범위: API, 인증·세션, DB, 콘텐츠 적재, LangGraph 에이전트, 챗봇, 배포·운영.
- 제외: 기능 정책 결정, 디자인 변경, 프런트엔드 컴포넌트 구현. 정책이 미확정인 캐러셀·토론장의 신규 API·DB 설계도 이번 작업 범위에서 제외한다.

> 구현 현황 보고서를 바탕으로 만든 작업 계획이다. 이 문서를 작성하면서 원본 저장소의 코드 실행, DB 조회, 테스트, 배포를 수행하지 않았다. 아래 체크박스는 기존 구현 여부가 아니라 **이번 작업의 검증·완료 여부**를 나타낸다. 코드 경로는 보고서에 기재된 원본 저장소 기준이다.

## 1. 현재 상태와 작업 원칙

| 영역 | 보고서상 상태 | 이번 작업의 초점 |
|---|---|---|
| FastAPI | 일반 V1 HTTP 작업 31개, 개발용 6개, 헬스체크 2개 구현 | 사용 경로의 실제 응답·권한·저장 결과 검증 |
| 인증·세션 | HttpOnly 쿠키, PostgreSQL 세션, CSRF 검사 구현 | 배포 도메인에서 세션 유지 및 개발용 인증 분리 |
| DB | PostgreSQL 17·pgvector, SQLAlchemy async, Alembic 구성 | 마이그레이션 재현, 영속 저장, 백업·복구 |
| 관심사·콘텐츠 | 분야·세부 토픽, 피드·상세, 반응·저장 API 구현 | 실제 DB를 사용한 주요 흐름 회귀 검증 |
| 콘텐츠 적재 | 파일 기반 일괄 적재, 중복 처리 구현 | 재실행 시 중복 방지 및 본문·출처 보존 |
| LangGraph | 영화·음악·애니메이션 실행 코드 존재 | MVP에 사용할 경로부터 실행·DB 연결 검증 |
| 영화 에이전트 | 실행·발행 연동 코드 존재, 일부 파일 미커밋 변경 | 변경 검토, 실행 결과 및 중복 처리 확인 |
| 챗봇 | 외부 LLM 호출·작업 조회 구현 | 마지막으로 보고된 크레딧 부족 장애 해소 여부 확인 |
| 벡터 기능 | 확장·컬럼 구조만 구현 | 현재 필수 작업에 포함하지 않음 |

작업 순서는 **기준 코드 정리 → 실행 환경·DB 검증 → API 검증 → 콘텐츠 생성·챗봇 검증 → 수동 배포 → 운영 검증 → CI/CD**로 잡는다. 배포 환경 준비는 정책·디자인 확정을 기다리지 않고 진행할 수 있다.

내부 테스트 배포와 일반 사용자 공개는 구분한다. 개발용 로그인에 의존하는 동안에는 접근이 제한된 내부 환경으로 검증하고, 공개 전에는 실제 사용자 인증 경로와 개발용 API 비활성화를 확인한다.

## 2. 단계별 태스크

### BE-01. 배포 기준 코드와 구현 목록 정리

**목적:** 재현 가능한 코드와 실행 범위를 확보한다.

- [ ] 원본 저장소의 현재 브랜치·커밋과 미커밋 변경 목록을 확인한다.
- [ ] `agent/movie/movie_info_agent.py`, `agent/movie/movie_review_agent.py`의 변경을 검토하고 배포에 포함할 변경을 테스트 후 커밋한다. 기존 작업을 덮어쓰지 않는다.
- [ ] 실행에 필요한 의존성·버전·설치 절차를 확인한다.
- [ ] 실제 등록 라우트와 구현 현황 보고서를 비교한다. 개발용 라우트 활성화 여부도 기록한다.
- [ ] 이번 검증에 필요한 기존 백엔드 테스트와 실행 명령을 정리한다.

**완료 기준:** 배포 대상 커밋이 특정되고, 설치·실행·검증 명령을 같은 코드에서 재현할 수 있다.

**관련 경로:** `backend/app/main.py`, `backend/app/api/v1/router.py`, `agent/README.md`

### BE-02. 환경변수와 DB 초기화 검증

**선행:** BE-01

- [ ] 실제 코드에서 사용하는 환경변수를 조사하고 값 없이 예시 파일을 정리한다. DB 접속, 외부 LLM 키·모델, 허용 Origin, 쿠키, 개발용 API 설정을 포함한다.
- [ ] 비밀값을 저장소·이미지·로그에 포함하지 않고 서버에 주입하는 방식을 정한다.
- [ ] `compose.yaml`을 기준으로 PostgreSQL 17과 pgvector를 실행한다.
- [ ] 비어 있는 테스트 DB에서 Alembic 마이그레이션을 끝까지 실행한다.
- [ ] 기존 DB가 있다면 백업·복제한 테스트 DB에서 업그레이드와 데이터 보존을 확인한다.
- [ ] 분야·세부 토픽 등 기본 데이터를 적재하고 재실행 시 중복 여부를 확인한다.
- [ ] DB 볼륨이 컨테이너 재생성 후에도 유지되는지 확인한다.
- [ ] `/health`, `/health/db`의 정상 응답과 DB 연결 실패 상황을 확인한다.

**완료 기준:** 새 DB에서 초기 구성이 재현되고, 기존 데이터 업그레이드·볼륨 유지·DB 연결이 확인된다.

**관련 경로:** `compose.yaml`, `backend/app/models/v1.py`, `backend/app/models/catalog.py`, `backend/app/models/content.py`

### BE-03. 인증·세션과 핵심 API 회귀 검증

**선행:** BE-02

| 검증 영역 | 확인할 내용 |
|---|---|
| 인증·세션 | 테스트 계정 로그인, 세션 조회, 로그아웃, 만료 세션·미인증 요청 처리 |
| 접근 제어 | 다른 사용자의 데이터 접근 거부, CSRF 검증, 개발용 API 노출 여부 |
| 사용자·관심사 | 사용자 조회, 온보딩 저장, 분야·세부 토픽 조회·추가·삭제, 기존 입력 검증 |
| 콘텐츠 | 최신순 피드, 검색·페이지 처리, 상세의 `topicId`, 비공개·접근 불가 콘텐츠 처리 |
| 반응·저장 | 좋아요·선호·북마크 등록/해제, 반복 요청, 사용자별 저장 목록 |
| 알림 | 기존 목록·미읽음 수·읽음 처리 API를 이번 검증 범위에 포함하는 경우 확인 |

- [ ] 관련 기존 테스트를 실행하고 실패를 해결한다.
- [ ] 실제 PostgreSQL을 사용해 계정 생성 또는 테스트 계정 준비 → 관심사 저장 → 피드 → 상세 → 반응·저장 → 재조회 흐름을 검증한다.
- [ ] 기본 Mock 모드와 구분해 `NEXT_PUBLIC_CONSUMER_DATA_MODE=api`로 호출되는 요청이 실제 백엔드에 도달하는지 확인한다. 프런트엔드 구현 변경은 이 문서의 범위 밖이다.
- [ ] 데이터가 다른 사용자에게 섞이지 않고, 서버 재시작 후에도 저장 상태가 유지되는지 확인한다.
- [ ] 개발용 로그인·API 의존성을 기록하고 내부 테스트 환경의 접근 제한을 적용한다.

**완료 기준:** 핵심 API 흐름이 실제 DB에서 통과하고 인증·권한 오류가 의도한 응답으로 처리된다. 변경이 필요한 API만 수정하고 관련 검증을 재실행한다.

**관련 경로:** `backend/app/api/v1/router.py`, `backend/app/services/reaction_service.py`, `backend/app/api/v1/users/me/bookmarks.py`

### BE-04. 콘텐츠 적재와 LangGraph 실행 검증

**선행:** BE-02. API에서 확인하려면 BE-03도 완료한다.

- [ ] 현재 콘텐츠 파일과 대상 DB의 콘텐츠 수량을 각각 확인한다. 보고서의 파일 49개·과거 DB 51개 기록을 현재 수량으로 간주하지 않는다.
- [ ] 테스트 DB에서 일괄 적재하고 본문·출처·태그·공개 상태가 보존되는지 확인한다.
- [ ] 같은 콘텐츠를 다시 적재해 중복 생성 없이 처리되는지 확인한다.
- [ ] 충돌·잘못된 입력·적재 실패 시 기존 데이터와 트랜잭션이 어떻게 처리되는지 확인한다.
- [ ] MVP에 사용할 LangGraph 실행 경로를 먼저 검증한다. 기존 DB 연동 경로가 있는 영화 에이전트부터 확인할 수 있다.
- [ ] 실행 이력·단계 결과·초안·콘텐츠 저장 결과를 확인한다.
- [ ] 기존 발행 동작, 미리보기, 중복 방지, 실패 후 재실행을 테스트한다. 발행 정책 변경은 수행하지 않는다.
- [ ] 이미지 적재를 사용할 경우 외부 키와 네트워크 접근을 확인하고 명시적으로 실행한다.
- [ ] 음악·애니메이션은 파일 출력과 DB 발행 연동을 구분해 검증 결과를 기록한다.

**완료 기준:** 채택한 경로에서 콘텐츠 생성 또는 파일 적재 → DB 저장 → API 조회가 재현되고, 재실행으로 중복이 발생하지 않는다. 지원하지 않는 연동 경로는 후속 작업으로 기록한다.

**관련 경로:**

- `backend/app/seeds/agent_contents.py`
- `backend/app/seeds/content_images.py`
- `backend/scripts/run_movie_agent_once.py`
- `backend/app/services/movie_agent_runner.py`
- `backend/app/services/movie_agent_publication.py`
- `agent/export_contents.py`

### BE-05. 챗봇 외부 LLM 연동 검증

**선행:** BE-02. BE-03·BE-04와 일부 병행 가능하다.

- [ ] 사용할 LLM 계정의 크레딧·모델 접근·API 키를 확인하고 실제 호출을 검증한다.
- [ ] 보고서에 기록된 `HTTP 429`, `insufficient_quota`·`credit_balance_exhausted` 문제가 해소됐는지 확인한다.
- [ ] 대화 생성 → 질문 → 작업 조회 → 답변 반환 흐름을 검증한다.
- [ ] 현재 콘텐츠와 관련 콘텐츠가 답변 문맥에 반영되는지 확인한다.
- [ ] 다른 사용자의 대화·작업 조회가 거부되는지 확인한다.
- [ ] 외부 API 실패·지연 시 작업 상태와 사용자에게 반환할 오류가 일관적인지 확인한다. 크레딧 부족을 무제한 재시도로 처리하지 않는다.
- [ ] 작업 수행 중 서버 재시작 시 상태·복구 동작을 확인하고 제한 사항을 기록한다.

**완료 기준:** 실제 LLM 답변과 실패 경로를 확인한다. 챗봇을 이번 배포에서 제공할 경우 필수 검증으로 취급한다.

**구현 참고:** 현재 챗봇은 FastAPI `BackgroundTasks` 기반이다. 콘텐츠 생성용 LangGraph와 별도 실행 경로이며, 영속 작업 큐는 아직 구현되지 않았다.

**관련 경로:** `backend/app/services/chat_service.py`, `backend/app/integrations/llm.py`, `backend/app/api/v1/chat/router.py`, `backend/app/models/chat.py`

### BE-06. 컨테이너 실행과 수동 배포 준비

**선행:** BE-02. 서버 생성·도메인 준비는 BE-03~BE-05와 병행 가능하다.

- [ ] 현재 Docker 구성으로 API와 DB를 실행하고 의존성·시작 명령·DB 연결을 확인한다.
- [ ] 컨테이너 재시작 설정과 종료 시 진행 중 요청 처리 동작을 확인한다.
- [ ] 마이그레이션을 명시적인 배포 단계로 두고, 여러 API 프로세스가 동시에 실행하지 않게 한다.
- [ ] 로그를 표준 출력으로 수집하고 요청 오류·DB 오류·에이전트·LLM 실패를 구분해 확인할 수 있게 한다.
- [ ] Nginx의 API 프록시와 요청 시간 제한을 실제 요청 흐름에 맞춰 설정한다.
- [ ] HTTPS용 도메인·DNS·인증서 발급 및 갱신 절차를 준비한다.
- [ ] 쿠키의 `Secure`, `SameSite`, 도메인 설정과 CORS·자격 증명 전송을 실제 프런트엔드/API 도메인 조합에서 검증할 준비를 한다.
- [ ] 버전이 식별되는 이미지와 직전 버전 복구 절차를 준비한다.

**완료 기준:** 새 환경에서 같은 이미지·설정으로 실행할 수 있고, 마이그레이션·시작·헬스체크·복구 순서가 문서화된다.

### BE-07. Lightsail 내부 검증 환경 배포

**선행:** BE-03, BE-04, BE-06. 챗봇 제공 시 BE-05도 완료한다.

**초기 구성:** Lightsail Linux 인스턴스에서 Nginx, API 컨테이너, PostgreSQL 컨테이너를 운영한다. DB 데이터는 영속 볼륨에 저장한다. 초기 배포는 수동으로 검증하고 자동화는 이후 적용한다.

- [ ] AWS 계정·배포 리전·Lightsail Linux 인스턴스 사양을 준비한다. 사양은 실제 프로세스 수와 메모리 사용량을 확인해 선택한다.
- [ ] SSH 접근을 제한하고 HTTP/HTTPS를 열어 서비스 접근을 구성한다.
- [ ] 고정 IP와 DNS를 연결한다.
- [ ] PostgreSQL은 컨테이너 내부 네트워크로 연결하고 외부 DB 포트를 공개하지 않는다.
- [ ] 서버에 실행 도구·배포 이미지·환경변수·영속 볼륨을 구성한다.
- [ ] DB 마이그레이션과 필요한 기본 데이터 적재를 실행한 뒤 API를 시작한다.
- [ ] Nginx·HTTPS를 적용하고 `/health`, `/health/db`를 확인한다.
- [ ] 실제 도메인에서 세션 쿠키·CORS·CSRF 및 핵심 API 흐름을 재검증한다.
- [ ] 개발용 API가 활성화된 내부 환경은 접근을 제한한다. 일반 사용자 공개 환경에서는 `ENABLE_DEV_API`를 비활성화하고 실제 사용자 인증 경로를 검증한다.
- [ ] 배포 커밋·이미지 버전·실행 설정·검증 결과를 기록한다.

**완료 기준:** 접근이 제한된 내부 환경에서 HTTPS로 핵심 API를 사용할 수 있고, 실제 DB·외부 연동과 재시작 후 데이터 유지가 확인된다. 내부 배포 완료를 일반 사용자 공개 준비 완료로 간주하지 않는다.

### BE-08. 백업·복구와 운영 점검

**선행:** BE-07

- [ ] DB 백업 주기·보관 위치·보관 기간을 정하고 백업을 자동 실행한다.
- [ ] 백업 파일을 Lightsail 인스턴스 밖에도 보관한다.
- [ ] 별도 테스트 DB에 백업을 복원해 사용자·콘텐츠·세션 관련 데이터의 복구를 확인한다.
- [ ] API·DB 컨테이너 재시작과 서버 재부팅 후 서비스 복귀를 확인한다.
- [ ] CPU·메모리·디스크·API 오류·헬스체크를 점검할 수 있게 한다.
- [ ] 로그 보관·회전과 인증서 갱신을 확인한다.
- [ ] LLM 사용량·크레딧 부족 및 외부 API 장애를 확인할 운영 방법을 정리한다.
- [ ] 배포 실패 시 직전 이미지로 되돌리는 절차를 검증한다. DB 변경은 호환성·복원 가능 여부를 별도로 확인한다.

**완료 기준:** 실제 백업 복원과 서비스 재시작·이미지 복구가 검증되고, 장애 시 확인 순서가 문서화된다.

### BE-09. GitHub Actions·ECR 배포 자동화

**선행:** BE-07, BE-08

- [ ] GitHub Actions에서 필요한 백엔드 테스트·이미지 빌드를 실행한다.
- [ ] AWS 접근은 필요한 권한만 부여하고, 가능하면 OIDC를 사용해 장기 AWS 키 저장을 피한다.
- [ ] ECR에 커밋 또는 릴리스 버전으로 식별되는 이미지를 업로드한다.
- [ ] Lightsail이 이미지를 가져오는 인증 경로와 권한을 확인한다.
- [ ] 이미지 가져오기 → 필요한 마이그레이션 → 컨테이너 교체 → 헬스체크 순서를 자동화한다.
- [ ] 동시 배포를 방지하고 헬스체크 실패 시 실패 상태를 명확히 남긴다.
- [ ] 이전 이미지로 복구할 수 있게 하고, 마이그레이션 호환성을 배포 전에 확인한다.
- [ ] 자동 배포 후 BE-03의 핵심 흐름을 간단한 배포 확인 절차로 다시 검증한다.

**완료 기준:** 같은 변경을 수동 서버 수정 없이 배포할 수 있고, 실패 감지·직전 이미지 복구·배포 이력 추적이 가능하다.

## 3. 이번 배포 이후의 별도 백엔드 작업

아래 항목은 현재 구현 범위와 구분한다. 이번 내부 검증 배포를 위해 모두 구현할 필요는 없다.

| 후속 항목 | 착수 조건 |
|---|---|
| 실제 소셜 OAuth | 일반 사용자에게 해당 로그인 방식을 제공하기 전. 현재 데모 로그인을 실제 OAuth로 간주하지 않음 |
| 음악·애니메이션 DB 발행 연동 | 해당 에이전트 결과를 자동으로 DB에 발행해야 할 때 |
| 영속 작업 큐·워커 분리 | 재시작 시 작업 유실, 긴 작업, 동시 실행이 운영상 문제가 될 때 |
| 임베딩 생성·벡터 검색 | 검색·추천 요구사항이 구체화됐을 때. pgvector 컬럼 존재만으로 구현 완료가 아님 |
| 사용자 행동 이벤트·개인화 추천 | 데이터 수집 요구사항과 이용 목적이 확정됐을 때 |
| 대화 목록·이력·삭제 API | 해당 기능을 제공할 범위가 확정됐을 때 |
| DB·API 인프라 분리 | 부하·복구 요구·운영 비용을 근거로 RDS나 ECS 등으로 이전할 필요가 생겼을 때 |

## 4. 배포 완료 확인표

- [ ] 배포 커밋과 이미지 버전이 기록돼 있다.
- [ ] 새 DB 마이그레이션 및 기존 데이터 보존 검증이 통과했다.
- [ ] Mock을 사용하지 않은 핵심 API 흐름이 통과했다.
- [ ] 사용자별 접근 제어·세션·CSRF를 확인했다.
- [ ] 콘텐츠 적재·재적재 시 중복 방지를 확인했다.
- [ ] 제공할 에이전트·챗봇의 실제 연동과 실패 처리를 확인했다.
- [ ] HTTPS·실제 도메인의 쿠키·CORS를 확인했다.
- [ ] DB가 외부에 노출되지 않고 데이터가 재시작 후 유지된다.
- [ ] 내부 테스트 환경과 공개 환경의 인증·개발용 API 설정을 구분했다.
- [ ] 백업 복원·서비스 재시작·직전 이미지 복구를 확인했다.
