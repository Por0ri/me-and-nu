# 사용량이 없는 기존 보류 작업의 복구 준비

이 문서는 `main`의 사용량 수정 배포 당시 준비 기록이다. 이후 복구 기능 구현·격리 검증은
[봉인 보류 비용 복구 문서](HELD_COST_RECOVERY_2026-11-26.md)에서 별도로 추적한다.
아래의 원래 작업·비용·봉인 증거와 당시 미구현 판단은 역사 기록으로 보존한다.

## 현재 결론

이번 사용량 수정은 **앞으로 생성되는 보류·생략 결과에 사용량 증거를 보존하는 수정**이다.
이미 봉인된 기존 결과를 보완하거나 자동 생성을 재개하는 기능은 아니다. 기존 보류 작업은
그대로 보존하고, 비활성 배포 후 읽기 전용 증거 묶음까지만 준비한다.

현재 복구 코드는 아래 작업을 지원하지 않는다. 후속 복구 코드와 격리 검증이 필요하며,
이번 준비 자료는 적용 가능한 `failure_recovery plan`이나 재개 승인 영수증이 아니다.

동일 항목과 원본 해시를 다시 대조한다. 작업·회원 원문이나 자격 증명을 Git에 넣지 않는다.

## 정상 보류와 회계 증거 누락은 다른 문제

Agent는 상품의 명확한 일정 근거가 없어 사실 추출 전에 `expiry_unresolved_held`로
종료했다. 제목·요청 작품·출처·보류 사유가 있는 정상 보류 결과지만, 해당 조기 반환이
사용량 필드를 빼고 저장했다. 컨트롤러는 명시적인 0회 기록도 없으므로 다음 작업을 중단했다.

해당 ONE PIECE 경로는 코드상 유료 링크 검토를 끄며 OCR 대상 출처도 아니어서 모델 호출 전
반환 경로와 일치한다. 그렇더라도 **사후 코드 해석을 제공자 사용량 영수증으로 대체하지 않는다.**
기존 결과에 `llm_calls=0` 또는 비용 0을 추가하지 않으며, 같은 기사를 재생성하지 않는다.

새 수정은 이전 사용량, 추출 사용량, 사용량이 불완전하다는 표시를 조기 반환에 함께 담는다.
모델 호출을 시도했는데 제공자 사용량이 없으면 0원으로 기록하지 않는다. 과거 봉인 결과를
읽는 `result_cost`의 `missing_cost_evidence` 차단은 유지한다.

## 기존 복구 경로를 사용할 수 없는 이유

- [`failure_recovery.py`](../worker/menu_worker/failure_recovery.py)의 대상은
  `job_needs_attention` 또는 `failed_generation_cost_unknown`으로 정지한 작업이다.
  DB 작업·시도는 `needs_attention`, 결과는 `null`, 봉인 결과 해시는 없어야 한다.
- 그 경로는 비정상 종료와 결과 없음 또는 `generation_failed` 영수증만 받는다.
  `exit=0`과 `manifest.json`이 있는 이번 정상 보류 결과는 의도적으로 거절한다.
- [`bounded_generation.py`](../worker/menu_worker/bounded_generation.py)의 과거 비용 예약
  기능은 특정 83388 기사 작업·시도·결과 해시에만 연결돼 있다. 이번 작업에 재사용할 수 없다.
- [`daily_resume.py`](../worker/menu_worker/daily_resume.py)의 명시적 실패 재개는 검증된
  기존 실패 복구 영수증에만 적용된다. 그 영수증을 새 보류 작업에도 적용하거나 체크포인트의
  정지 사유를 바꿔 통과시킬 수 없다.

기존 [실패 복구 문서](FAILED_GENERATION_RECOVERY_2026-11-26.md)의 명령은 이번 대상에
그대로 실행하지 않는다. `daily_failure_recovery`라는 별도 제품 명령도 없으며,
`test_daily_failure_recovery.py`는 기존 실패 복구와 일일 컨트롤러의 회귀 테스트다.

## 이번에 준비하는 읽기 전용 증거

운영 담당자는 생성 Worker·컨트롤러·적재기를 중지하고 타이머 비활성 및 빈 브로커를 확인한
상태에서 private helper `held_cost_prepare.py`를 실행할 수 있다. 이 helper는 적용·재개 인자를
제공하지 않는다. 원본 작업 DB·체크포인트·산출물은 읽기만 하며, 별도의 root 전용 준비 폴더에
원본 체크포인트와 작업 DB 스냅샷, 해시를 묶은 검토 자료를 저장한다.

준비 자료는 다음을 서로 연결한다.

1. 원본 체크포인트 바이트 SHA-256, 해당 행과 정책 날짜·실행 ID·당일 4회/1건.
2. 전체 전용 작업 DB 5개 테이블의 현재 스냅샷과 정확한 작업·시도 행.
3. 입력의 출처·정규화 URL·작품·유형·입력 해시·중복 방지 키.
4. 대상의 `launch.json`, `exit.json`, `manifest.json`, `result.json`, 표지 이력과 전체
   산출물 파일 목록·크기·해시. DB의 결과 해시와 봉인 manifest의 결과 해시가 같은지 확인한다.
5. 이전 실패 복구 영수증·감사 기록·당일 원본 행들의 해시와 현재 알려진 비용.
6. Worker·타이머 상태, 브로커 대기/미확인 수, 서비스 데이터 보존을 확인한 배포 전후 기록.

준비가 끝나도 `apply_supported=false`, `generation_enabled=false`, `resume_authorized=false`다.
준비 자료를 복구 영수증 디렉터리에 쓰거나 기존 감사 기록에 등록하지 않는다. 해시·이력·실행
상태가 조회 도중 바뀌면 자료 생성을 거부한다. 비밀값과 DB 원문은 서버 private 폴더에만 남는다.

## 후속 구현안 — 아직 미구현

봉인된 정상 보류 결과의 비용 미확정을 처리하는 **별도 검증 분기**가 필요하다. 기존 실패
복구 조건을 넓게 풀거나 정상 결과의 봉인 검증을 생략하는 방식은 사용하지 않는다.

- 최초 범위는 `succeeded / held / expiry_unresolved_held`, `exit=0`, 봉인 검증 성공,
  사용량 증거 없음으로 중지된 대상에 한정한다. 검수 통과 결과나 실행 중·종료 불명확 작업은 거절한다.
- 계획은 위 모든 원본 해시와 전체 DB 스냅샷을 묶는다. 적용 시 기존 파일·DB 잠금과 CAS를
  사용하고, 백업·영수증을 먼저 보존한 뒤 체크포인트만 원자적으로 바꾼다.
- DB의 `succeeded / held`와 시도 이력, `result.json`·manifest·result SHA는 바꾸지 않는다.
  체크포인트에서만 해당 행의 정리 완료를 기록하되 `accounting_method=unknown`,
  `estimated_cost_usd=null`, 전체 비용 미확정을 명시한다. 기존 비용·영수증·4회/1건을 유지한다.
- 새 영수증의 종류를 기존 `needs_attention` 실패 영수증과 구분한다. 컨트롤러의 비용 집계,
  완료 이력 검증, 일일 정책 이월, 호스트 정리/재개 검증이 이 종류를 일관되게 확인해야 한다.
  원래 실패 영수증 형식과 검증은 계속 지원한다.
- 적용 후에도 명시적인 정지 상태를 유지한다. 타이머·Worker 시작, 큐 발행, 추가 LLM 호출,
  서비스 DB 적재는 별도 재개 단계다. 새 날짜나 새 실행 폴더로 이력을 우회하지 않는다.
- 같은 기사의 source+canonical URL 및 생성 시작 이력 차단을 유지한다. 보류 정리로
  검수 통과 수가 증가하거나 `export-staging`/검수 대기 적재가 허용되지 않아야 한다.

필수 후속 회귀는 원본 8작업/8시도·봉인 파일 불변, 원래 보류 상태·미확정 비용 유지,
반복 적용과 중간 중단 복구, 변조·잠금·실행 중 대상 거절, 동일 기사 재생성/내보내기 차단,
정리 후 자동 재개 금지, 다른 기사 진행 시 40회/20건 유지, 다음 날 비용·이력 이월이다.
실제 LLM 없이 격리 DB에서 검증한 뒤 적용 가능 여부를 다시 판단한다.

## 이번 검증과 남은 작업

사용량 수정의 최종 Agent 합동 회귀는 **326건 통과, 실패·오류·생략 0건**이다.
네트워크 차단·API 키 없는 컨테이너에서 테스트했으며 소스 해시도 실행 전후 같았다.
여기에는 과거 사용량 없는 봉인 결과를 계속 거절하는 회귀가 포함된다.

이 결과는 **새 출력의 사용량 보존 수정 검증**이다. 이번 기존 보류 작업의 복구 적용·유료 재개가
가능해졌다는 의미가 아니다. 현재 단계의 완료 조건은 수정 배포, 비활성 유지, 원본 보존 대조,
검토용 증거 준비이며, 기존 보류 비용 정리 코드는 후속 구현으로 남는다.
