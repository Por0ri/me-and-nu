# RAG 운영 스케줄러 연결과 비활성 검증

기준 main: `bfa9e17b0263e70d092406466c622ab277f0b51d` (PR #137 반영).
이번 범위는 코드 연결·비활성 설정 준비·무과금 검증이다. 서버 정책이나 systemd를
교체하지 않고 새 RAG 유료 생성, 서비스 DB 적재, 자동 공개도 실행하지 않는다.

## 동작

- 기존 schema-v1 기사 스케줄은 그대로 유지한다. schema-v2 정책에 `rag`를
  명시한 경우에만 RAG scope/runtime 해시와 날짜별 별도 inbox를 일일 계획에 묶는다.
- 단일 일일 controller가 기사와 RAG를 순차 처리한다. 기존 일일 원장과 복구
  영수증을 상속하며 **합산 최대 40회 시도·검수 통과 20건**을 유지한다.
  생성 실패·보류·생략의 기존 시도와 비용을 지우거나 같은 기사를 재생성하지 않는다.
- 하루는 한국 시간 00:00부터 다음 날 00:00 직전까지다. 안전한 작업 완료에 필요한
  시간이 남지 않으면 새 작업을 받지 않는다. 새 예산 상한이나 임의 종료 시각을 추가하지 않는다.
- 두 Worker는 각각 `anime-generation-live`와 `content.rag_generate`만 소비한다.
  재개 검사에는 두 작업 원장·봉인된 결과·두 큐를 모두 포함한다.
- 기사와 RAG 적재기는 별도 inbox를 읽지만 같은 일일 정책 해시와 DB 잠금으로
  합산 20건을 제한한다. 각 적재기의 처리 수 합계도 일일 검수 통과 수와 대조한다.
- 신규 결과는 `pending_review / needs_review / checking`으로 적재한다.
  운영자 승인 전에는 피드에 나오지 않고, 재적재는 기존 승인이나 검수 이력을 되돌리지 않는다.
- 전날 RAG 결과를 복구 적재할 때는 정확한 원래 날짜를 `--reconcile-policy-date`로
  지정하고 기존 정책 해시·만료 시각을 그대로 검증한다. 복구 사실을 별도 영수증으로 남긴다.
  현재/미래 날짜를 이 옵션으로 우회하거나 만료된 콘텐츠를 적재할 수 없다.
- 새 RAG 실패에서 비용이 미확정이면 안전하게 중단한다. 기사 복구 영수증을
  새 RAG 실패에 임의로 재사용하는 자동 복구는 추가하지 않는다.

## 키·모델 준비

기존 `/home/ubuntu/.secrets/anime-openai-key.txt`는 활성화용 구성에서 RAG Worker에만
읽기 전용으로 연결한다. 값이나 해시를 출력·복사하지 않는다. controller와 적재기는
모델 키를 받지 않는다. 비활성 구성에는 RAG 키 mount와 외부망 연결이 없다.

생성·독립 검수는 기존 `gpt-6-luna`, 검색 임베딩은 기존 `text-embedding-3-small`
1,024차원을 유지한다. 저장된 벡터는 재임베딩하지 않는다. 모델 단가는
`deploy/rag-generation/model-settings-20261126.json`에 공식 출처·확인 날짜와 함께
명시하고 준비 도구에서 SHA를 확인한다. 단가는 비용 기록용이며 일일 예산 제한이 아니다.

공식 근거: [생성 모델](https://developers.openai.com/api/docs/models/gpt-6-luna),
[검색 임베딩](https://developers.openai.com/api/docs/models/text-embedding-3-small).
등록되지 않은 모델 snapshot의 비용을 임의로 추정하지 않고 기존 미확정 처리 규칙을 유지한다.

`prepare_runtime.py`는 새 파일만 만들며 기존 runtime·영수증을 덮어쓰지 않는다.
기본값은 `enabled=false`다. 로컬 비활성 준비 파일 SHA:
`146e69fa8db8491c13b0bebb15b188cb6d8fd0b67fb7bd661dd7fddb4c89dd49`.

서버 읽기 전용 점검에서 기존 키가 uid 10001/mode 0600의 비어 있지 않은 일반 파일이고,
전용 vector DSN이 비공개 권한이며, 격리 실행 사본의 SQLite journal이 DELETE임을 확인했다.
키와 DSN 내용은 읽지 않았다. 실제 provider 권한·유료 생성 성공 여부를 새로 확인한 것은 아니다.

## 비활성 사전 점검과 향후 전환

비활성 사전 점검은 운영 중인 기사 스케줄과 **별도 검증 state/journal**에서 한다.
OFF 정책·runtime 해시로 만든 journal을 나중에 ON으로 바꿔 재사용할 수 없다.
이를 허용하려고 기존 해시 검사나 이력 보존 조건을 완화하지 않았다.

향후 활성화는 현재 기사 실행을 먼저 정상 종료·검증하고, 그 최종 체크포인트의
이력을 seed로 삼는 다음 한국 날짜의 새 혼합 정책·plan·journal로 전환한다.
현재 날짜의 시도 수를 초기화하는 두 번째 스케줄을 만들지 않는다.
검토할 설정은 RAG 작품/유형/출처 scope, 명시적 `feed_valid_days`, 새 runtime SHA,
이미지 digest, 적재기 전용 DSN 파일이다. 기존 저널·비용·복구 영수증을 삭제하지 않는다.

현재 서버의 비활성 `menu-rag-prepared` Worker도 RAG 큐를 구독하므로, 실제 활성화 전에는
새 scheduled Worker와 동시에 소비하지 않는지 확인해야 한다. 스케줄러는 시작 전·후
Docker 실행 설정을 검사하여 외부 프로젝트의 RAG Worker, 다른 이미지·큐·노드, 중복
Worker가 있으면 생성 명령을 실행하지 않는다. 로그에는 개수와 통과 여부만 남긴다.
아직 작업이나 Worker 시작이 없었던 사전 차단은 동일한 준비 계획을 유지하므로,
운영자가 충돌 Worker를 정리한 뒤 다시 검사할 수 있다. 시작 후 불일치는 중단 상태로 남긴다.
이 검사는 현재 Docker 호스트의 실행 계약을 확인하며 다른 서버의 소비자까지 탐색하지 않는다.
이번에는 Worker를 정지하거나 교체하지 않는다. 공개에는 기존 운영자 승인 절차를 그대로 사용한다.

## 검증 기록

실제 LLM 호출·서비스 DB 연결·서버 파일 쓰기 없이 검증했다.

- 네트워크 없는 backend 적재·추천 피드 회귀: 144건 통과.
- Linux 호스트 스케줄러 회귀: 42건 통과. 기존 기사 흐름, 혼합 40/20, 이틀 재개,
  두 적재기 사이 중단 후 재개, RAG 소비자 충돌 차단과 준비 계획 보존을 포함한다.
- 네트워크 없는 Worker 공유 제한·재개·중복·기존 실패/보류 이력 회귀: 111건 통과.
- 임시 PostgreSQL의 적재·승인·기존 추천 흐름: 20건 통과.
  외부에서 생성된 Celery 봉투를 입력받는 별도 선택 테스트 1건은 미선택으로 건너뛰었다.
- 임시 PostgreSQL의 RAG 작업 중복·기존 원장 보존·혼합 이력 검사: 19건 통과.
- 실제 Docker mount/이미지 검사: 3건 통과. 읽기 전용 controller의 DELETE 사본 조회,
  WAL 조건 차단, 기존 기사 이미지에서 provider 패키지 없이 RAG controller 연결을 확인했다.
- 기존 비활성 구성과 새 Compose/runtime 준비 검사: 21건 통과.

처음 추천 배치 검사 2건은 backend 검증 이미지에 numpy가 없어 실패했다.
운영 이미지는 변경하지 않고 별도 로컬 테스트 이미지에 numpy를 추가한 뒤 모두 통과했다.
임시 DB는 외부망·호스트 포트 없이 만들고 검증 후 해당 실행에서 만든 자원만 삭제했다.
수집 파서·추천 알고리즘·API 공개 규칙·서비스 DB schema는 변경하지 않았다.
총 360건이 통과했고 선택 테스트 1건은 위 사유로 건너뛰었다. 마지막 원격 조회에서도
main은 위 기준 커밋과 같았다. 서버 최종 조회는 기사 Worker·비활성 RAG Worker가
healthy, 메인 health HTTP 200, 기존 작업 기록 23건·미확정 비용 기록 2건 유지로 확인됐다.
이번 변경사항의 커밋·푸시·운영 배포는 실행하지 않았다.

로컬 상세 증거: `out/rag-scheduler-validation-20261126/`의 테스트 로그,
`postgres-verification.json`, `host-binding-verification.json`, 비활성 runtime과 준비 영수증.
