# BE 인계: 실제 iPhone Safari 검증

현재 패키지의 자동 검증 대상은 Windows loopback HTTPS다. 아직 iPhone에서 접속하거나 검증하지 않았다. 배포·LAN 공개·방화벽·인증서 설치는 별도 승인 대상이며 이 문서는 실행 승인이 아니다.

## 접근 경로 선택

가장 먼저 BE가 이미 관리하는 **접근 제한된 테스트 호스트**가 있는지 확인한다. 그 호스트에서 네 조건과 동일 Mock을 함께 실행하고 기존 인증된 HTTPS 진입점을 재사용할 수 있다면 Windows 방화벽 변경/Caddy 설치/iPhone 사설 CA 신뢰를 피할 수 있다. 운영 API를 공유하는 환경은 사용하지 않는다. 일반 Preview도 후보지만 배포 보호, 별도 합성 Mock, 서버의 외부 요청 제한, 동일 origin, 자동 배포 정책을 먼저 확인해야 한다. 운영 환경변수/DB 연결을 상속하는 Preview는 부적합하다.

현재 소스를 인터넷에 그대로 올리면 안 된다. `/__lab/start/*`는 loopback용 합성 세션 발급기이지 원격 사용자 인증이 아니다. 외부 진입점 앞에 접근 인증/허용 대상을 제한하고, 모든 FE·API·이미지·실험 선택 경로를 동일하게 보호해야 한다. `/__lab/stop`, 상태/진단 경로도 외부에 노출하지 않는다.

BE 호스트에 맞춰 추가 구현/검증할 항목:

1. 테스트 전용 HTTPS origin을 확정한다. TLS는 정상 신뢰 체인이어야 한다. 실험 인증서 개인키를 Git으로 전달하지 않는다.
2. `config.cjs`의 origin과 `patch-snapshots.cjs`의 same-origin 제한을 그 origin 기준으로 적용하고 **네 FE를 다시 빌드**한다. NEXT_PUBLIC 값을 실행 시에만 바꿔서는 안 된다.
3. FE/Mock은 loopback에 두고 기존 인증된 reverse proxy만 진입점으로 사용한다. 게이트웨이가 넘길 Host/Origin 및 `serve.cjs`의 host 검증을 함께 설계한다. 이 서버는 현재 `Host:127.0.0.1:8443`만 받으므로 단순 포트 전달만으로 iPhone 접속은 되지 않는다. 브라우저에 내려가는 API 주소도 현재 loopback이므로 origin 재빌드가 필요하다.
4. Secure/HttpOnly 쿠키를 테스트 도메인에 한정하고 CSP connect-src/img-src, CSRF, 보호 이미지, A/B/C/D 선택을 실제 HTTPS origin에서 재검증한다. 인증을 위해 운영 OAuth를 붙이지 않는다.
5. Mock 미정의 요청, 운영 API/DB/외부 서비스 요청은 실패해야 한다. TLS reverse proxy를 포함한 서버 outbound 정책을 검토한다. 외부 API 주소와 미정의 경로의 부정 테스트가 실제 접속 전에 거부되는지 확인한다.
6. 다른 사용자/비허용 IP의 접근 거부, 직접 FE 포트 접근 거부, 실험 시작/중지 경로 보호, 로그에 인증정보 미포함을 확인한 뒤 승인받는다.

Windows LAN 경로는 보류 상태다. 기존 Node Public 전체 포트/원격 IP 허용 규칙을 그대로 유지하는 조건에서는 Node를 LAN에 바인딩하지 않는다. 비-Node 진입점이나 별도 격리된 테스트 PC를 검토할 수 있으나 새 방화벽 규칙만으로 기존의 모든 광범위 규칙을 덮어 제한할 수 있다고 가정하지 않는다. 관리자 감사/Caddy 설치/방화벽 변경을 이 패키지가 실행하지 않는다.

## iPhone 비교 절차

1. 기종·iOS 빌드·Safari·여유 저장 공간·배터리/발열·열린 탭 수·네트워크·시각/시간대를 기록한다. 화면 녹화 여부도 모든 조건에서 같게 한다. 실계정은 사용하지 않는다.
2. 같은 fixture 해시, 10슬라이드, 같은 네트워크/HTTPS origin/인증 정책으로 비교한다. 새 합성 세션에서 시작한다. 실험 사이 기존 탭을 닫고 같은 대기 시간을 둔다. 데이터 삭제/재부팅을 한다면 모든 조건에 같은 절차를 적용하고 기록한다.
3. 순서 편향을 줄이기 위해 `A→B→C→D`, `B→C→D→A`, `C→D→A→B`, `D→A→B→C`를 한 묶음씩 반복한다. 각 조건 최소 3회, 가능하면 5회 이상 수행하고 실패한 실행도 남긴다. 종료가 잦거나 기기가 뜨거우면 중단하고 재개 조건을 기록한다.
4. HOME 진입 후 첫 이미지/로딩 종료, 30초 대기, 가로 10장 스와이프, 세로 스크롤, 다음 페이지 끝까지 로드, DETAIL→HOME 위치/포커스, 저장→SAVE→MY→HOME 동기화, 백그라운드 30초 후 복귀를 같은 순서로 수행한다. C는 모든 데이터를 받으면서 HOME 카드 1개를 유지하는지 확인한다.
5. 서버 로그에서 최초/후속 limit, nextCursor, 123개 ID의 순서/유일성, 이미지 요청과 응답 오류를 확인한다. B는 이미지 요청·네이티브 Blob/object URL/decode/preload가 0이어야 한다. 재시도 등 이번 Mock에 구현되지 않은 오류 주입 시나리오는 성공으로 기록하지 않는다.
6. 오류가 발생하면 현지 시각과 UTC 오프셋, 조건, 경과 시간, 마지막 동작, 하얀 화면/자동 새로고침/탭 종료/브라우저 종료 여부를 기록한다. 가능하면 해당 시각의 iOS 분석 데이터/Jetsam 원본을 별도의 제한된 채널로 보존한다. 개인 식별정보를 제거하기 전 공개 GitHub에 올리지 않는다.
7. WebContent 프로세스·종료 사유·발생 시각이 실제 실행과 일치하는지 BE가 대조한다. Mac이 없으면 Safari 실시간 프로세스 메모리/힙을 직접 측정했다고 쓰지 않는다. DOM·요청 수는 관측 지표이며 메모리 수치가 아니다.

기록 양식: 실행 ID / 날짜·시각·시간대 / 기기·iOS / A·B·C·D / 원본 SHA / fixture SHA / 슬라이드 수 / cache·tab 초기 조건 / 최초 limit·카드 수 / 수신 123건 / 이미지 요청 수 / 마지막 동작 / 경과 시간 / 성공·종료·재로드 / 연결된 Jetsam 파일 / 비고.

## 판단과 종료

- B만 안정적이면 이미지 경로를 우선 조사하되 B의 아이콘·SVG·첫 이미지 대기 변경도 고려한다.
- C만 안정적이면 마운트된 DOM/컴포넌트·이미지 수를 우선 조사한다. C도 원본 100건 응답을 보관한다.
- D가 초기에는 안정적이어도 123건 누적 후 다시 종료되는지 반드시 확인한다. page20은 초기 부하 완화이며 무한 누적 DOM을 해결하는 변경은 아니다.
- 실제 iPhone 재현 소실과 회귀 검증 전에는 해결 완료/베타 안정성 확보로 표시하지 않는다. 베타 시작 여부는 별도 팀 승인이다.
- 완료 후 테스트 진입점을 닫고 임시 인증/세션/키를 폐기한다. 별도 승인으로 설치했던 인증서나 임시 방화벽 규칙이 있다면 이름/경로를 확인해 **그 항목만** 제거한다. 이 loopback 패키지는 OS 인증서·방화벽을 바꾸지 않으므로 복원할 해당 설정이 없다. 비교 로그는 비밀정보 제거 후 보존한다.
