# 유형별 자동수집 출처 라우팅

`config/sources.json`은 출처 주소와 수집 상태를, `config/source_type_map.json`은 출처가 지원할 수 있는 콘텐츠 유형을 관리합니다. 하나의 출처를 여러 유형에 연결할 수 있지만, 연결만으로 자동수집이나 생성 근거가 승인되는 것은 아닙니다.

## 후보 발견과 원문 근거 분리

- 콘텐츠 후보는 작품별 공식 사이트를 순회해 찾기보다 유형별 뉴스·행사·상품·리뷰 매체와 집계 출처에서 찾습니다. 후보를 처음 발견한 매체와 실제 발표·행사의 원문 출처 URL은 서로 다른 역할로 보존합니다.
- 작품별 공식 사이트 레코드는 삭제하지 않습니다. 다만 `work_title_ko`가 지정된 프랜차이즈 전용 공식 사이트는 `discovery_enabled: false`로 두어 반복 후보 탐색 대상에서 제외하고, 발견된 항목의 원문/귀속 정보로 연결할 수 있게 유지합니다. `status: active`만으로 후보 탐색이 실행되는 것은 아닙니다.
- 범용 매체의 후보가 공식 발표를 인용하더라도 원문 링크를 데이터에 연결하고, 날짜·장소·가격 등 중요한 사실을 그 원문에서 확인합니다. 원문 개별 URL을 출처 후보 레지스트리에 계속 추가하지 않습니다.
- `crawl-generate`는 후보 URL이 활성화된 유형별 1차 출처 도메인이면 그 페이지를 직접 검증합니다. 후보가 등록된 HTML 발견 매체의 기사이면 기사 본문 내 외부 링크 중 유형에 연결된 활성 1차 출처를 찾아 원문을 한 번 확인합니다. 원문을 하나로 특정하지 못하면 발견 기사만으로 생성하지 않고 `original_source_unresolved`로 보류합니다.
- DB의 `SourceEvidence.url`은 사실을 실제로 확인한 원문 URL입니다. `discovered_via_source_id`, `discovery_url`, `discovery_title`은 후보 발견 경로를 별도로 보존하며, 발견 매체를 원문 사실 근거로 승격시키지 않습니다. 발견 기사와 원문 링크 관계는 원문 캡처 메타데이터에도 남깁니다.
- 집계·전문 매체가 `terms_review` 등 보류 상태라면 후보를 자동 수집하지 않습니다. 유형별 매체 후보를 추가로 검증한 뒤 상태를 별도로 승인해야 합니다.

## 생성 근거로 세는 기준

- 정보형 10개 유형: `active` + 자동 수집 방식 + `primary` 출처만 집계합니다. `editorial`은 평가·순위·감상 기반의 `review`와 `curation`에만 허용합니다.
- `humor`: 자동 API 어댑터로 수집되는 `trend_only` 출처만 사용합니다. Mastodon은 공개·비민감 원글만 대상으로 하며, 본문은 익명화된 임시 소재로 30일 보관하고 계정·미디어는 저장하지 않습니다. 사실 확인 자료가 아니라 토론·유머 소재로만 쓰고, 결과는 원문 문장 복사가 아닌 재구성으로 제한합니다.
- RSS/discovery 역할은 후보를 찾는 데만 쓰며 생성 근거 수에 포함하지 않습니다.
- 상태나 역할이 바뀌면 `source-routing` 명령과 테스트 결과가 이를 반영합니다. 신규 출처 추가 시에도 실제 HTTP 응답, robots 경로, 추출 결과를 검증한 뒤에만 승인 상태로 전환합니다.

## 유형별 후보 발견 출처 원칙

아래는 출처를 찾고 연결할 때 적용할 방향입니다. 실제 연결 수와 실행 가능 상태는 설정 변경에 따라 달라지므로, 이 문서는 승인 개수의 근거가 아닙니다. 중복 출처는 여러 유형에 연결할 수 있습니다.

| 유형 | 생성 근거 승인 수 | 활성 자동 라우팅 출처 |
|---|---:|---|
| 유형 | 후보 발견 출처 원칙 |
|---|---|
| 소식 `news` | 종합 애니 뉴스·배급/방영 공지·보도자료 피드에서 발견하고, 발표 주체의 원문 링크를 함께 기록 |
| 행사 `event` | 행사 일정·애니 뉴스·주최자 보도자료에서 발견하고, 주최자/장소의 원문에서 기간·국가·장소 확인 |
| 작품 가이드 `guide` | 신뢰 가능한 작품 카탈로그·백과형 출처에서 발견 및 교차 확인 |
| 인물 `people` | 애니 전문 뉴스·인터뷰·제작사 발표에서 발견하고 인터뷰/발표 원문 연결 |
| 굿즈 발매 `goods` | 상품 전문 매체·상점/제조사 보도자료에서 발견하고 판매/제조 주체 원문 연결 |
| 비하인드 `behind` | 제작 인터뷰·메이킹·업계 매체에서 발견하고 인터뷰·제작 주체 원문 연결 |
| 리뷰·분석 `review` | 검토된 애니 전문 리뷰 매체의 편집 콘텐츠를 출처로 사용 |
| 유머 `humor` | 승인된 공개 커뮤니티 API에서 주제 신호만 수집하며 사실 근거와 분리 |
| 캐릭터 `character` | 작품 카탈로그·백과형 출처 및 확인 가능한 공식 설정 자료 연결 |
| 큐레이션 `curation` | 투표·평점·편집형 랭킹 출처의 표본과 집계 기간을 함께 기록 |
| 음악 `music` | 음반사·음악 전문 매체·배급사의 발매/공연 공지에서 발견하고 원문 연결 |

유형별 현재 승인 수는 고정 표로 간주하지 않습니다. 아래 실행 명령과 라이브 preflight 결과를 확인하고, `terms_review` 후보는 검증 전까지 자동 라우팅하지 않습니다. 현재 일부 유형은 이 원칙에 맞는 활성 후보 발견 출처가 충분하지 않을 수 있으므로, 그 공백은 새 매체를 검증해 채워야 합니다.

## 실행과 검증

`uv run ani-menu source-routing`은 연결 출처 수, 자동 요청 승인 수, 생성 근거 승인 수를 분리해 표시합니다. `uv run ani-menu discover --content-type guide --work-title Naruto`처럼 작품 제목을 주면 Kitsu·Wikipedia API와 ANN 검색에서 그 작품의 상세 후보를 찾습니다. Wikipedia API 요청은 프로젝트 저장소를 식별하는 User-Agent를 사용하고, 후보별 상세 페이지 하나만 읽습니다. `uv run pytest tests/test_source_registry.py tests/test_reference_sources.py -q`에는 유형별 생성 근거 자동 출처가 3개 미만이거나 참조 수집기가 깨지면 실패하는 검사가 있습니다. 이 검사는 라우팅·응답 구조를 보장하지만, 모든 작품명에 항상 좋은 후보가 나온다는 뜻은 아닙니다. 실제 생성 전에는 개별 항목의 제목, 작품 ID, 원문, 기간, 이미지 권리를 다시 검증해야 합니다.

커뮤니티 토론·밈은 별도 정책으로 취급합니다. 작품명을 주면 해당 작품 태그 타임라인을 우선 조회하고, 공개·비민감 원글의 짧은 텍스트만 익명화해 30일간 소재로 씁니다. 답글·부스트·봇 태그·계정 정보·미디어는 저장하지 않고, 생성물은 원문을 인용/복제하지 않는 요약·재구성으로 제한합니다. 이 소재는 사실 근거가 아니며, 토론·예측은 의견임을 드러냅니다.
