# 유형별 크롤러 에이전트

## 에이전트 수와 책임

상위 역할은 총 13개다.

- 유형별 크롤러 11개: `news`, `event`, `guide`, `people`, `goods`, `behind`, `review`, `humor`, `character`, `curation`, `music`
- 기존 콘텐츠 생성 에이전트 1개: `agents/content_generation/`
- 기존 독립 검수 에이전트 1개: `agents/reviewer/`

정보·유머·이미지 디렉터리는 재사용되는 수집/처리 기능이다. 별도 상위 크롤러 역할로 세지 않으며, 기존 생성기나 검수기를 복제하지 않는다. 유형별 크롤러는 공통 수집기와 유형별 출처 매핑을 사용한다.

## 실행 및 적재

유형별 후보 점검·적재만 할 때는 discover를 사용하고, 수집부터 통과 콘텐츠 적재까지 전체 파이프라인을 실행할 때는 다음 명령을 사용한다.

    uv run ani-menu crawl-type --content-type event --limit 10

이 명령은 해당 유형 크롤러로 후보를 수집·적재한 뒤 후보별로 원문 재수집, 인용문 기반 팩트 추출, 이미지 큐레이션, 기존 콘텐츠 생성 및 독립 검수 그래프를 실행한다. 비유머 유형은 기존 crawl-generate의 검증·중복·수정/탈락 규칙을 그대로 사용한다. 유머는 자동 승인된 trend_only 출처의 아이디어를 사실 검증 없이 의견·토론 신호로 처리해 동일 생성·검수 그래프에 전달한다. 통과 결과만 기존 피드 대기열에 저장한다. 후보별 결과와 실행 요약은 output/crawl_runs/<type>/<UTC 실행시각>/에 기록된다. 작품 지정 검색이 필요한 캐릭터 유형은 --work-title을 함께 전달한다.

유형별 후보 수집은 다음 명령으로 실행한다. 후보는 검증된 사실이나 승인 콘텐츠가 아니라 `discovery_only` 또는 `trend_only` 신호로 저장된다.

```powershell
uv run ani-menu discover --content-type event --limit 20
```

`--content-type`에 11개 유형 코드 중 하나를 지정하면 해당 유형의 크롤러 역할이 선택된다. 유형을 생략하면 기존 공통 발견 경로를 사용한다. 유형별 크롤러는 해당 유형에 매핑된 출처 중 승인 상태·수집 어댑터·역할이 모두 맞는 출처만 allowlist로 전달한다. 수동/차단/검토 대기 출처는 요청하지 않는다.

유형별 실행 그래프는 `사전 출처 검사 → 후보 수집 → 유형 품질 게이트 → 후보 적재 → (설정 시) 원문 페이지/이미지 캡처` 순서다. 품질 게이트는 출처 매핑, 출처 역할, HTTPS, 제목, 후보의 유형 태그를 확인하고 중복 URL을 제거한다. 유머는 trend 출처만 허용하고, 인물/캐릭터처럼 작품명이 필요한 수집은 `--work-title` 없이는 실행하지 않는다. 유형별 필수 신호는 원문 캡처에 진단용으로 남기며, 광범위한 정규식만으로 후보를 사실로 승인하지 않는다.

공식/편집/참고 HTML 출처에서 이미지 캡처를 켜면 후보와 같은 원문 페이지에서만 이미지를 모아 기존 `image_curator`에 전달한다. 이미지의 출처·권리·robots·다운로드 검사를 그대로 적용하고, 커뮤니티 이미지나 다른 후보 페이지의 이미지를 섞지 않는다. `--no-capture-images`는 이미지 다운로드 없이 후보 수집 경로만 시험할 때 쓴다.

```powershell
uv run ani-menu discover --content-type event --limit 20 --no-capture-images
uv run ani-menu discover --content-type event --limit 20 --capture-images
```

CLI 결과의 `source_run_results`에는 출처별 시도 여부, 결과 상태, 후보 수, 오류가 담긴다. 따라서 사전 등록/승인 수와 이번 실행에서 실제 요청을 보낸 출처 수를 구분해 확인할 수 있다.

## 새 출처 후보 발굴

개별 글 후보(`discovery_candidate`)와 새 사이트 후보(`source_candidate`)는 별도 DB 레코드다. 유형 크롤러가 원문 페이지를 캡처하면 기사 본문의 미등록 외부 링크에서 새 호스트 후보를 만들고, 실행당 최대 3개 호스트를 대상으로 홈페이지·robots·유형별 목록 링크·본문 추출을 시험한다. 통과한 유형만 `sources.json`과 `source_type_map.json`에 `role=discovery`로 등록되어 다음 실행부터 후보 수집에 참여한다. `source-discover`로 별도 실행할 수 있고, 상태는 `source-candidates`로 확인한다.

자동 승격은 해당 사이트가 후보 발견용으로 작동하는지 확인하는 단계다. 발견 사이트의 글을 사실 근거로 자동 승인하지 않는다. 생성 근거는 활성 1차/허용된 편집·참고 출처에서 다시 수집하고 검증해야 한다. 실패한 사이트 후보는 오류와 유형별 검증 결과를 보관하며 자동 재시도하지 않는다.

기본 로컬 적재 DB는 `data/ani_menu_local.sqlite3`이다. DB backend 설정에 따라 PostgreSQL을 사용할 수도 있다. 크롤링 후보 적재는 콘텐츠 생성 실행과 별개다.

## 수집 테스트 결과 (2026-10-24)

각 11개 유형의 discovery-only 경로를 실제 실행했고, 후보는 기존 SQLite DB에 적재했다. 당시 반환된 후보 수는 `news 5`, `event 5`, `guide 2`, `people 3`, `goods 2`, `behind 0`, `review 5`, `humor 5`, `character 0`, `curation 5`, `music 5`였다. 같은 날 캐릭터 유형은 작품명을 지정한 경로도 시험했고, `Naruto`에서 후보 5건을 발견·적재했다. 이 수치는 현재 이미지 캡처 단계까지 포함한 새 그래프의 실수집 결과가 아니라, 해당 날짜 discovery 경로의 기록이다.

비하인드 0건은 이번 목록 수집 실행에서 후보가 없었다는 뜻이며, 출처 등록이나 유형 역할이 없다는 뜻은 아니다. 캐릭터 데이터는 작품명 검색 경로가 필요하다. 일부 출처는 robots.txt 확인에서 HTTP 403을 반환했으며 해당 출처를 우회하지 않았다. 이 결과는 한 번의 라이브 수집 확인이지, 모든 출처의 지속 가용성 보증은 아니다.
