# 출처 자동수집 검증 기록

검증일: 2026-10-21
상태: 1차 기술 점검. **검증 완료/운영 허용 목록이 아님.**

## 분류 대상 콘텐츠 유형

`news` 소식 · `event` 행사 · `guide` 작품 가이드 · `people` 인물 · `goods` 굿즈 · `behind` 비하인드 · `review` 리뷰 · `humor` 유머 · `character` 캐릭터 · `curation` 큐레이션 · `music` 음악

한 출처는 여러 유형에 연결될 수 있다. 따라서 유형별 연결은 중복을 허용하되, 출처 자체의 수와 유형-출처 연결 수는 별도로 센다.

## 1차 확인 범위와 결과

현재 `config/sources.json`에는 46개 레코드가 있다. 그중 구체적인 URL이 있고 `rss` 또는 `html` 방식인 비커뮤니티 후보 37개를 낮은 빈도로 점검했다. 게시판 수집 후보, 수동 방식, 정책/설정 보류(API·YouTube 포함) 9개는 이번 본문 요청에서 제외했다.

- 34개는 robots 확인 뒤 URL이 HTTP 200으로 응답했다(이 중 RSS 2개).
- AmiAmi는 robots 응답은 있었지만 대상 페이지가 403이었다.
- 루리웹은 연결 시간 초과로 robots/본문을 확인하지 못했다.
- Reddit은 robots 규칙이 대상 경로를 허용하지 않아 본문 요청을 하지 않았다.
- robots.txt 404는 허가로 간주하지 않는다. 사이트에서 수집 규칙을 찾지 못했다는 뜻일 뿐이다.
- AnimeSchedule·PR TIMES RSS는 기존 수집기 파싱 실행에서 각각 4건·5건, 오류 없이 총 9개의 **미검증 후보**를 반환했다. PR TIMES RSS 응답의 전체 엔트리 수는 애니메이션 관련 후보 수가 아니다.

HTTP 200은 네트워크 접근성만 확인한다. 이 점검만으로는 목록 파서가 유효한 항목을 안정적으로 추출하는지, 사이트 약관이 자동 수집/LLM 입력/저장을 허용하는지, 이미지 사용이 허용되는지 검증되지 않는다. 그러므로 새 출처를 `active`로 승격하지 않았다.

## 현재 레지스트리의 분류 공백

레지스트리에는 기존의 단일 `category` 값(예: `official_news`, `goods`, `community_trend`)이 있지만, 아래 11개 서비스 콘텐츠 유형을 나타내는 `content_types[]`는 없다. 기존 `category`를 새 유형으로 자동 치환하면 오분류할 수 있어 보류한다.

후보를 정식 유형별 출처 목록에 넣기 전에 각 출처별로 다음을 채우고 테스트한다.

| 항목 | 통과 기준 |
|---|---|
| 유형 연결 | 실제 제공 정보에 근거해 11개 코드 중 하나 이상 지정 |
| 자동 접근 | 피드/API/공개 목록 URL 응답, robots 및 리다이렉트 확인 |
| 추출기 | 실제 제목·원문 URL·날짜 등 허용 필드를 반복 추출하고 샘플 검수 |
| 사용 조건 | 자동 요청, LLM 입력, 저장/보존 조건 확인. 확인 전에는 활성화하지 않음 |
| 권리/최소화 | 이미지·본문 복제와 사실 메타데이터 수집을 분리하고 필요 최소 필드만 저장 |
| 작품/지역 | 작품 관련 출처는 정확한 `menu_work_id`; 행사만 개최 국가를 별도 지정 |

## 다음 검증 단계

1. `EXPANDED_SOURCE_CANDIDATES.md`와 `CONTENT_TYPE_SOURCE_CATALOG.md`의 후보를 유형별로 정규화하고, 같은 출처의 여러 유형 연결을 보존한다.
2. URL이 포괄적이거나 구체적인 자동수집 경로가 없는 후보는 `URL 미정`으로 남긴다. 근거 없이 임의의 RSS/API 주소를 만들지 않는다.
3. 각 구체 URL에 대해 접근/robots → 유형별 추출기 → 반복성/샘플 검수를 진행한다. 커뮤니티 등 보류된 후보는 정책 확인 전 본문을 요청하지 않는다.
4. 기술 검증과 사용 조건이 모두 통과한 유형-출처 연결만 정식 레지스트리 및 활성 수집 대상으로 등록한다. 실패·미확인 후보는 사유와 함께 보류 상태로 유지한다.

## 새 후보 1차 기술 점검

후보 문서 3개(`EXPANDED_SOURCE_CANDIDATES.md`, `CONTENT_TYPE_SOURCE_CATALOG.md`, `SOURCE_OVERVIEW.md`)의 유형 표를 교차해 재점검했다. 같은 URL이 여러 유형에 연결되면 각 유형 연결을 보존하고 URL 네트워크 검사는 한 번으로 계산했다.

- 후보 문서 표에서 추출한 유형-URL 연결: **122개** (기존 93건의 후보 레코드 수와는 집계 단위가 다름)
- 고유 URL: **95개**
- 기존 실행 설정과 URL이 정확히 같은 항목: **7개**
- 정책·API 문서 등 수집 엔드포인트가 아닌 참고 링크: **2개**
- 새로 점검한 구체 수집 후보 URL: **86개**
- robots 확인 후 HTTP 200: **77개**; HTTP 200 외 응답: **1개**; robots 403/429 등으로 본문 요청을 건너뛴 URL: **8개**
- 기존 HTML 목록 추출기로 한 건 이상 후보 링크를 뽑은 URL: **49개**. 30건 제한 내 샘플이며, 후보가 실제 해당 유형에 맞는지 아직 품질 검수하지 않았다. 0건은 전용 어댑터가 필요하거나 개별 상세 페이지라 목록 추출 대상이 아닐 수 있다.

유머 표에는 Reddit·Bluesky의 정책/API 문서 링크만 있고, 커뮤니티 자동수집에 사용할 구체 API/피드 URL은 정의되어 있지 않았다. TheQoo·DCInside·Arca.live·FMKorea는 robots만 확인하고 게시판 본문은 요청하지 않았다: 각각 200(AI/봇 관련 규칙 포함), 200(AI 봇 제한 규칙 포함), 403, 200(제한 규칙 포함). 따라서 유머 자동수집은 **미검증/보류**이며, 정책 문서 링크를 수집 출처로 세지 않는다. Reddit은 이전 점검에서 대상 경로가 robots에 막혀 본문을 요청하지 않았다.

이 86개 검사는 접근성과 일반 목록 추출기의 1차 신호일 뿐이다. robots.txt 404 또는 허용 응답은 이용 허락이 아니며, 200/추출 후보가 있어도 약관·AI 입력·저장 조건 및 유형별 정확도가 통과한 것이 아니다. 새 URL은 아직 정식 실행 레지스트리나 활성 수집 대상으로 승격하지 않았다.

### 후보 93개 URL 재실행 점검

2026-10-21에 세 후보 문서의 유형별 표에 실제 링크로 기재된 URL을 정규화해 다시 검사했다. 한 URL이 여러 유형에 있으면 유형 연결은 각각 세고, 네트워크 검사는 URL당 한 번 수행했다. 커뮤니티는 robots 차단을 우회하지 않았다.

- 고유 후보 URL: **93개**; 유형-URL 연결: **120개**
- robots 확인 후 현재 기본 목록 파서가 기사 후보를 1개 이상 추출: **58개 URL** (상한 30개/URL, 총 1,068개 후보 링크)
- 접근은 됐지만 해당 파서가 후보를 뽑지 못함: **23개 URL**
- robots endpoint에서 401/403/429 등으로 확인 불가: **9개 URL**
- 대상 URL HTTP 403: **2개 URL**
- robots가 해당 경로를 명시적으로 불허: **1개 URL**

이 수치는 **기술적 1차 결과**다. 후보 제목이 실제 표에 적힌 콘텐츠 유형에 맞는지, 같은 페이지에서 반복적으로 안정 추출되는지, 원문/LLM 입력·보관 조건이 허용되는지까지 확인한 결과가 아니다. 특히 일반 홈페이지에서 링크가 뽑힌 것만으로 해당 링크가 애니메이션 관련 기사라고 볼 수 없다. 따라서 58개를 곧바로 모두 `active`로 켜지는 대신, 다음 구현 단계에서 유형별 샘플 검수와 허용 필드·출처 역할을 붙여 등록해야 한다.

### 유형 연결 상태

95개 URL은 출처가 아니라 URL 후보 수이고, 일부는 같은 사업자/도메인의 복수 목록이다. 각 유형 연결과 자동수집 판정은 다음 단계에서 검증 결과를 대조한 뒤 등록한다. 특히 `humor`는 정확한 자동 피드/API가 없고, `character`/`guide`의 많은 URL은 목록이 아닌 개별 자료 페이지라 일반 기사 목록 파서로는 충분하지 않다.

### 유머 공개 API 3개 연결 시험

2026-10-21에 Mastodon 세 인스턴스의 공개 `#anime` 태그 타임라인 API를 각각 한 번 호출했다. 세 곳 모두 HTTP 200을 반환했고, 응답 JSON에서 게시물 본문·계정·이미지는 저장하지 않고 해시태그 빈도만 집계하는 파서가 각 1개 주제 신호를 만들었다. `parse_mastodon_tag_timeline` 단위 테스트도 추가했다.

| 인스턴스 | endpoint | 연결/파싱 | 자동 요청 상태 |
|---|---|---|---|
| Mastodon.social | `/api/v1/timelines/tag/anime` | HTTP 200 / 태그 집계 성공 | `terms_review` — 비활성 |
| Mastodon.online | `/api/v1/timelines/tag/anime` | HTTP 200 / 태그 집계 성공 | `terms_review` — 비활성 |
| mstdn.jp | `/api/v1/timelines/tag/anime` | HTTP 200 / 태그 집계 성공 | `terms_review` — 비활성 |

세 건은 기술상 자동 요청이 가능한 후보이며, 승인된 자동수집 출처 세 건이라는 뜻은 아니다. Mastodon API 문서는 공개 타임라인 접근이 인스턴스의 공개 미리보기 설정에 따라 달라질 수 있다고 안내한다. 인스턴스별 약관·AI 입력 범위가 확인되기 전까지 이 세 출처는 `trend_only`로 승격하지 않는다. 따라서 현재 `humor`의 승인된 자동 요청 수는 여전히 0이다.

### 2026-10-23 후속 검증 및 남은 공백

- 실제 현재 `trend_only` 등록 상태의 Mastodon 세 인스턴스를 작품별 태그 타임라인으로 조회했다. 나루토 `#Naruto` 타임라인은 HTTP 200이었고, 40개 중 30개에 `bot` 태그가 있었다. 봇 태그 제외, 공개/민감도/원글 필터, 영어·한국어·일본어 토론 신호와 최소 반응 기준을 추가했다. 세 인스턴스 실수집 결과는 태그 요약 3건과 익명 게시물 소재 1건, 수집 오류 0건이었다. 원문 후보는 30일 뒤 만료되며 본문을 복사해 콘텐츠로 쓰지 않도록 생성 지침을 강화했다.
- `collect_candidates(content_type="behind")` 실수집은 0건/오류 0건이었다. 현재 활성 출처는 일반 뉴스 목록 경로라 제작 인터뷰를 반환하지 않았다. 히로아카 공식 인터뷰 경로는 검색 인덱스에서 확인했으나 직접 HTTP 요청은 403이어서 활성화하지 않았고 접근 제한을 우회하지 않았다. 뒤의 콘텐츠 유형은 공식 제작진 인터뷰를 안정적으로 찾는 자동 후보 경로가 확보될 때까지 실운영 가능으로 간주하면 안 된다.
- 이미지 메타데이터 필드(`visible_text`, `detected_languages`, `depicted_entities`)는 있으나 픽셀 OCR/비전 분석이 실행되지 않는 점을 확인했다. 현재 `asset_kind`·인물 표시는 URL 및 alt-text 기반 추정이다. 빈 OCR 값은 글자 없는 이미지라는 뜻이 아니며, 자막 제거와 캐릭터 단위 이미지 매칭은 미해결이다. 기존 GPT 모델에 이미지를 보내면 API 비용이 증가하므로, 무료 로컬 OCR 엔진을 선택하거나 이미지 분석 비용을 승인하기 전에는 이미지 비전 호출을 켜지 않는다.
