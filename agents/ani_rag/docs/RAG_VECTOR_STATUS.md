# RAG 벡터 근거 상태

확인일: 2026-11-23

## 현재 상태

- 기존 RAG 근거 전체의 벡터 색인이 완료됐다: 청크 734,432개, 고유 벡터 704,063개.
- 임베딩 모델은 `text-embedding-3-small`, 차원은 1,024다. sidecar 파일은 약 4.01 GB다.
- 색인 완료 시각은 2026-11-19다. 각 청크의 벡터 누락은 0개로 확인했다.
- 크롤러와 콘텐츠 생성 런타임은 이 sidecar를 읽기 전용으로 열고 같은 임베딩 모델로 검색한다. 관련도 점수는 근거를 찾는 기준이며 사실 판정 점수는 아니다.
- 새 `reference_fact`가 DB에 들어오면 별도 벡터 인덱서가 기본 5분 간격으로 [`update_vector_evidence_index.py`](../scripts/update_vector_evidence_index.py)를 실행해 sidecar를 갱신하도록 준비했다. 단독 실행은 [`run_vector_indexer.py`](../scripts/run_vector_indexer.py), 전체 실행은 [`manage_workers.ps1`](../scripts/manage_workers.ps1)로 제어한다.

## DB와 백업

2026-11-23에 실제 임시 SQLite DB에 준비된 0002–0006 마이그레이션을 추가 적용했다. 변경 전 온라인 백업은 다음 위치에 보관했다.

`%LOCALAPPDATA%\Temp\ani_rag_live_backup_20261123\ani_rag_live_20261111_pre_migration.sqlite3`

마이그레이션 뒤 주요 건수는 그대로였다: 문서 642,181개, 청크 331개, 작품 연결 1,131,901개, 이미지 2,509개, 초안 129개. 이번 작업은 표와 색인 상태를 추가했고 기존 자료 행은 바꾸지 않았다. DB 파일은 약 3.13 GB다.

## 동작 확인

임시 복사본에서 다음 한 건 흐름을 확인했다.

`MCP 검색·원문 읽기 → 기존 작품 ID 확인 → 원문 URL을 뺀 RAG 근거 대조 → 초안 생성 → 별도 검수 통과`

실제 DB에는 이 시험 초안을 저장하지 않았다. 후보 원문 자체가 자기 주장을 뒷받침하는 근거로 다시 검색되지 않도록 URL 제외도 추가했다.

## 아직 자동으로 돌지 않는 부분

- 반복 검색은 [`automatic_plans.json`](../config/automatic_plans.json)에 설정했다. 크롤러를 시작하면 RAG 전용 작품 스냅샷의 모든 작품·7개 유형과 승인 출처 요청을 순환 예약한다.
- Firecrawl MCP는 제한된 웹 검색과 한 페이지 읽기를 한다. 인터넷 전체를 순회하거나 다음 검색 페이지로 넘기는 기능은 현재 연결에서 확인되지 않았다.
- 새 참고자료의 벡터 갱신은 수집 후 별도 실행해야 한다.
- 검색 계획은 작품 ID 오름차순으로 7일에 걸쳐 배치된다. 계획 하나가 검색어 대안 및 여러 후보 읽기로 확장될 수 있어 7일은 계획 순환 주기이지 모든 원문을 빠짐없이 읽는 보장은 아니다.
- 같은 Firecrawl MCP 세션의 URL 검색·웹 검색·후보 읽기는 순차 처리한다. 별도 Wikidata 서버의 요청 하나만 겹쳐 실행하며, 동시 요청 수를 무제한으로 늘리지는 않는다.
- Firecrawl은 제한된 결과만 제공하며 다음 페이지 커서는 없다. 따라서 인터넷 전체를 빠짐없이 순회하지 않는다.
- Windows 재부팅 때 자동으로 시작하는 설정은 두지 않았다. 전체 작업은 `scripts/manage_workers.ps1 start`로 시작해야 한다. 이번 작업에서는 워커를 실행하지 않았다.

워커는 이번 작업에서 시작하지 않았다. 기존 일정 체크포인트는 보존하고 새 7일 일정용 체크포인트 경로를 사용하도록 했다. 기간형 프로젝트 파일과 DB는 수정하지 않았다.
