# RAG 작업 상태

## 흐름

`승인된 참고자료 수집 → 근거 저장·벡터 색인 → MCP 웹 검색 → 후보 페이지 읽기 → 작품 연결 → 후보 URL을 제외하고 RAG 근거 대조 → 기준 통과 시 콘텐츠 생성 → 별도 검수`

웹 검색 결과는 주제를 찾는 후보일 뿐 사실 근거가 아니다. 페이지 원문도 RAG 근거를 대신하지 않는다. 검수 결과에 따라 통과, 수정 후 재생성, 탈락 보관으로 나뉜다. 수집·생성·검수는 각각 별도 프로세스로 실행할 수 있다.

## 확인된 준비

- 전체 기존 근거의 벡터 색인이 만들어졌고, 크롤러·생성 런타임이 이를 읽는 연결이 있다.
- MCP 웹 후보 검색부터 작품 연결, RAG 비교, 생성, 독립 검수까지 임시 DB 복사본에서 한 건 통과를 확인했다.
- 웹 후보의 자기 URL을 RAG 검색 결과에서 제외한다.
- Wikidata의 실제 도구 형식에 맞춘 구조화 MCP 어댑터를 크롤러 실행 경로에 연결했다.
- 실제 임시 SQLite DB에 추가 마이그레이션을 적용하기 전 온라인 백업을 만들었고, 기존 주요 자료 건수는 유지됐다.
- 루트 `catalog/`와 확인된 임시 작품을 ID 오름차순으로 순환한다. 검색 계획은 7일 주기로 고르게 배치한다. 중지 뒤 밀린 계획은 한 번에 하나씩 순서대로 큐에 넣는다.
- Firecrawl을 사용하는 수집·웹 검색·후보 읽기는 같은 MCP 세션에서 차례로 실행한다. 별도 Wikidata 세션 작업은 Firecrawl 작업 하나와 겹쳐 실행한다.
- Firecrawl에서 크레딧·인증·호출 제한 오류가 확인되면 해당 크롤러 프로세스의 Firecrawl 호출을 멈춰 같은 오류를 반복하지 않는다. 크레딧 충전 또는 제한 해제 뒤 크롤러를 다시 시작해야 한다.
- 새 참고 근거를 5분마다 확인해 벡터 sidecar에 추가하는 별도 인덱서 실행 파일과, 수집·생성·검수·색인 작업을 각각 숨김 프로세스로 시작·중지·확인하는 Windows 스크립트를 만들었다.

## 운영 시작 전 남은 일

1. 7일은 전체 계획을 한 번 도는 목표 주기다. 한 계획이 검색어 대안과 검색 결과 페이지 읽기로 이어질 수 있으므로 실제 MCP 호출 수와 비용은 계획 수보다 많다.
2. 서버에서도 루트 `catalog/menu_works.csv`와 `catalog/menu_work_entries.csv`를 두 에이전트에 읽기 전용으로 제공한다.
3. Firecrawl 검색은 한 번에 제한된 후보만 제공한다. 다음 페이지 커서가 없어 인터넷 전체를 빠짐없이 훑는 방식은 아니다.
4. Windows 자동 시작은 설정하지 않았다. `scripts/manage_workers.ps1 start`를 실행해야 네 작업이 시작되고, `stop` 또는 `status`로 관리한다. 이번 작업에서는 실제 워커를 시작하지 않았다.

작업을 시작하면 크롤러가 전체 RAG 작품 스냅샷을 ID 오름차순으로 순환해 근거 수집과 웹 후보 검색을 예약하고, 생성·검수는 각자 자기 큐를 계속 처리한다. 인덱서가 새 참고자료를 벡터 색인에 반영한다. 운영 시작과 중지는 위 스크립트로 직접 제어한다.
