# 일일 생성 비활성 배포

`compose.inactive.yaml`은 이미지 반입과 비활성 컨테이너 준비용 **독립 구성**이다.
기존 `compose.runtime.yaml`·`compose.approved.yaml`과 합치지 않는다.

- Worker·Controller·importer 명령은 모두 `--help`다. 자동 수집·생성·적재를 실행하지 않는다.
- 네트워크는 `none`, 키·실제 DB/Redis 주소·호스트 파일 연결·공개 포트는 없다.
- importer의 `offline_not_used` 주소는 도움말의 Settings 검사에만 필요하며 실제 대상이 아니다.
- 이미지의 healthcheck를 끄고, 비 root 사용자·읽기 전용 파일시스템·`restart: no`를 사용한다.
- 최종 컨테이너는 `created` 또는 종료 상태로 둔다. 기존 API·추천·작업 DB·Redis·이력 파일을 바꾸지 않는다.

검증된 소스로 이미지를 빌드하고, `inactive.env.example`의 두 값만 정확한 로컬 이미지 ID
(`sha256:` + 소문자 16진수 64자리)로 채운 별도 파일을 준비한다. 예산·날짜·승인 해시나
자격증명을 이 파일에 넣지 않는다. Compose 자체는 태그를 거절하지 않으므로 배포 검사에서
두 값의 형식과 `docker image inspect` 결과를 대조해야 한다. 렌더링된 설정도
`test_inactive_deploy.validate_inactive_config(config, image_ids)`로 같은 계약을 검사할 수 있다.

아래 회귀는 합성 이미지 ID만 사용한다. Docker Compose CLI로 설정을 렌더링하며 daemon,
실제 이미지, 네트워크, DB, API 키는 사용하지 않는다.

```text
python -m unittest discover -s deploy/daily-generation -p test_inactive_deploy.py -v
```

도움말을 확인할 때도 이 독립 구성의 네트워크·mount 금지 조건을 유지한다. 컨테이너를
준비할 때는 `create`만 사용하고 자동 시작·재시작을 설정하지 않는다. 실제 활성화는 별도의
실행 날짜·등록된 출처 범위·기존 이력·승인된 정책을 확인한 뒤 검토한다. 준비된 이미지가
있다는 사실만으로 유료 실행이나 서비스 적재가 승인된 것은 아니다.

## 서비스 노출 기한 (2026-11-27)

RAG 혼합 일정의 `feed_valid_days`를 명시적으로 `null`로 설정하면 Agent의 기한을 유지한다.
Agent 결과에도 기한이 없으면 임의 TTL을 만들지 않는다. 기존 정수 정책 및 정책 SHA 검증은
유지하며, 새 콘텐츠는 운영자 승인 전까지 비노출이다. 기존 데이터 보존·추천 적용 규칙은
[노출 기한 계약](../../docs/CONTENT_EXPIRY_POLICY_2026-11-27.md)을 따른다.

## Agent 검수 통과 20건 기준 실행 (2026-11-27)

기사와 RAG가 합산하여 **하루 Agent 검수 통과 콘텐츠 20건**에 도달하면 종료한다.
새로 승인한 정책은 시도 횟수 상한을 없앤다. `40`을 큰 숫자로 바꾸는 방식이 아니라
`max_attempts: null`로 명시하며, 실패·보류·반려·생략 횟수와 실제 사용 비용은 계속 기록한다.
검수 통과 수는 기존 일일 이력에서 계산하므로 이미 통과한 콘텐츠도 20건에 포함된다.

호스트 일정 정책과 Worker의 일일 정책은 버전 번호가 다르다.

| 구분 | 이전 정책 | 새 정책 |
| --- | --- | --- |
| 호스트 `schedule-policy.json` | v1/v2, `max_attempts: 40` | v3, `max_attempts: null`, `success_target: 20` |
| 새 날짜의 Worker `daily_policy` | v3, `max_attempts: 40` | v4, `max_attempts: null`, `success_target: 20` |
| 새 날짜의 실행 `config.max_new_jobs` | 이전 누적 횟수 + 40 | `null` |
| RAG 접수 영수증 | v1, `attempt_ordinal` 1~40 | v2, 양의 순번, `limit_revision_sha256` 필수 |

새 일일 계획은 `menu_worker.daily_resume --success-target-only`로 명시한다. 이 플래그를
주지 않은 기존 v3 계획은 원래 40회 제한으로 재현된다. `scheduled_run.py`는 새 호스트 정책에서
새 날짜를 준비할 때 플래그를 붙이며, 이미 봉인된 계획에는 소급해서 붙이지 않는다.
`schedule-policy.example.json`은 새 정책의 **비활성 준비 예제**다. 예제의 해시·출처·경로를
실제 검토 값으로 채워도 `rag.enabled: false` 상태는 유료 실행 권한을 부여하지 않는다.

- 여러 작품·유형 배분과 **한 건씩 순차 생성**을 유지한다. 같은 기사·RAG 후보는 기존
  중복 방지 이력에 따라 건너뛰며, 할당량을 채우기 위해 실패 후보를 재생성하지 않는다.
- 한국시간 다음 날 00:00 경계와 작업별 1,500초 제한을 유지한다. 새 작업에 필요한 시간이
  남지 않으면 종료한다. 후보가 소진되면 정해진 간격으로 다시 수집하고, 새 후보가 없으면
  자정에 종료할 수 있다. 하루 20건을 반드시 생산한다는 의미는 아니다.
- 생성 시작 여부·사용 비용·결과 봉인이 불확실하면 기존처럼 중단한다. 시작 전 실패와
  완전한 0비용이 증명되는 A08 유형만 실패 이력과 사용한 시도를 보존하면서 다음 후보로 간다.
  비용 누락을 무료로 처리하거나 과거 미확정 비용을 삭제하지 않는다.
- Agent 검수 통과는 서비스 공개 승인이 아니다. 적재 후 상태는
  `pending_review / needs_review / checking`이며, 운영자 승인 후 공개한다.

### 이미 실행한 날짜의 한도 변경

2026-11-27 전환 기준은 **기존 기록 32개, 당일 9회 시도·6건 통과**다. 이 경우 추가 목표는
14건이며 20건을 새로 생성하는 것이 아니다. 원래 v3 계획·정책·config·32개 기록·seen·
생성/비용/검수 영수증·적재 봉투는 그대로 둔다. A08 복구 영수증도 다시 만들지 않는다.

1. 자동 실행과 Worker가 정지하고 큐가 빈 상태에서 원본 checkpoint·journal·작업 DB·산출물을
   백업한다. 진행 중인 작업이 없어야 하며 기존 일일 시도·통과 수와 원본 해시를 대조한다.
2. 공통 순수 검증기 `worker/menu_worker/daily_limits.py`의 `build_limit_revision`으로
   한도 변경 승인을 만든다. 원래 일일 정책 SHA, 적용 시작 기록 위치, 이전 records·seen SHA,
   당일 시도·통과 수, 승인 시각·사유, `max_attempts: null`을 함께 고정한다.
3. 검토한 해시와 원본 파일의 CAS 검사가 일치할 때만 `daily_limit_revisions`에 추가한다.
   기존 배열·정책·config를 교체하거나 당일 `start_record_index`를 옮기지 않는다.
   호스트 journal에는 같은 revision SHA를 고정하고 날짜 디렉터리에 원본 JSON을 보관한다.
4. 변경 이후 기록만 `daily_limit_revision_sha256`으로 승인에 연결한다. 기존 기록은
   변경하지 않으며, 재시작·다음 날짜 준비에서도 원본 prefix와 승인 연결을 재검증한다.
5. A08처럼 `reconciled_paused`인 일정은 별도 검증 후 정확한 기존 영수증을 지정한
   `--resume-reconciled`로 재개한다. 한도 변경이나 타이머 활성화만으로 복구 상태를 해제하지 않는다.

이 변경은 작업 DB 스키마나 기존 작업 ID를 바꾸지 않는다. Worker/controller·기사 생성기·
RAG 생성기·importer와 호스트 스케줄러를 호환 버전으로 함께 준비해야 한다. 기존 importer는
v3/40회와 RAG v1만 허용하므로 Worker만 바꾸면 41번째 이후의 정상 결과가 적재 단계에서 막힌다.
RAG 결과 봉투의 native v1 형식은 유지한다. 새 v2 접수는 신규 v4 일자에서 revision 값이
`null`이고, 같은 날 변경에서는 검토된 revision SHA를 담는다. importer는 별도로 승인된
revision JSON·SHA와 이를 대조하며, 기존 6건의 v1 접수·원래 적재 정책도 계속 검증한다.
호스트와 읽기 전용 대시보드에는 같은 `daily_limits.py`를 해시로 고정해 동봉한다.
대시보드는 당일 시도 수를 계속 표시하되 상한과 남은 시도 수는 `null`로 구분한다.

### 무과금 검증 기록

Worker 관련 **122개 테스트와 124개 하위 검사**가 통과했다. 네트워크가 없는 Docker,
읽기 전용 소스, 비어 있는 모델 키로 실행했으며 실제 LLM·서비스 DB 쓰기는 없었다.
40회 미통과 뒤 41번째 통과부터 총 20건을 채우는 흐름, 기존 9회/6건에서 14건 추가 후 종료,
기존 v1/v2/v3의 40회 제한, 중복 방지·순차 배분, 자정·시간 부족·비용 불명확 중단을 포함한다.

격리 PostgreSQL의 기존 A08 회귀 12개와 신규 2개도 **14개 모두 통과**했다. 신규 검사는
기존 40개 실패 작업·시도 원문을 유지한 채 41번째 v2 접수를 처리하는 경우와, 과거 미확정 비용·
A08 영수증·당일 revision을 보존해 다음 v4 일자의 계획/사전 검사/활성화를 검증하는 경우다.
이 수치는 합성 검증 결과이며 운영 콘텐츠 생성 건수나 배포 완료를 의미하지 않는다.

## 이전 횟수 기준 실행 정책 (2026-11-26, 일일 v3)

2026-11-26에 도입한 계획은 일일 정책 v3를 사용한다. 활성화용 Compose와 환경 변수 예제에서 일일 예산과
별도 종료 시각 입력을 제거했다. `--daily-budget-usd`·`--deadline` 없이 계획을 생성하며,
등록된 출처 목록과 실행할 한국시간 날짜·원본 이력 해시·새 체크포인트 경로는 계속 확인한다.

- 여러 작품·뉴스·행사·굿즈가 **하루 최대 40회 시도, 검수 통과 20건 도달 시 종료** 기준을
  공유한다. 생략·반려·실패도 실제 생성 시도로 집계되며, 이전 작업·비용·검수 이력은 보존한다.
- 달러 금액으로 실행을 막는 조건은 새 정책에 적용하지 않는다. 실제 사용량·추정 비용과
  기존 비용 예약은 계속 기록한다. 비용을 확인할 수 없는 결과를 0달러로 취급하지 않는다.
- 날짜별 횟수를 구분하기 위한 **한국시간 다음 날 00:00 경계**와 개별 작업 1,500초 제한은
  유지한다. 새 작업에 필요한 시간이 남지 않으면 그날 실행을 종료한다. 운영자가 별도의
  마감 시각을 정할 필요는 없다.
- 같은 날 재시작해도 저장된 시도·통과 횟수를 이어가며, 계획 변경으로 초기화할 수 없다.
  기존 정책 v1/v2 기록은 원래 예산·시각과 함께 읽고 검증한다. 이전 계획을 재현할 때만
  종전 예산·종료 시각 인자를 함께 사용한다.
- 검수 통과는 자동 공개가 아니다. 기존 적재기는 `pending_review / needs_review / checking`
  상태로 저장하며, 운영자 승인 후 공개한다. 적재 정책·봉투는 기존 v2 형식을 유지한다.

`daily_resume`는 **한 날짜의 계획만** 수행한다. 아래 호스트 실행 관리자
`scheduled_run.py`가 승인된 반복 정책에 따라 날짜별 계획을 만들고 이력을 이어준다.
첫 실행 전에는 새 이미지 반영, 기존 이력·빈 큐·등록 출처·정책 해시 사전 검사와 실제
실행 승인이 필요하다.

자동 수집·유료 생성은 기본 비활성이며 이 문서 변경만으로 실행되지 않는다.

## 매일 반복 실행 연결 (2026-11-26)

`scheduled_run.py`는 호스트에서 기존 Docker Compose 서비스만 관리한다. 생성 Worker에
Docker 소켓이나 서비스 DB 권한을 전달하지 않는다. `schedule-policy.example.json`의
플레이스홀더를 실제 검증 값으로 대체하고, `routes`에는 승인한 등록 출처 목록 전체를
기록한다. 정책의 SHA256은 JSON 키 정렬·구분자 `,`/`:`·UTF-8 형식의 `digest(policy)`이다.
예제의 일부 경로만 남기면 현재 전체 등록 목록과 달라 실행이 차단된다.

```text
python3 scheduled_run.py --policy /absolute/release/schedule-policy.json \
  --reviewed-policy-sha256 REVIEWED_SHA256 --state-root /absolute/existing/state \
  --runtime-env /absolute/private/runtime.env --release-dir /absolute/release
```

기본 명령은 상태를 읽기만 한다. 파일 작성·Docker 실행·LLM 호출·서비스 DB 쓰기가 없다.
`--preflight`는 호스트의 날짜별 계획·정책·환경 파일과 journal을 준비한 뒤 기존 생성기의
작업 이력·빈 큐를 검사한다. 이때 생성 체크포인트·작업 큐·서비스 DB에는 쓰지 않고,
Worker 시작·실제 생성·적재도 하지 않는다. 반복 사전 검사는 같은 계획을 재사용하며
이미 실행을 시작한 날짜의 상태는 바꾸지 않고 검사를 거절한다.
실제 실행은 같은 명령에 `--apply`를 명시한다. 실행 관리자는 매번 다음을 수행한다.

1. 승인 정책·환경 파일·Compose 파일 해시, 최초 원본과 완료한 날짜별 체크포인트 해시 확인.
2. 같은 날짜 완료 시 아무 작업도 하지 않음. 새 날짜이면 이전 체크포인트와 같은 디렉터리에
   `daily-YYYY-MM-DD.json`을 계획하고, `scheduled/YYYY-MM-DD/`에 계획·적재 정책·환경 파일 보존.
3. 등록 출처·한국시간 날짜 경계·통과 20건과 승인된 시도 제한을 확인한다. 새 날짜는 일일 v4,
   기존 날짜는 봉인된 v3와 별도로 승인된 한도 변경 이력을 대조한다.
4. 새 실행은 기존 생성기의 무과금 사전 검사 후 Worker 시작. 재시작은 파일·DB 잠금 하에
   기존 작업 소유권·원본·결과 증거를 먼저 검사. 이미 종료한 작업은 Worker를 다시 시작하지 않음.
5. 한 건씩 순차 생성하여 20건 통과에 도달하면 종료. 기존 40회 정책을 재현할 때만 시도 상한을
   적용한다. 날짜 종료도 허용하되 불확실한 작업이나 비용은 별도 복구 없이 다음 날로 넘기지 않음.
6. 모든 작업 종료와 빈 큐를 확인한 뒤 해당 Worker를 중지하고, 기존 적재기를 `--once --apply`로
   실행. 적재 결과는 검수 대기이며 운영자 승인·자동 공개는 하지 않음.
7. 적재 건수가 통과 건수와 맞으면 그날 완료를 영구 기록. 다음 날짜에는 이 체크포인트를 이어 사용.

파일 잠금과 기존 생성기의 DB 잠금으로 병렬 실행을 막는다. 날짜별 계획은 변경하지 않고
원본·작업·비용·검수 이력을 보존한다. 기존 환경 파일은 소유자만 읽도록 `0600`이어야 한다.
계획과 환경 파일은 호스트만 읽고, UID 10001은 날짜별 inbox와 필요한 적재 정책만 접근한다.
Docker는 `default` context로 고정하며 상속된 `DOCKER_*`·Compose·일일 정책 환경 변수는 제거한다.

`me-nu-daily-schedule.service`와 `.timer`는 설치용 템플릿이다. 타이머는 5분마다 확인하지만
동일 날짜 완료 후에는 추가 생성하지 않는다. 서비스가 실행 중이면 중복 인스턴스를 만들지 않는다.
`/etc/me-nu-daily-schedule.env`에는 다음 **절대 경로와 승인 해시**를 넣는다. 실제 키 값은 넣지 않는다.

```text
DAILY_SCHEDULE_RELEASE_DIR=/absolute/release
DAILY_SCHEDULE_POLICY=/absolute/release/schedule-policy.json
DAILY_SCHEDULE_SHA256=REVIEWED_SHA256
DAILY_SCHEDULE_STATE_ROOT=/absolute/existing/state
DAILY_SCHEDULE_RUNTIME_ENV=/absolute/private/runtime.env
```

설치나 `daemon-reload`만으로 타이머를 활성화하지 않는다. 실제 유료 반복 실행 승인 이후에만
타이머를 시작한다. 중단하려면 먼저 타이머를 비활성화하여 새 날짜 실행을 막고, 진행 중 작업은
원본 체크포인트와 Worker 상태를 확인해 정상 종료 또는 별도 복구한다.

오류는 `scheduled/journal.json`의 `blocked` 상태와 비공개 단계별 로그에 남는다. 비용 누락·
변경된 출처·미완료 작업·적재 오류는 자동으로 재시도하지 않는다. 특히 재부팅이 자정을 지나
전날 결과가 미적재 상태라면 현재 적재기의 당일 정책 규칙을 우회하지 않고 전환을 차단한다.
이때 원본 결과와 작업은 그대로 남으며 운영자가 검증·복구한 후 이어야 한다. 실패 시 기존
Worker가 아직 남아 있을 수 있으므로, 불확실한 진행 작업을 강제 종료하거나 큐를 비우지 않는다.

네트워크 없는 Linux 테스트에서 호스트 실행 관리자 회귀 18건을 확인했다. 사전 검사 후 같은 계획 적용, 이틀 연속 실행,
동일 날짜 반복 호출, 계획 저장·생성 종료 후 재시작, 동시 실행 잠금, 출처 변경 차단,
전날 미적재 차단, 비용 누락 차단, 실제 UID 10001 파일 접근 권한을 포함한다.

## 여러 작품·유형의 순차 배분 이력 (2026-11-25, 정책 v2)

아래는 v2 도입 당시의 구현·검증 기록이다. 현재 새로 승인하는 계획의 시도 제한·예산·시간
입력 규칙은 위의 검수 통과 20건 정책을 따른다.

`main`의 `c62476c`를 기준으로, `menu_worker.daily_resume --registered-routes`를 추가했다.
기존 필수 인자와 함께 실행하면 **계획만** 출력한다. `--preflight`는 읽기 전용 검사,
`--apply`는 정확히 검토한 계획 해시가 있을 때만 실행된다. 예산·실행 날짜·종료 시각은
여전히 별도로 정해야 하며, 기본값이나 반복 Beat 일정은 추가하지 않았다.

- 일일 범위는 활성 공식 HTML 출처 중 기존 작품 ID가 정확히 하나로 연결되고,
  수집 파서와 생성 계약이 지원하는 뉴스·행사·굿즈 조합이다. 현재 7작품·16조합이다.
  원피스는 기존 파서 범위인 굿즈만 포함한다. 범용 출처의 작품을 추측하거나 새 작품을 만들지 않는다.
- 전체 범위를 하나의 일일 정책 v2에 고정한다. `compose.approved.yaml`도 이 선택 인자를
  사용하므로 활성화 전 같은 인자로 계획·사전 검사를 다시 해야 한다.
  기존 v1 단일 경로 계획·작업·비용·검수 이력은 계속 읽을 수 있다. 작업 DB 스키마 변경은 없다.
- 후보가 있는 작품 중 당일 시도가 적은 작품을 우선하고, 유형·출처별 시도 횟수와
  과거 순서를 이용해 배분한다. 후보 없음·일시적인 목록 조회 실패는 다른 경로를 막지 않는다.
  카탈로그 불일치·범위 밖 작품·비용 불명·모호한 발행 상태는 기존처럼 중단한다.
- 생성은 한 건의 완료를 확인한 뒤 다음 한 건을 발행한다. 모든 경로가 **하루 최대 40회 시도,
  검수 통과 20건 목표**, 동일한 비용·종료 시각을 공유한다. 생략·반려도 시도 횟수에 포함한다.
  재시작 시 저장된 기록에서 배분을 복원하며, 같은 날 계획을 바꿔 제한을 초기화할 수 없다.
- 중복 기준은 출처 ID와 정규화 URL이다. 동일 기사가 여러 유형에서 발견돼도 한 번만 처리한다.
  이전 비용 예약과 작업 이력을 보존하며, 검수 통과 결과만 기존 봉투·번들 형식의 v2로 내보낸다.
- 적재 정책 v2의 `routes`는 검토한 일일 계획의 경로 목록을 그대로 복사한다.
  `import-policy.example.json`은 현재 카탈로그 예시이며 승인 자료가 아니다. 날짜·해시·대상은
  실제 계획과 일치해야 한다. 출처·유형·작품 ID가 봉투와 번들 모두 일치해야 적재된다.
  적재 결과는 `pending_review / needs_review / checking`으로 유지하고 자동 공개하지 않는다.

현재는 경로별 최대 20개 후보를 먼저 모아 배분한다. 한 경로 조회는 최대 240초로 제한되어
16개 경로 모두 지연되면 첫 생성 전 수집에 약 64분이 걸릴 수 있다. 게시물 부족·반려·비용·종료
시각에 따라 20건에 못 미칠 수 있으며, 할당량을 채우려고 범위 밖 기사나 중복을 생성하지 않는다.

검증은 모델 키 없는 격리 환경에서 진행했다. 일일/재개/출처 정책 75개, 배분 10개,
설치된 Agent 파서 연결·기존 수집 13개, 비활성 배포 계약 8개를 확인했다.
패키지 테스트의 카탈로그 경로 1곳을 수정하고 해당 7개 출처 테스트를 다시 통과시켰다.
실제 임시 PostgreSQL·Redis·단일 Celery Worker로 3작품/3유형을 처리해 3개 봉투를 만들었고,
중복 요청·중복 메시지의 추가 생성은 0건이었다. 기존 합성 작업 4건도 그대로 보존했다.
백엔드 회귀 373개 및 4개 하위 검사, 별도 Celery 적재 연결 검사 1개가 통과했다.
연결 검사는 dry-run 무변경, 격리 DB 3건 적재, 재적재 신규 0건, 승인 전 피드 0건을 확인했다.
실제 LLM 호출·비용·서비스 DB 접근은 모두 0이며 추천 코드·출처 기본 수집 설정을 변경하지 않았다.

후속 리뷰에서 혼합 목록을 유형 분류 전에 20건으로 잘라, 뉴스 20건 뒤의 굿즈·행사 후보를
놓치는 문제를 확인했다. 일일 경로만 `retain_fetched_candidates`를 사용해 이미 조회한 페이지의
후보를 기존 페이지당 최대 200건 범위에서 유형 분류·정렬까지 보존한다. 이후 원문을 조회하기
전에 요청 한도(최대 20건)를 적용한다. 전체 페이지 탐색은 켜지 않고 기존 시간 제한과 일반
수집 동작도 유지한다.

이 수정은 네트워크·모델 키가 없는 컨테이너에서 Agent 연결·기존 수집 16개, 순차 배분·수집 큐
15개 테스트를 통과했다. 다른 유형 20건 뒤의 굿즈·행사 보존, 요청 5/20건의 원문 조회·반환 상한,
추가 페이지 조회 방지와 페이지당 200건 한도를 확인했다. 신규 테스트의 URL 기대값은 기존
말미 슬래시 제거 규칙에 맞춰 보정했으며, 실제 URL 정규화 규칙은 변경하지 않았다.
