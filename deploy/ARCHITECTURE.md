# Lightsail 아키텍처와 증설 계획

기준일: 2026-10-17. 대상은 팀 테스트 환경이며, 아래 구성은 초기 배포와 향후 확장을 위한 제안이다. 현재 저장소에는 배포용 Docker 이미지·Compose·환경변수 예제가 준비되어 있고, AWS 리소스 생성과 HTTPS 연결은 아직 수행하지 않았다. 실제 실행 절차는 [배포 가이드](README.md)를 따른다.

## 초기 구성

초기에는 **Lightsail 범용 4GB 인스턴스 1대에 API, PostgreSQL, Redis를 함께 실행**한다. 이는 팀 테스트를 시작하기 위한 사양이며, 동시 접속자 수나 처리량을 보장하는 수치는 아니다. 콘텐츠 생성 Agent까지 같은 서버에서 실행하는 것은 이 사양의 전제에 포함하지 않는다. 메모리가 부족하면 범용 8GB로 증설하고, 메모리 특화 플랜은 실제 메모리 사용량을 측정한 뒤 검토한다. 플랜의 제공 사양은 [AWS 인스턴스 번들 안내](https://docs.aws.amazon.com/lightsail/latest/userguide/amazon-lightsail-bundles.html)를 기준으로 확인한다.

다음은 HTTPS 연결까지 완료했을 때의 목표 구성이다. 프록시와 도메인은 추가 설정이 필요하다.

```text
팀원 브라우저 / 프런트엔드
        |
        | HTTPS API 요청
        v
API 도메인 -> 고정 IPv4
        |
        v
Lightsail 인스턴스 1대
  HTTPS 프록시 (Nginx 또는 Caddy, 추가 설정)
        |
        | 127.0.0.1:8000
        v
  Docker Compose
    FastAPI (작업 프로세스 1개)
      |-- PostgreSQL 17 + pgvector -> postgres-data 볼륨
      |-- Redis (세션 저장)        -> redis-data 볼륨
      `-- 외부 LLM 등 API 호출

    migrate -> PostgreSQL 스키마 갱신 후 종료

  두 데이터 볼륨은 기본적으로 이 인스턴스의 디스크를 사용

PostgreSQL 백업 -> 서버 외부의 비공개 저장소 (추가 설정)
```

| 구성 요소 | 역할과 현재 상태 |
| --- | --- |
| FastAPI | 요청 처리와 DB 접근. 배포용 설정은 준비됨 |
| PostgreSQL | 콘텐츠 본문, 이미지 URL, 사용자·대화 등 영구 데이터. pgvector 확장 필요 |
| Redis | 현재는 세션 저장소. 콘텐츠 원본 저장소나 작업 큐로 구현되어 있지 않음 |
| 고정 IP·HTTPS 프록시 | 외부 접속 경로. 인스턴스 생성 후 추가 설정 |
| 이미지 객체 저장소 | 직접 생성·업로드하는 이미지 파일을 보관할 때 도입. 현재 미연결 |
| 생성 Worker·작업 큐 | 콘텐츠 생성 작업을 별도 실행하는 향후 구성. 현재 배포 이미지에 미포함 |

현재 [Compose](../compose.deploy.yaml)는 API를 호스트의 루프백 주소에만 연결하므로 `공인 IP:8000`으로 직접 접속할 수 없다. PostgreSQL과 Redis는 외부 포트를 열지 않는다. 프런트엔드와 API는 HTTPS와 같은 사이트의 도메인 구성을 권장한다. 예를 들어 `test.example.com`과 `api.test.example.com`을 사용하고, 실제 프런트엔드 주소를 CORS에 등록한다. 이는 현재 `SameSite=Lax` 세션 쿠키에 맞춘 구성이다.

OAuth는 별도 작업으로 남아 있다. 최초 배포에서는 공개 API와 상태 확인을 검증하고, 로그인·온보딩 등 인증이 필요한 통합 테스트는 OAuth 연결 후 진행한다.

## 이미지와 데이터가 늘어날 때

**저장 용량과 실행 메모리는 별도로 확장한다.** 이미지 파일이 쌓인다는 이유만으로 메모리 특화 서버를 선택하지 않는다. RAM은 API·DB·생성 작업이 실행 중 사용하는 공간이고, 이미지 파일과 DB의 누적 데이터는 디스크 또는 객체 저장소를 사용한다.

현재 [콘텐츠 모델](../backend/app/models/content.py)은 이미지 파일 대신 `image_url`을 저장하며, [이미지 적재 코드](../backend/app/seeds/content_images.py)도 외부 이미지 URL을 연결한다. 직접 생성하거나 업로드하는 이미지까지 보관하려면 다음 흐름을 추가한다.

```text
콘텐츠 생성 또는 업로드
  |-- 이미지 파일 -> Lightsail Object Storage 또는 S3
  `-- 본문·이미지 참조 -> PostgreSQL

브라우저 -> 이미지 저장소의 제공 URL 또는 CDN -> 이미지 표시
```

객체 저장소는 이미지 같은 파일을 서버 디스크와 분리해 보관한다. 이미지 조회량이 커지면 CDN을 추가해 이미지 전송 부하를 분산한다. 버킷 생성만으로 기존 코드가 파일을 업로드하는 것은 아니므로, 업로드·접근 권한·삭제 처리도 구현해야 한다. [AWS 객체 저장소 안내](https://docs.aws.amazon.com/lightsail/latest/userguide/amazon-lightsail-faq-buckets.html)

용량은 `하루 생성 건수 × 콘텐츠당 이미지 수 × 평균 파일 크기 × 보관 일수`로 추정한다. 예를 들어 하루 1,000건에 이미지 2장씩, 장당 500KB라면 약 1GB/일, 30GB/30일이다. 이는 예시이며 썸네일·파일 버전·백업·전송량은 별도다. DB에는 본문 외에 인덱스와 변경 기록도 쌓이므로 실제 디스크 증가량을 함께 측정한다.

DB 디스크만 부족하다면 추가 블록 디스크로 DB 볼륨을 옮기거나 별도 DB 서버로 이전하는 방법도 있다. 추가 디스크는 여러 API 서버가 동시에 공유하는 DB나 파일 시스템을 대신하지 않는다. [AWS 블록 스토리지 안내](https://docs.aws.amazon.com/lightsail/latest/userguide/amazon-lightsail-faq-block-storage.html)

## 부하에 따른 증설 방향

첫 대응은 작은 단위의 사양 증설 또는 저장소 분리다. 이후 API와 생성 작업, DB의 부하를 나누어 필요한 부분만 확장한다. 아래 단계는 고정 일정이 아니며, 먼저 나타나는 병목에 따라 적용한다.

| 상황 | 대응 | 필요한 준비 |
| --- | --- | --- |
| 초기 팀 테스트 | 범용 4GB 서버 1대 | HTTPS, 백업, 상태·자원 모니터링 |
| 이미지 보관량·조회량 증가 | 객체 저장소, 필요 시 CDN 추가 | 이미지 업로드·참조·삭제 경로 구현 |
| API와 DB의 메모리 부족 | 우선 범용 4GB → 8GB 증설 | 사용량 확인, 점검 시간 확보, 데이터 이전 검증 |
| 생성 작업 때문에 API가 느려짐 | 생성 Worker를 별도 서버에 배포 | 작업 큐, 재시도, 중복 실행 방지, 동시 실행 수 제한 |
| DB 쿼리·디스크 부하 증가 | 쿼리·인덱스 점검 후 DB 분리 또는 증설 | pgvector 지원, 데이터 이전, 백업·복구 검증 |
| API 요청량 증가 또는 API 서버 이중화 필요 | 로드밸런서 뒤 API 서버 2대 이상 | 공통 DB·Redis, 작업 분리, 서버 간 요청·세션 검증 |

생성 Worker는 API 요청 처리와 분리해 콘텐츠 생성·임베딩 같은 작업을 담당한다. 로컬 모델을 쓰면 모델과 동시 실행 수에 맞춰 RAM·CPU 또는 GPU를 따로 산정한다. 외부 생성 API를 쓰는 경우에는 외부 서비스의 속도 제한과 비용도 확인한다. 현재 [백엔드 이미지](../backend/Dockerfile)는 `agent/` 코드를 포함하지 않으므로 Worker 배포는 별도 구현이 필요하다.

여러 서버로 확장할 때의 목표 구조는 다음과 같다.

```text
브라우저 -> HTTPS 로드밸런서 -> API 서버 A / API 서버 B
                                 |
                                 |-- 공통 PostgreSQL
                                 |-- 공통 Redis (세션)
                                 `-- 작업 큐 -> 생성 Worker
                                                  |-- PostgreSQL
                                                  `-- 이미지 객체 저장소

브라우저 -> 이미지 제공 URL / CDN -> 이미지 객체 저장소
```

API 서버마다 독립된 DB를 복제해서 실행하면 요청이 도착한 서버에 따라 데이터가 달라진다. 모든 API 서버는 동일한 DB와 세션 저장소를 사용해야 한다. 이는 [AWS 로드밸런싱 구성 안내](https://docs.aws.amazon.com/lightsail/latest/userguide/configure-lightsail-instances-for-load-balancing.html)의 데이터 계층 분리 원칙과도 맞는다.

**현재 Compose를 다른 서버에 그대로 복사하는 것만으로 수평 확장이 완성되지는 않는다.** 다음 변경이 선행되어야 한다.

- 서버 외부 DB·Redis에 연결하도록 환경변수와 네트워크를 변경한다. 현재 주소는 Compose 내부 서비스 이름으로 고정되어 있다.
- 현재 [채팅 생성 작업](../backend/app/api/v1/chat/router.py)은 API 프로세스 안에서 실행되고 질문·결과는 DB에 기록된다. 재시작으로 중단된 작업이 처리 중 상태에 남지 않도록, 작업 큐와 Worker에 재시도·중복 실행 방지·시간 초과 복구를 구현한다. Redis 세션 공유만으로 이 문제가 해결되지는 않으며, 작업 큐의 메모리·보존 정책은 세션 저장소와 별도로 설계한다.
- 모든 API 서버의 세션 쿠키 이름·Redis 키 접두사·CORS 설정을 일치시킨다. API 서버 수에 따라 늘어나는 DB 연결 수가 DB의 연결 한도를 넘지 않도록 연결 풀도 조정한다.
- DB 마이그레이션은 배포 과정에서 한 번 실행하고, API 서버별 동시 실행을 피한다.
- 로드밸런서가 접근할 프록시·헬스체크 경로와 신뢰할 프록시 주소를 설정한다. 현재의 루프백 API 포트를 그대로 로드밸런서 대상으로 사용할 수는 없다.
- DB 분리 시 호스트 방화벽·DB 접근 정책을 설정한다. Lightsail의 인스턴스 방화벽은 공인 IP 트래픽에 적용되며 사설 IP 접근 제한을 대신하지 않는다. [AWS 방화벽 안내](https://docs.aws.amazon.com/lightsail/latest/userguide/understanding-firewall-and-port-mappings-in-amazon-lightsail.html)

관리형 DB로 이전할 때는 PostgreSQL 버전뿐 아니라 필요한 pgvector 확장 지원 여부도 확인한다. API를 2대로 늘려도 DB·Redis가 각각 1대라면 해당 서버 장애 시 서비스가 중단될 수 있다. 데이터 계층 이중화와 자동 복구는 가용성 목표에 따라 별도로 설계한다. 이 계획은 초기에는 수동 증설을 전제로 하며 자동 증설은 포함하지 않는다.

## 인스턴스 사양을 올리는 절차

Lightsail은 기존 서버의 크기를 즉시 바꾸는 방식이 아니라 **스냅샷으로 더 큰 인스턴스를 만든 뒤 접속을 전환**한다. 고정 IPv4를 새 인스턴스로 옮기면 같은 접속 주소를 유지할 수 있다. 스냅샷으로 더 작은 플랜을 만드는 것은 지원되지 않아, 축소하려면 별도의 데이터 이전이 필요하다. [AWS 사양 증설 절차](https://docs.aws.amazon.com/lightsail/latest/userguide/how-to-create-larger-instance-from-snapshot-using-console.html)

DB까지 한 서버에 있는 초기 구성에서는 다음과 같이 점검 시간을 확보한다.

1. 이전 이미지·환경 설정을 보관하고, PostgreSQL 백업과 복원 가능 여부를 확인한다. Redis 세션을 보존할지 재로그인을 허용할지도 정한다.
2. 외부 요청과 생성 작업의 신규 접수를 막는다. 진행 중 쓰기 작업을 완료하거나 정리하고, API·Worker 등 모든 쓰기 주체를 멈춘다.
3. PostgreSQL·Redis를 정상 종료하고 스냅샷을 생성한다. 기존 서버는 새 쓰기를 받지 않도록 유지한다.
4. 같은 리전에 더 큰 인스턴스를 생성한다. 새 서버에서 서비스나 예약 작업이 자동으로 시작하는지 확인하고, 검증이 끝날 때까지 실제 사용자 요청과 생성 작업을 받지 않는다.
5. 새 서버에서 데이터 볼륨·DB 스키마·Redis·환경 설정·HTTPS 프록시를 확인한다. 세 상태 경로와 공개 API를 검증하고, 데이터 수와 주요 레코드를 확인한다.
6. 고정 IP를 새 서버로 이동하고 접속·인증서·방화벽을 확인한다. 새 서버만 쓰기를 받도록 서비스를 연다.
7. 이전 서버는 중지 상태로 보관하다가 새 서버의 안정성과 백업을 확인한 뒤 정리한다.

전환에는 서비스 중단 시간이 발생할 수 있으므로 복제·기동·검증 시간을 사전 연습으로 측정한다. 새 서버에 쓰기를 허용하기 전에는 이전 서버로 되돌리기 쉽지만, **새 데이터가 저장된 뒤에는 IP만 되돌리면 해당 데이터가 누락된다.** 그때는 다시 쓰기를 중지하고 최신 데이터를 이전하거나 새 서버에서 문제를 수정한다. 이전 서버와 새 서버가 함께 존재하는 기간의 비용도 고려한다.

## 증설 판단과 백업

서버 수는 가입자 수보다 실제 요청과 자원 사용량을 보고 결정한다. 아래 수치는 팀 테스트용 경보 기준의 초안이며, 첫 부하 테스트 결과에 맞춰 조정한다.

| 관찰 대상 | 점검 기준 초안 | 대응 |
| --- | --- | --- |
| 서버 메모리 | 사용 가능한 메모리 20% 미만이 15분 지속, 반복적인 메모리 부족 종료 | 누수·동시 작업 수 점검 후 RAM 증설 또는 Worker 분리 |
| CPU | 지속적인 CPU 부하와 버스트 잔량 감소 | 생성 작업 분리, 처리량 제한 또는 사양 변경 |
| 디스크 | 사용량 70% 경고, 80% 도달 또는 30일 내 소진 예상 | 로그·DB 증가 원인 확인, 저장소 확장 |
| API | 비슷한 요청에서 p95 응답 시간이 평소의 2배로 지속 상승하거나 오류 증가 | 외부 API·DB·서버 중 지연 원인 확인 후 해당 부분 개선 |
| Redis | 데이터 메모리가 설정 한도의 80%에 접근하거나 세션 저장 실패 | 세션 만료·누적량 확인 후 한도와 서버 RAM 함께 조정 |
| 생성 작업 | 작업 대기 시간이 목표를 초과 | 외부 API 한도와 DB 여유를 확인하고 Worker 처리량 조정 |

CPU·네트워크·버스트 지표는 Lightsail에서 확인한다. RAM과 디스크 사용량은 서버에서 측정하고, 지속적인 경보가 필요하면 CloudWatch Agent 등 수집 구성을 추가한다. [AWS 메모리 모니터링 안내](https://aws.amazon.com/blogs/compute/monitoring-memory-usage-lightsail-instance/)

현재 Redis의 `maxmemory=128mb`는 데이터 메모리에 대한 설정으로 컨테이너 전체 RAM 제한이 아니다. `noeviction` 정책 때문에 한도에 도달하면 새 세션 저장이 실패할 수 있다. 이미지 보관량과 Redis 메모리 요구량을 직접 연결해서 계산하지 않는다.

DB 영속 볼륨과 같은 서버에 둔 백업은 서버 손실에 대비한 복구 수단으로 충분하지 않다. 테스트 데이터가 쌓이기 시작하면 서버 외부의 비공개 저장소에 정기 DB 백업을 보관하고 별도 환경에서 복원을 연습한다. 백업 주기는 팀이 허용할 데이터 손실 범위에 맞춘다. 예를 들어 하루마다 정상 백업하면 마지막 백업 이후 최대 약 하루의 변경분을 잃을 수 있다. 복구에 걸리는 시간도 실제 복원으로 측정한다.

## 팀 공유용 설명

초기에는 Lightsail 범용 서버 한 대에 백엔드, PostgreSQL, Redis를 배포해 팀 테스트를 시작한다. 직접 생성하는 이미지는 객체 저장소에 보관해 서버 사양과 독립적으로 저장 용량을 늘린다. 실제 메모리 부족이 확인되면 먼저 서버 사양을 올리고, 콘텐츠 생성 작업이 API 응답을 방해하면 생성 서버를 분리한다. 이후 요청량이 증가하면 DB와 세션 저장소를 공통으로 사용하는 API 서버를 추가하고 로드밸런서로 요청을 분산한다. 증설 시점은 가입자 수보다 응답 시간, 메모리, 디스크 증가량과 작업 대기 시간을 기준으로 판단한다.
